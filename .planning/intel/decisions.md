**취소선 이력 처리 규칙**

M0 결정 로그 자체가 규약을 정하고 있다 — "결정이 뒤집히면 기존 항목을 지우지 말고 **취소선 + 사유**를 남긴다"(`docs/GPTRPG-M0-decisions.md` 문서 목적란). 따라서 취소선 항목은 경쟁 변형이 아니라 **이력**이며, 아래에서는 후행 결정을 권위로 기록하고 이력은 `decision` 안에 함께 남겼다.

**M0는 완료가 아니다**

이 결정들은 M0의 **설계** 부분만 닫는다. M0의 나머지 절반인 킬 크리테리아 실험은 미실시이며, 가설 H1(재미)·H5(원가)가 진짜 킬 조건을 들고 있다. `requirements.md` 참조.

## D1. 플레이 모델 = 실시간 동기 파티

- source: docs/GPTRPG-M0-decisions.md §2 D1
- status: locked
- decision: 실시간 동기 파티를 먼저 만든다. 비동기(PbP)·솔로는 후속 마일스톤에서 같은 엔진 위에 추가한다. 근거는 방향 비대칭 — 실시간 → 비동기 전환은 쉽고(비동기는 실시간의 퇴화 케이스) 비동기 → 실시간은 재작성에 가깝다.
- scope: 플레이 모델, 마일스톤 순서

## D2. "세션"을 1급 개념에서 강등

- source: docs/GPTRPG-M0-decisions.md §2 D2
- status: locked
- decision: 캠페인 = 영속 상태(진짜 게임), 세션 = 단순 접속 구간(뷰포트). 원 기획안의 "세션 종료 시 컴파일", "세션당 토큰 예산" 등 세션 중심 서술을 전부 재작성한다. 안전 정지 지점(장면 경계·전투 종료·목표 달성 직후 "지금 끊기 좋습니다" 표시, 전투 중간 이탈 시 경고 + 상태 스냅샷 강제)을 도입한다. 시작 시 플레이 예정 시간은 힌트로만 받고 강제하지 않는다.
- scope: 캠페인/세션 개념, 중단·재개, 페이싱

## D3. 코어 아키텍처 = 이벤트 소싱 + Session Actor + PacingPolicy

- source: docs/GPTRPG-M0-decisions.md §2 D3
- status: locked
- decision: 4계층(전송 어댑터 / Session Actor / Rules Core / Event Log + 파생 상태 스냅샷). 불변 규칙 3가지 — ① Rules Core는 시간을 모른다(타이머·접속 상태 개념 금지) ② Session Actor가 유일한 쓰기 주체다(세션당 단일 직렬화 지점) ③ 모드는 코드 경로가 아니라 PacingPolicy 설정값이다(새 모드 추가 = 표에 열 하나). 이벤트 소싱은 **M0에서 확정해야 하는 유일한 되돌릴 수 없는 결정**이다 — CRUD 제자리 변경으로 먼저 짜면 재접속 델타 동기화·리플레이·비동기 참여·관전자 합류·다시보기가 전부 나중에 불가능해진다.
- scope: 코어 아키텍처, 이벤트 소싱, 동시성, 진행 정책

## D4. 첫 타깃 룰북 = 던전월드 계열 (PbtA)

- source: docs/GPTRPG-M0-decisions.md §2 D4
- status: locked
- decision: 첫 타깃을 던전월드 계열(PbtA)로 한다. D&D 5e는 M4로 이동하며, 원 기획안 3.1절의 "가장 복잡한 것으로 엔진 완결성 검증" 논리를 폐기한다. 핵심 비대칭 — PbtA는 사람에게도 LLM에게도 쉽고, 5e는 둘 다 어렵다. 초심자가 가장 헤매는 부분(액션 이코노미·그리드·리소스 추적)이 정확히 LLM이 가장 못하는 부분이다.
- scope: 첫 타깃 룰북, 마일스톤 배치

## D5. 핵심 설계 원칙 2 수정 — 전용 어댑터 폐기

- scope: 설계 원칙 2, 룰북 추상화

## D6. 판정 커널 로드맵

- source: docs/GPTRPG-M0-decisions.md §2 D6
- status: locked
- decision: 커널 6종 로드맵 — PbtA 티어(2d6+스탯 → 10+/7-9/6-)와 d100 롤언더가 M0, d20 롤오버가 M1(UGC 수요 1순위), 다이스풀 성공셈과 Year Zero가 M2, FATE/퍼지가 M3. M0에 2개를 넣는 이유는 판정 방향(롤오버 vs 롤언더)과 성공 등급 체계가 서로 달라서 둘이 같은 효과 DSL 위에서 돌면 추상화가 옳다는 강한 증거가 되기 때문 — 커널이 하나면 잘못된 추상화를 만들어도 알 수 없다. 6개 커널이 시장의 80~90%를 덮는다.
- scope: 판정 커널(판정 방식), 마일스톤 배치

## D7. 효과 DSL 도입 + 자동화율 지표

- source: docs/GPTRPG-M0-decisions.md §2 D7
- status: locked
- decision: 3층 구조(룰북 정의 = 데이터 / 효과 DSL = 데이터 / 판정 커널 = 코드)를 도입한다. 원자 연산 목표 30~50개. DSL로 표현 못 하는 롱테일은 `requires_ruling`으로 표시해 Ruling 계층이 받는다 — 하드 실패가 아니라 우아한 성능 저하. 자동화율 = DSL로 자동 처리된 판정 수 / 전체 판정 수. 모든 룰북은 플레이 가능하며 다만 자동화율이 다르다. 룰북 등록 시 자동 산출해 유저에게 표시한다.
- scope: 효과 DSL, 자동화율 지표, 룰북 표현력

## D8. 시나리오는 룰북에 종속되지 않는 독립 계층

## D9. 시나리오 포맷 = 플러그인 인터페이스, 4종

- source: docs/GPTRPG-M0-decisions.md §2 D9
- status: locked

- scope: 시나리오 포맷, 위협 시계

## D10. 외부 메신저 전제 → 조율 시스템 대폭 축소

- source: docs/GPTRPG-M0-decisions.md §2 D10
- status: locked
- decision: 플레이어 간 대화와 순서 조율은 외부 메신저에서 끝나므로 플랫폼이 강제하지 않는다. 스포트라이트 토큰(선착순 락) 삭제 / 상반 행동 이니셔티브 강제 정렬 삭제 / 3초 리액션 팝업 완화(타이머 없는 대기, 짧은 타이머는 스트리머 프리셋에만) / AFK 타임아웃 강제 스킵 데몬 대폭 축소("자리 비움" 표시 + 수동 넘기기) / 파티 채팅·보이스·친구 시스템 안 만듦(초대 링크 하나로 대체). 대체 개념은 락이 아니라 신호등.

## D11. 재개(Recap)를 1급 기능으로 승격

- source: docs/GPTRPG-M0-decisions.md §2 D11
- status: locked
- decision: 재개를 1급 기능으로 올린다. 파티 리캡(3~5문장) / 개인 리캡 / 관계 장부. 원 기획안 4장의 압축 시스템(구조화 서사 레저 + 엔티티 장부)은 토큰 절약 용도로만 설계되어 있었으나 같은 데이터로 유저용 리캡을 만든다. 압축 품질 검증 기준 교체 — 기존(스키마 준수 + 엔티티 누락 없음) → "3주 뒤에 읽고 게임을 이어할 수 있는가".
- scope: 재개(리캡), 압축 시스템 목적, 이탈 방지

## D12. 목표 재정의 — 완벽 방어에서 투명성으로

- source: docs/GPTRPG-M0-decisions.md §2 D12
- status: locked
- decision: 목표를 "룰북 100% 재현 / 할루시네이션 완벽 방어"에서 "틀렸을 때 유저가 알아챌 수 있고 고칠 수 있다 / AI가 계산한 것과 판단한 것이 구분되어 보인다"로 교체한다. 필요한 3가지 — ① 판정 근거 표시(Show Your Work) ② 자동/재량 구분 표시 ③ 정정 가능성(방장이 판정을 뒤집고 홈브루로 저장). 사유는 100% 재현이 구조적으로 불가능하고(룰북은 자연어로 쓰인 열린 시스템), 인간 GM도 100% 재현하지 않으며, 문제의 성격이 정확도가 아니라 신뢰이기 때문.
- scope: 제품 목표, 투명성, 신뢰

## D13. 제품 정체성 우선순위 — 무엇이 양보 불가인가

- source: docs/GPTRPG-M0-decisions.md §2 D13
- status: locked
- decision: ① 룰 정합성 = 대체 가능(D12의 투명성 + 정정 가능성으로) / ② 결과의 무게 = 양보 불가 / ③ 플레이어 주체성 = 양보 불가 / ④ 불확실성 = 양보 불가 / ⑤ 공동 창작 = 양보 불가 / ⑥ 전술적 깊이 = 연기(M4). 앞으로의 모든 설계 결정은 이 표를 기준으로 채점한다.
- scope: 제품 정체성, 설계 채점 기준

## D14. 주사위는 순수 코드 — LLM 관여 지점 없음

- source: docs/GPTRPG-M0-decisions.md §2 D14
- status: locked
- decision: 주사위·판정 연산에 LLM 관여 지점을 두지 않는다. 어떤 판정이 발동하는가 = 파서 + Ruling 계층(LLM), 무슨 주사위를 굴리는가 = 판정 커널 + 효과 DSL(순수 코드), 실제 굴림 = 암호학적 난수 생성기(순수 코드), 결과 해석 = 판정 커널(순수 코드), 결과 묘사 = GM 에이전트(LLM, 수치는 못 바꿈). Provably Fair는 ④ 불확실성이 양보 불가이므로 제품 약속을 증명 가능하게 만드는 장치로 유지한다. (이력: 초기 비판 W5 "Provably Fair가 있지도 않은 문제를 푼다" 철회.)
- scope: 주사위, 난수, Provably Fair, LLM 경계

## D15. 이탈 행동의 "제재"는 두 층

- source: docs/GPTRPG-M0-decisions.md §2 D15
- status: locked
- decision: 서사적 대가(딴 길로 샘·엉뚱한 짓)는 막지 않고 세계가 반작용한다 — 전선의 시계는 계속 돌고 돌아왔을 때 상황이 나빠져 있다. 사회적 제재(타 플레이어 괴롭힘·안전 선 침범)는 하드 블록 — 안전 도구 + 방장 권한. TRPG의 정통 해법은 막는 게 아니라 대가를 치르게 하는 것이다.
- scope: 이탈 행동, 제재 구조

## D16. Ruling 계층 = 닫힌 집합 분류 + 플레이어 확인

- source: docs/GPTRPG-M0-decisions.md §2 D16
- status: locked
- decision: 처리 파이프라인 — ① 무브 분류[닫힌 집합] ② 능력치 선택[닫힌 집합] ③ 주사위[순수 코드] ④ GM 무브 선택[닫힌 집합, 7-9/6-일 때만] ⑤ 서술[자유 생성]. LLM은 ①②④에서 분류만, ⑤에서 서술만 한다. 판정 발동 방식은 **(다) 혼합형** 확정 — LLM이 제안하면 플레이어가 확인한다. 부수 효과로 신뢰도 임계값(0.9)과 폴백 UI를 폐기하고 신뢰도는 UI 강도로만 쓴다. Ruling 계층으로 들어오는 3종 — 룰북에 없는 창의적 행동 / 효과 DSL로 표현 못 한 롱테일 / 판정이 필요 없는 그냥 되는 일(플레이의 절반 이상). 자주 나오는 Ruling은 방장이 홈브루로 굳혀 자동화로 승격시킬 수 있다.
- scope: Ruling 계층, 판정 발동, 신뢰도 임계값, GM 무브

## D17. 아키텍처 축소 — 서브에이전트 10개 → 4개

- source: docs/GPTRPG-M0-decisions.md §2 D17
- status: locked
- decision: 서브에이전트를 4개로 축소한다 — `action_classifier`(Light), `master_gm`(M0에서 Heavy), `onboarding_agent`(Medium), `context_summarizer`(Light). 삭제·병합·강등 — combat_parser/exploration_parser 병합 → action_classifier, dice_narrator 병합 → master_gm, entity_ledger_keeper 코드로 강등, rules_interpreter 보류(M1 부활 가능), reaction_classifier·initiative_resolver 삭제. 메시지 버스도 축소 — gRPC + Redis Streams 이중 구성은 M0에 과하며 Session Actor가 유일한 직렬화 지점이므로 인프로세스 함수 호출로 충분하다. 턴당 LLM 호출 3~4회 → 2회, 실제 평균 약 1.5회. W7(뷰별 정보 분리)은 가시성 필드로 축소하고 시야 계산은 M4로 이동.
- scope: 서브에이전트 구성, 메시지 버스, 턴당 호출 수, 가시성

## D18. `master_gm` 모델 티어 — M0은 Heavy, 이후 이원화

- source: docs/GPTRPG-M0-decisions.md §2 D18
- status: locked
- decision: M0은 Heavy 고정. 이후 (C) 상황별 이원화로 내린다 — 일상 서술은 Medium, 결정적 순간(전선 징조 진행·캐릭터 죽음·강한 성공/실패)은 Heavy. 순서를 이렇게 잡는 이유는 Heavy로도 재미없으면 제품이 성립하지 않아 거기서 판단이 끝나기 때문이며, 반대로 하면 모델이 작아서 재미없는 건지 설계가 틀려서인지 구분할 수 없다. M0에서 재는 것은 원가가 아니라 품질 상한선이다 — 단 원가가 생존 가능한 범위인지는 답해야 한다.
- scope: 모델 티어, M0 측정 목적

## D19. 모델 전략 — 에이전트별 분리, 교체 가능하게

- source: docs/GPTRPG-M0-decisions.md §2 D19
- status: locked
- decision: 모델을 하나로 통일해 판단하지 않는다. 프로바이더 추상화 계층을 M0에 넣어 에이전트별 모델·프로바이더를 설정값으로 만든다(지금은 공짜, 나중은 재작성). 자체 호스팅은 M0의 결정 사항이 아니다 — TRPG는 이용률 패턴이 최악(저녁 8시~자정 집중)이라 실효 원가가 이론값의 3~4배가 된다. 한국어 서사 품질이 특수 변수이므로 영어 벤치마크와 별도로 측정한다. 캐싱이 지배 변수이며, 프롬프트 조립 순서를 안정성 순서(영구 고정 → 세션 고정 → 턴마다 변함)로 짜는 것은 최적화가 아니라 M0의 설계 제약이다.
- scope: 모델 전략, 프로바이더 추상화, 캐싱 제약, 자체 호스팅

## D20. 수익 모델

- source: docs/GPTRPG-M0-decisions.md §2 D20
- status: locked

- scope: 수익 모델, 무료 티어, 코스메틱

## D21. 위협 시계 — 데이터 구조와 진행 규칙

- source: docs/GPTRPG-M0-decisions.md §2 D21
- status: locked
- decision: 대본이나 분기 트리가 아니라 "나쁜 일 목록 + 순서"만 저장하고 칸 사이의 사건과 플레이어 대응은 AI가 즉흥 생성한다. 진행 규칙 세 가지를 함께 쓴다 — ① 실패 누적 카운터(판정 실패 시 +1, 기본 3회 도달 시 강제 1칸 진행 후 초기화; 봐주기 방지 안전장치) ② 조건 트리거(시간 경과·장소·선행 칸) ③ AI 선택(GM 대응 목록에서 "시계 진행"). ③만 있으면 봐주기가 생기고 ①만 있으면 기계적이 된다. ①이 관측 지표를 공짜로 만든다 — "실패는 많은데 시계가 안 돈다"를 사후 자동 집계 가능. 확정 규격 = 시계 하나 4~6칸 / 8~15시간, 무료 1~2칸. 저작 주체 (다)안 — 우리 3~5개(초보자 첫 경험은 반드시 이 중에서) / 유저 무한 / AI 무한(초보자 첫 경험에는 미사용), 셋이 완전히 같은 양식.
- scope: 위협 시계 구조, 진행 규칙, 관측 지표, 무료 단위, 저작 주체

## D22. 캐릭터 만들기 — 7가지 동작 + 애착 설계

- source: docs/GPTRPG-M0-decisions.md §2 D22
- status: locked
- decision: 어떤 룰북이든 캐릭터 만들기는 7가지 동작의 조합으로 표현된다(하나 고르기 / 여러 개 고르기 / 숫자 나눠 담기 / 정해진 숫자 배치 / 주사위로 채우기 / 자유 서술 / 자동 계산). 룰북 데이터가 "만들기 단계 목록"을 갖고 시스템이 순서대로 실행한다. 애착 장치 6개 — 숫자를 서술로 번역해 실시간 표시 / 선택지를 이야기 질문으로 감싸기 / 순서 바꾸기(재미있는 것 먼저, 기계적 단계는 추천값 선채움) / 되돌리기 상시 / 자유 서술 → AI 추천(자동 확정 금지) / 완성 순간 캐릭터 카드 보상. M0의 범위는 데이터 형태·절차·검증 규칙이며 화면 배치·컴포넌트·반응형은 M0가 아니다. (이력: ~~프리젠 우선 안 — 초보자에게 완성품 집어들기(30초)를 기본 경로로 제공~~ 폐기. 사유 — ② 결과의 무게(양보 불가)와 충돌한다. 30초에 집어든 캐릭터가 죽으면 아프지 않다.)
- scope: 캐릭터 생성, 7가지 동작, 애착 설계, M0 범위선

## D23. 안전 장치 — AI가 갖지 못한 "GM의 눈"

- source: docs/GPTRPG-M0-decisions.md §2 D23
- status: locked
- decision: 안전 장치는 규정 준수 기능이 아니라 AI가 갖지 못한 GM의 눈을 대체하는 장치다. 정통 TRPG 표준 도구를 그대로 쓴다(0번 모임 / 선과 장막 / 정지 카드). 4개 층 — 1층 방 생성 시 톤·선·장막 설정 / 2층 정지 카드(익명·설명 요구 없음·즉시 작동의 세 원칙 절대, 강도 2단계) / 3층 AI가 넘지 않게 하는 3겹(프롬프트 상시 포함, 출력 전 검사, 장막 전환 처리) / 4층 신고·강퇴·차단. 핵심 설계 판단 — 안전 장치가 몰입을 깨면 안 되므로 작동 사실을 알리지 않고 이야기를 자연스럽게 돌린다("안전 장치 작동 사실을 언급하지 말 것"을 AI에 명시 지시).
- scope: 안전 장치, 선과 장막, 정지 카드, 모더레이션

## D24. 사람이 오고 가는 문제 — 친구 초대 링크 우선, 낯선 사람 매칭은 미룬다

- source: docs/GPTRPG-M0-decisions.md §2 D24
- status: locked
- decision: M1은 친구 초대 링크만, 공개방 매칭은 M2 이후. 매칭에는 신고·차단·성인 인증·톤 필터가 전부 딸려 오는 큰 덩어리이므로 초대 링크만으로 먼저 출시하면 M1 범위가 크게 줄어든다. M1에 남는 것 — 초대 링크 / 정지 카드 / 선·장막 방 설정 / AI 출력 검사 / 중도 이탈 처리 / 정원 미달 진행 / 첫 만남 캐릭터 소개 / 진행 중 합류. 사람이 빠질 때 세 경우를 다르게 처리한다(잠깐 자리 비움 / 오늘 중도 이탈 = 서사적 배경화 / 영구 이탈 = 캐릭터 보존, 방장 판단). AI가 남의 캐릭터를 조종하지 않는다 — ③ 플레이어 주체성 위반. 정원이 안 차도 진행한다.
- scope: 매칭, 초대 링크, 드롭인/드롭아웃, 정원 미달

## D25. 캐릭터 라이프사이클 — 유형 목록으로

- source: docs/GPTRPG-M0-decisions.md §2 D25
- status: locked
- decision: 유형은 우리가 코드로 구현하고 어느 유형인지는 룰북이 데이터로 선언한다. 성장(경험치 누적 / 사용 기반 개선 / 점수 지급 / 성장 없음) · 회복(휴식 / 시간 경과 / 치료 판정 / 안전지대 / 거의 회복 안 됨) · 장비(개별 품목 + 무게·슬롯 = 1순위 구현 / 추상 회분 / 하중 등급만 / 관리 없음) · 죽음(즉사 / 빈사→안정화 / 협상 / 부상 누적 / 캐릭터 교체 전제) · 화폐. 경험치 획득 조건은 룰북이 별도 정의하며 우리가 정하지 않는다. 플랫폼 층으로 남는 것 — 세션 마감 시점의 "자리", 죽은 캐릭터 기록 보존, 레벨업 화면의 7가지 동작 재사용, 숫자→서술 번역. (이력: ~~초안 — 던전월드의 규칙(실패→경험치 / 세션 끝 질문 3개 / 장비 회분 추상화 / 죽음 협상 / 5분 생성 목표)을 플랫폼 기능으로 올림~~ 폐기. 사유 — 원칙 2의 정신과 원칙 3 위반.)
- scope: 캐릭터 라이프사이클, 성장·회복·장비·죽음·화폐

## D26. 룰북의 실제 형태 — 원문을 버리지 않는다

- source: docs/GPTRPG-M0-decisions.md §2 D26
- status: locked
- decision: 룰북은 세 부분이다 — ① 원문(자연어, 게임 중에도 살아 있음) ② 구조화 데이터 ③ 연결(①의 어느 문단이 ②의 어느 항목인가). 유저가 쓰는 것은 ①뿐이며 ②는 도구가 만들고 유저가 확인, ③은 자동으로 붙는다. 확인할 때 구조화 데이터를 보여주지 않고 **시험 판정 결과**를 보여준다. 점진적 구조화 — 원문만 있어도 플레이되고(자동화율 20%) 자주 나오는 판정을 굳히며 자란다. "굳히는" 메커니즘은 D12·D16의 홈브루 승격이 이미 담당하므로 별도 기능이 아니다. 안전한 기본값 — 확실한 것만 구조화하고 애매한 것은 원문 + 재량 판정으로 남긴다. 룰북 파일 업로드는 M1 포함 확정.
- scope: 룰북 형태, 원문 보존, 저작 흐름, 점진적 구조화

## D27. 룰북 파일 목차 + 판정 엔진 형태 (2개 방식으로 검증)

- source: docs/GPTRPG-M0-decisions.md §2 D27
- status: locked
- decision: 룰북 파일 목차 8항목(메타 / 원문 / 캐릭터 정의 / 판정 정의 / 효과 목록 / 라이프사이클 / 적·위협 정의 / 원문↔구조 연결표). 두 판정 방식 비교 검증에서 세 가지 발견 — ① 결과 등급을 코드에 고정하면 안 된다(룰북이 자기 등급 집합을 선언하며, 등급이 이름 목록이 아니라 수치인 경우도 받아야 함) ② 수정치도 유형 목록이 필요하다(숫자 가감 / 주사위 추가·제거 / 목표값 변경 / 재굴림) ③ 두 방식이 같은 인터페이스에 들어간다(검증 통과). M0 범위선 — 목차·검증·선언 사항 결정·원자 연산 규모 판단까지가 M0이고, 필드 단위 상세 규격·실제 구현·최종 목록·스키마 문서는 M1.
- scope: 룰북 목차, 판정 인터페이스, 등급·수정치 표현, M0 범위선

## D28. 자유 텍스트 해석 검증 계획

- source: docs/GPTRPG-M0-decisions.md §2 D28
- status: locked
- decision: 검증 방법은 ① 플랫폼이고 정답 데이터는 룰북마다 따로 필요하다. D16이 신뢰도 임계값을 폐기했으므로 측정 대상이 정확도에서 **마찰**로 바뀐다 — 첫 제안이 맞음(엔터 한 번, 이상적) / 첫 제안 틀렸으나 후보에 있음(클릭 한 번, 허용) / 후보 어디에도 없음(직접 찾아야 함, 문제). 목표는 앞의 두 가지 합쳐 95% 이상. 측정할 실패 유형 5종 중 1순위는 판정 필요 여부 오판(양방향). 한국어 특수 사항(목표 생략·자유 어순·반말/줄임말·오타)을 별도로 다룬다. 정답 데이터는 M0 실험의 부산물로 확보한다 — 사용자 실험 세션당 약 80개, 2세션 합계 약 160개, 사내 플레이로 약 140개 보충해 300개.
- scope: 파서 검증, 마찰 지표, 정답 데이터 조달, 한국어 특수성

## D29. 라이선스·저작권 정책

- source: docs/GPTRPG-M0-decisions.md §2 D29
- status: locked
- decision: 전부 ① 플랫폼 정책이며 법적 결론이 아니다. 원 기획안의 "우회" 표현을 정정한다 — CC-BY는 우회가 아니라 조건부 허가이고 공식 세계관 고유명사는 애초에 SRD 범위 밖이다. 보호되지 않는 것(게임 메커니즘·판정 구조·수학) vs 보호되는 것(룰북의 문장·고유명사·표의 창작적 배열)이 사업의 기반이며, 리트로클론은 대체로 합법이다(초기 분석의 침해 오해를 정정). 유저 업로드는 공개 범위 3단(비공개 관대 / 친구만 관대 / 공개 마켓 엄격 — 라이선스 선언 + 유사도 검사 + 등록 검수 + 신고 창구). AI 생성물의 권리는 저작권이 아니라 **약관상의 이용권**으로 설계한다. 유저 룰북 수익화는 자작 오리지널에 한해 허용하며 판단 기준은 판정 방식이 아니라 문장과 고유명사의 자작 여부다.
- scope: 라이선스, 저작권, 유저 업로드, AI 생성물 권리, 수익화 허용 범위

## D30. 마일스톤 0 결론 — 가설과 멈출 조건

- source: docs/GPTRPG-M0-decisions.md §2 D30
- status: locked
- decision: 검증할 가설 6개와 멈출 조건 3등급을 정의한다 — 진짜 킬 = H1(재미)·H5(원가), 전략 변경 = H3·H4, 재설계 = H2·H6. **진짜 킬이 두 개뿐이라는 것이 중요하며 M0 실험은 H1과 H5에 우선 집중한다.** 실험 하나로 대부분을 잰다 — 위협 시계 1개 + 룰북 1개 + 캐릭터 4개, 참가자는 TRPG 경험자 2명 + 비경험자 2명, 우리는 GM을 하지 않고 관찰만 한다, 1세션 3~4시간 → 1주 간격 → 2세션 3~4시간. **1주 간격이 실험의 핵심**이며 "두 번째 세션에 왔는가"가 H1의 답이다. 최소 도구 범위를 정해 제품이 아니라 실험 도구를 만든다. 이 실험이 답하지 않는 것(낯선 사람 플레이·장기 캠페인·여러 룰북에서의 재미·동시 접속 규모·저가 모델 서사 품질)을 명시한다. (가설·수용 기준 상세는 `requirements.md` 참조.)
- scope: M0 가설, 킬 크리테리아, 실험 설계, 측정 항목, 최소 도구 범위

## D31. 기억 주입 규칙 — 장면에 있는 것만 넣는다

- source: docs/GPTRPG-M0-decisions.md §2 D31 (중복 출처: docs/superpowers/specs/2026-07-30-m0-closeout-design.md §1)
- status: locked
- decision: 층은 ① 플랫폼 기능. 매 턴 넣는 것은 네 가지로 고정한다 — 현재 장면에 등장한 대상 / 내 캐릭터 상태 / 위협 시계 상태 / 최근 대화 몇 턴(**초기값 10턴, 실측으로 조정**). 나머지 저장소는 이름 + 한 줄 색인만 보이며, AI가 상세를 필요로 하면 요청하고 코드가 꺼내 다음 턴에 넣는다. **금지** — AI가 저장소 전체를 훑는 경로는 만들지 않으며 원 기획안의 ~~"상시 주입"~~은 폐기한다. 안전장치로 턴당 토큰 예산 상한을 두되 저장소 색인·위협 시계 상태·관계 장부는 접지 않는다. 미룸 — 검색 기반 주입은 M0에 넣지 않는다(검색 품질이라는 실패 지점을 추가하면 H1을 측정할 수 없다). 폐기한 대안 — 예산 상한만 두고 오래된 것부터 접는 방식(1세션에 심은 복선이 접힌다).
- scope: 기억 주입, 엔티티 장부, 토큰 예산, 프롬프트 캐싱

## D32. 적과 NPC의 숫자는 룰북이 선언한다

- source: docs/GPTRPG-M0-decisions.md §2 D32 (중복 출처: docs/superpowers/specs/2026-07-30-m0-closeout-design.md §1)
- status: locked
- decision: 층은 ② 표현 어휘 — 그릇은 우리가, 내용은 룰북이. 플랫폼이 정하는 것은 식별자·표시 이름·상태값 묶음(키-값 그릇)·소속 룰북·가시성뿐이고, 룰북 데이터가 상태값 묶음의 항목·각 값의 뜻·바닥났을 때 벌어지는 일을 선언한다. 상태 변경은 효과 표현(D7)을 통해서만 일어난다. 저장은 캐릭터와 같은 그릇을 재사용하고 유형으로만 구분한다. **금지** — 플랫폼 코드에 체력·피해·태그처럼 룰북 고유의 개념을 넣지 않는다(폐기한 룰북별 전용 어댑터와 같은 실수의 다른 얼굴). 대가 — 코드가 "체력"을 모르므로 자동화율이 룰북 작성 품질에 의존한다. 별도의 전투 AI는 필요하지 않다(적의 행동은 닫힌 GM 대응 목록에서 나옴). 좌표계·전술 그리드는 M4 유지. H3 검증에 적 표현도 포함한다.
- scope: 적·NPC 데이터 표현, 상태값 묶음, 전투 AI, H3 검증 범위

## D33. 응답 속도 목표와 초과 시 행동

- source: docs/GPTRPG-M0-decisions.md §2 D33 (중복 출처: docs/superpowers/specs/2026-07-30-m0-closeout-design.md §1)
- status: locked
- decision: 층은 ① 플랫폼 기능. ~~"전체 3초"~~를 폐기한다(완결 기준이었고 달성 불가능 — 무거운 모델의 첫 토큰이 1~2초, 완결이 5~10초). 사람이 기다림을 느끼는 두 지점에 각각 목표를 둔다 — 문장 입력 → 행동 확인 표시 0.5초, 확인 → GM 서사 첫 글자 2초, 완결까지는 목표 없음(스트리밍이므로 체감은 첫 글자에서 결정). 초과 시 행동 — 첫 글자 5초 초과 시 진행 표시, 15초 타임아웃 시 판정 결과(주사위·성공/실패·시계 변화)를 먼저 내보내고 서사를 뒤이어 붙인다. 주사위와 판정은 순수 코드(D14)라 서사보다 먼저 끝나 있어 추가 설계 없이 된다. 목표는 "AI가 느려도 게임이 멈추지 않는다".
- scope: 레이턴시 목표, 타임아웃 동작, 스트리밍
