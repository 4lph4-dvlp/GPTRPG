# Phase 9: 에이전트 구조 재편 - Context

**Gathered:** 2026-08-06
**Status:** Ready for planning

<domain>
## Phase Boundary

**진행자를 「상황 판단」과 「서술」로 쪼개고, 사람이 기다리지 않는 작업을 배경으로 돌리는
자리를 구조로 열고, 어떤 에이전트가 무엇을 받는지를 코드에 명시한다.**

이번 논의에서 사용자가 배경 작업 자리와 병렬 판단 조각의 **실제 내용물**까지 정했다 —
"구조만 만들고 내용은 나중"이 아니라 위협 시계 조건 검사·관계 기록·문맥 압축 세 최소판을
이번 단계에서 실제로 만든다. 그만큼 14·15단계는 이 최소판을 다듬는 작업으로 가벼워진다.

**출발점(사용자와 함께 확인한 사실):** 지금 코드는 판정 한 번에 AI를 **정확히 둘, 순서대로만**
부른다(분류 → 서술, `src/gptrpg/agents/config.py:26`의 `AGENT_ROLES = ("action_classifier",
"master_gm")`). "동시에 여러 참조를 수집하는 자리"도 "사람을 안 기다리게 하는 배경 작업"도
지금 코드엔 **하나도 없다.** 7단계(D-64)가 연 것은 구조상의 자리일 뿐, 실제로 그 자리를
채우는 것은 이 단계가 처음이다.

**범위 밖 (명시):**

- 서술이 걸러야 할 지시문 유출·탈옥 방어 자체 → Phase 10 (이 단계는 "서술이 지시문을
  안 받는다"는 구조까지만 만든다. 받은 것 안에서 새는지 검증하는 필터는 Phase 10)
- 위협 시계 진행 규칙 ②③의 **완성형**(CLOCK-02의 "AI 제안 → 사람 확인" 화면, CLOCK-03의
  진행자 수동 조작 화면, CLOCK-04의 "왜 돌았는지" 표시) → Phase 15. 이 단계는 **조건 검사
  로직과 배경 실행 자리**까지만 최소판으로 만든다
- 관계 기록의 **완성형**(MEM-04 요약 추적, MEM-06 한 줄 색인, MEM-07 상세 요청 경로) →
  Phase 14. 이 단계는 사건에 남기는 최소 기록까지만 만든다
- 문맥 압축의 **완성형**(MEM-05 캐시 계측 비교, 요약 품질) → Phase 14. 이 단계는 "오래된
  대화를 접어서 배경에서 처리하는 자리"까지만 만든다
- 캐릭터 상태 변화·소지품(RULE-*) → Phase 11·12
- 캐릭터 만들기(CHAR-*) → Phase 12.1

## Implementation Decisions

### 배경층 — 무엇을 진짜로 넣는가

- **D-01:** 배경 작업 자리에 **최소판 셋을 전부** 만든다 — ① 위협 시계 조건 검사(원래
  Phase 15/CLOCK-01 예정) ② 관계 기록 최소판(원래 Phase 14/MEM-02 일부 예정) ③ 문맥 압축
  최소판(원래 Phase 14/MEM-03 일부 예정). 사용자가 "필요한 모든 것들"로 확정했다 — 하나만
  골라 증명용 더미로 남기는 안은 기각됐다.
  - 이유(사용자 확인): 배경층이 실제로 검증되려면 자리에 "진짜 뭔가"가 있어야 하고,
    이왕 만들 거면 세 후보를 다 만드는 쪽을 선택했다.
  - **PROJECT.md에 이 결정을 D-63(M1 항목을 v1.1로 당김)과 같은 패턴으로 기록해야 한다**
    — 이번에는 v1.1 안에서 Phase 14·15 항목 일부를 Phase 9로 당기는 것이다.
  - — **Reversibility:** costly — Phase 14·15가 이 최소판 위에 얹힌다. 여기서 만드는
    사건 종류·인터페이스가 두 단계의 출발점이 되므로, 나중에 모양을 바꾸면 두 단계 모두
    다시 손대야 한다.

- **D-02:** 세 최소판 각각이 새 사건 종류를 필요로 하면(위협 시계는 기존 `ClockAdvanced`
  재사용 가능 — 아래 code_context 참조, 관계 기록·문맥 압축은 새 사건 종류 필요) 그때마다
  `EVENT_SCHEMA_VERSION`을 올리고 `rules_core/reducer.py`의 분기를 **같은 커밋에** 반드시
  동반한다 — Phase 8 D-06/ROADMAP이 반복 경고한 사고(빠뜨리면 세션이 영구히 안 열림)를
  그대로 피한다.

### 병렬 참조 수집 — 실제 후보 셋

- **D-03:** 판정 하나가 끝난 뒤 **세 조각을 병렬로 판단**한다 — (a) 이 결과가 장면에 새
  대상(인물·사물)을 등장시키는가 (b) 이 결과가 위협 시계에 영향을 주는가 (c) 이 결과가
  관계에 영향을 주는가. 세 조각은 서로의 출력을 쓰지 않으므로 동시에 돌 수 있다(ARCH-04
  — 의존 관계가 코드에 정적으로 박히고, 셋을 병렬로 돌릴지는 런타임 판단이 아니다).
  - "예전 구상(서브에이전트 여럿이 각자 판단해 진행자에게 넘긴다)이 판단 쪽으로 되살아난다"는
    PROJECT.md D-64 해설이 정확히 이 셋으로 구체화됐다.

- **D-04:** (a)는 **서술이 그 인물/사물을 언급해야 하므로 턴 안에서 끝나야 한다** — 서술
  호출 전에 결과를 받아 반영한다. (b)(c)는 서술이 끝난 뒤에도 반영될 수 있다 — 배경 작업
  (D-01)으로 이어져 이번 턴 서사에는 굳이 안 나와도 되고, 다음 턴부터 보이면 된다.
  - **정직하게 남는 미결정 (계획 단계에서 풀 것):** (b)(c)가 "턴 안 병렬 판단 → 배경
    작업이 그 판단을 이어받아 처리"라는 2단 구조인지, 배경 작업 자체가 판단부터 반영까지
    통째로 맡아서 (b)(c)의 병렬 조각은 그 배경 작업을 "이번 턴엔 확인할 필요가 있는가"만
    빠르게 거르는 문지기 역할인지는 사용자가 특정하지 않았다 — 리서치/계획이 정한다.

- **D-05:** 병렬 참조 수집 중 하나가 타임아웃되면 **플레이어 화면엔 티를 내지 않는다** —
  운영자 로그에만 남긴다(ARCH-05). "없으면 없는 대로 진행"이 조용한 정상 경로다.
  - 참고: `agents/invoke.py`의 `call_with_one_retry`가 이미 "두 시도 다 실패하면 stderr에
    한 줄 찍고 실패 껍데기를 돌려준다"는 같은 패턴을 갖고 있다 — 새 규칙이 아니라 기존
    규칙의 확장이다.

### 상황판단 → 서술 핸드오프

- **D-06:** 서술 담당에게 넘기는 것이 **판정 결과 한 줄**(`check_summary`,
  `cli/turn_flow.py:289`)에서 **위 세 조각의 판단 결과까지 포함하도록 넓어진다.** 단,
  **서술 담당은 여전히 진행자 지시문·규칙·시나리오 원문 자체를 받지 않는다**(ARCH-02,
  잠금 요구사항) — 넘기는 것은 "이미 상황판단이 정한 사실"뿐이지, 그 사실을 정하는 데 쓴
  지시문·규칙 원문이 아니다.
  - 지금 `master_gm.narrate()`는 `check_summary: str` 딱 한 문자열만 받는다
    (`agents/master_gm.py:142-149`) — 이 시그니처가 구조화된 "사실 묶음"을 받도록 넓어져야
    한다는 것이 이번 논의의 핵심 산출물이다.

### Claude's Discretion

사용자가 명시적으로 위임하지 않았으나 요구사항·기존 구조가 이미 답을 정해 두어 계획
단계에서 Claude가 판단할 것들:

- **병렬 판단 조각의 실제 호출 모양** — (a)(b)(c) 셋을 각자 독립된 작은 LLM 호출 셋으로
  쪼갤지, 한 번의 호출에서 JSON 세 칸으로 한꺼번에 받아올지는 비용·지연 트레이드오프
  문제다(D18 — M0은 원가보다 품질 상한선이 우선이지만, D-64 공통 전제가 "사람이 실제로
  기다리는 시간"을 판단 기준으로 남겨 뒀다). 프롬프트 캐싱 구조(`prompt_assembly.py`의
  "영구 고정 → 세션 고정 → 턴마다 변함" 순서, 캐싱 유무가 원가 3.7배 차이)를 셋으로
  쪼갤 때도 유지할 방법을 리서치가 확인해야 한다.
- **위협 시계 최소판이 CLOCK-02(AI 제안 → 사람 확인 화면)의 확인 게이트를 이번 단계에서
  만들지, 배경에서 자동 반영으로 갈지.** 단 D14(AI가 판정·수치에 안 닿는다)는 넘을 수
  없다 — 시계 칸 이동은 결국 코드가 확정한다. 자동 반영으로 가더라도 "AI가 서사 안에서
  스스로 시계 진행을 선언하는 경로는 계속 막혀 있다"(ROADMAP Phase 15 주석)는 지켜야 한다.
- **관계 기록 최소판의 저장 형태** — 자유 텍스트냐 구조화 필드냐는 계획 단계 판단.
  Phase 14가 이 위에 요약 추적(MEM-04)·한 줄 색인(MEM-06)을 얹으므로, 나중에 검색·요약이
  가능한 모양으로 짜는 것이 유리하다는 것만 힌트로 남긴다.
- **문맥 압축 최소판이 실제로 무엇을 압축하는가** — 지금 `TurnContext.recent_turns`는
  10턴 고정 자르기(`agents/context.py:14-15,60-62`, `TooMuchContext`)다. 이번 단계의
  최소판이 "11턴째부터 요약으로 접는다"까지 가는지, 아니면 "접을 자리와 사건 기록 형식만
  만들고 실제 요약 로직은 Phase 14"로 남기는지는 리서치 단계에서 비용 대비 판단.
- **`AGENT_ROLES` 확장 방식** — 지금 `("action_classifier", "master_gm")` 둘뿐인
  `agents/config.py:26`이 새 역할 이름들(상황판단 조각들 포함)로 늘어나야 한다. 역할
  이름·모델 선택 UX(`gptrpg agents select`)를 몇 개까지 늘릴지는 계획 단계 판단.
- 함수·모듈 이름, HTTP 응답 모양(웹 경로 `web/routes_actions.py`가 CLI `turn_flow.py`와
  같은 흐름을 그대로 미러링하고 있으므로 — 아래 code_context 참조 — 두 곳 다 고쳐야 한다는
  것만 못박는다).

## Specific Ideas

- **"필요한 모든 것들"** — 배경 작업 후보를 하나만 고르라는 질문에 사용자가 준 답. 최소판
  셋(시계·관계·압축)을 전부 만드는 것으로 확정됐다. 계획 단계에서 "너무 크면 쪼개서 갈지"
  판단할 때 이 답이 "일부만 하고 나머지 미루기"가 아니라 "셋 다 최소판으로"라는 것을
  다시 확인할 것.
- **병렬 판단 조각 셋 — 장면 신규 대상 / 위협 시계 영향 / 관계 영향** — 사용자가 멀티
  셀렉트로 직접 고른 정확한 세 문장이다. 이름을 새로 지을 때도 이 세 개념을 그대로
  유지할 것 (예: 넷째 조각을 추가로 만들지 않는다 — 사용자가 고른 것은 정확히 셋이었다).
- **타임아웃 시 조용히 넘어가되 운영자 로그에는 남긴다** — "플레이어 화면엔 안 보이지만
  운영자는 알아야 한다"는 이미 `invoke.py`의 기존 stderr 관례와 정확히 같은 모양이다.
  새 규칙을 발명하지 말고 그 관례를 그대로 재사용할 것.
