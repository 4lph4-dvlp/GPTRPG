# Phase 1: 규칙 코어와 사건 기록 - Context

**Gathered:** 2026-07-31
**Status:** Ready for planning

<domain>
## Phase Boundary

게임에서 일어난 모든 일이 순서대로 쌓이는 사건 기록과, 그 기록을 처음부터 훑으면 현재 상태가 똑같이 재구성되는 구조. 주사위와 판정은 AI가 끼어들 지점이 구조적으로 없는 순수 코드로만 일어난다.

**이 단계가 만드는 것:** 규칙 코어 + 사건 기록 + 진행 담당(세션 액터) 세 층 — 가져다 쓰는 Python 라이브러리와, 그것을 실제로 불러 쓰는 명령줄 재생 도구.

**이 단계가 만들지 않는 것:** 화면, HTTP 서버, WebSocket, AI 호출 코드, 룰북을 파일에서 읽어 들이는 기능, 두 번째 판정 방식, 진행 정책 설정값(턴 타이머·순서 강제).

**이 단계의 유일한 숙제(로드맵 원문):** 기록에 필드를 빠뜨리지 않는 것. 빠뜨린 필드는 Phase 6에 가서야 드러나고, 그때는 이미 끝난 두 세션을 다시 할 수 없다.

</domain>

<decisions>
## Implementation Decisions

### 코어의 경계와 결과물

- **D-01:** Phase 1의 결과물은 **Python 라이브러리 + 명령줄 재생 도구**다. 재생 도구는 기록 파일을 받아 처음부터 훑어 현재 상태를 만들어 보여준다. 화면과 서버는 만들지 않는다.
  - *이유:* 성공 조건 1번이 실물로 증명되고, 명령줄이 첫 손님이 되면서 "웹 전용으로 짜이지 않았다"가 말이 아니라 코드로 증명된다. 웹 서버를 여기서 올리면 "요청이 들어왔으니 현재 시각을" 같은 것이 규칙 코어까지 새어 들어가 성공 조건 4번을 깨뜨릴 위험이 있다.

- **D-02:** 실행 언어는 **Python으로 확정**한다. `.planning/PROJECT.md`의 열린 결정 표에 「보류」로 남아 있던 항목을 여기서 닫는다. **브라우저 안에서 규칙 코어가 도는 시나리오는 포기한다.**
  — **Reversibility:** costly — 언어를 바꾸면 규칙 코어·사건 기록·진행 담당 전량 재작성이다. 다만 M0 규모에서는 재작성 대상이 작다.
  - *이유:* 가장 무거운 일이 Phase 3의 AI 진행자이고 그쪽 도구가 Python에 가장 잘 깔려 있다. 규칙 코어가 AI를 부르는 층과 같은 프로세스에 있으면 연결 비용이 없다. 브라우저 실행은 로드맵 M1~M4 어디에도 요구가 없다(솔로 모드·비동기 플레이도 서버에서 돈다).
  - *중요한 분별:* "어떤 클라이언트에서든 쓸 수 있다"는 성질은 **언어가 아니라 경계에서** 나온다. 명령줄과 웹이 둘 다 붙을 수 있으면 목적은 달성된다.

- **D-03:** 판정 방식 **하나(2d6 등급식)를 실제로 코드에 넣어 끝까지 돌린다.** 두 번째 방식(d100 롤언더)은 Phase 2다.
  - *이유:* 성공 조건 2번·3번이 판정이 실제로 한 번은 돌아야 증명된다. 그리고 Phase 2가 "여기에 두 번째를 넣어봤더니 플랫폼 코드를 고쳐야 했나"를 재는 진짜 시험장이 되려면 첫 번째가 실물로 있어야 한다.

- **D-04:** 규칙 코어의 경계는 **자동 검사로 강제한다.** 규칙 코어 폴더 안에서 시각·무작위·파일·네트워크 관련 기능을 직접 가져다 쓰면 테스트가 실패한다.
  - *이유:* 성공 조건 4번은 한 번 지켰다고 계속 지켜지지 않는다. 나중에 누가 "잠깐만 시각 하나만" 하고 넣으면 조용히 무너진다. 첫 판을 깔 때 넣으면 거의 공짜다.
  - *주의:* 주사위의 무작위도 여기 포함된다. 규칙 코어가 무작위를 직접 뽑으면 같은 굴림을 재생할 수 없다. → D-11 참조.

- **D-05:** 진행 담당(세션 액터) 층은 **명령 수신 → 검증 → 규칙 코어 호출 → 기록에 쓰기까지 실제로 동작**하게 만든다. 진행 정책 설정값(턴 타이머·순서 강제·리액션 윈도우)은 Phase 4다.
  - *이유:* 성공 조건 5번(쓰기 주체가 하나뿐)은 이 층이 없으면 증명할 대상 자체가 없다. 명령줄 재생 도구도 이 층을 불러서 돈다.

- **D-06:** 세 층을 **한 Python 패키지 안의 세 폴더**(규칙 코어 / 사건 기록 / 진행 담당)로 나누고, 서로 못 가져다 쓰게 자동 import 검사로 막는다. 별도 배포 패키지로 쪼개지 않는다.
  - *이유:* 경계 보장은 따로 쪼개는 것과 똑같으면서 버전 맞추기·배포 수고가 없다. 진짜로 밖에서 가져다 쓸 곳이 생기면(M1 이후) 그때 떼어낸다.

### 기록을 어디에 쌓나

- **D-07:** 사건 기록은 **SQLite 파일 하나**에 쌓는다.
  — **Reversibility:** costly — Postgres로 옮길 때 이미 쌓인 기록의 데이터 이전이 필요하다. 다만 사건 기록은 구조가 단순(순번·종류·내용·판 번호)해서 이전 비용이 낮다.
  - *이유:* 설치할 것이 없고(Python 기본 탑재) 파일 하나로 끝나면서, "순번 N번부터 끝까지 줘" 같은 조회를 제대로 한다. Phase 4의 "끊겼다 다시 붙기"가 여기서 거의 공짜로 나온다. 세션 하나에 사건 수천 개, 두 세션이면 만 개 안팎이라 규모는 문제가 아니다.

- **D-08:** 현재 상태는 **매번 기록을 처음부터 훑어 만들고**, 세션이 도는 동안은 메모리에 유지한다. **중간 저장(스냅샷)을 두지 않는다.**
  — **Reversibility:** reversible — 순수하게 속도 문제이므로 나중에 붙여도 아무것도 깨지지 않는다.
  - *이유:* 진실이 기록 한 군데에만 있는 상태가 유지되고, 성공 조건 1번이 매일 저절로 검증된다. 수천 개 규모에서 체감되는 속도 차이가 없다.

- **D-09:** 쓰기 주체가 하나라는 것을 **두 겹으로** 강제한다 — ① 세션당 진행 담당이 하나만 살아 있고 명령은 큐로 줄을 서서 하나씩 처리 ② 기록에 순번을 붙이고 "내가 본 마지막이 N번"을 같이 써서, 같은 순번에 둘이 쓰려 하면 저장소가 한쪽을 거부.
  — **Reversibility:** costly — 순번은 기록 스키마의 일부라 이미 쌓인 기록에 소급 적용할 수 없다.
  - *이유:* ①만으로는 한 서버 안에서만 보장된다. 나중에 서버를 늘리거나 실수로 같은 세션이 두 번 열리면 조용히 깨진다. SQLite에서 ②는 유일성 제약 한 줄로 끝난다.

### 기록의 생김새

- **D-10:** 사건 **종류별로 필수 항목을 코드에 못박고**, 빠진 채로 쓰려 하면 거부한다. 느슨한 자루 방식을 쓰지 않는다.
  — **Reversibility:** one-way — 기록에 남지 않은 정보는 소급해서 만들어낼 수 없다. Phase 5의 두 세션 기록이 Phase 6 판정의 입력값이고, 그중 재미(H1)와 원가(H5)는 프로젝트를 멈출 수 있는 조건이다.
  - *이유:* 빠뜨린 필드가 Phase 6이 아니라 직접 돌려볼 때 바로 드러난다.

- **D-11 (이 단계에서 가장 값이 큰 결정):** 필드 누락은 **집계를 거꾸로 돌려 검증한다.** MEAS-01~06이 요구하는 숫자 여섯 개의 목록을 지금 만들고, 가짜 세션 기록을 지어 "이 기록만으로 여섯 개가 전부 산출되는가"를 테스트로 확인한다. 하나라도 안 나오면 필드가 빠진 것이다.
  - *이유:* 필드 누락이 실험 이후가 아니라 실험 전에 드러난다. 부수 효과로 Phase 4의 집계 기능이 사실상 절반 완성된다.
  - *산출해야 하는 여섯 가지:* 실제 토큰 소모량 / 실제 턴 수 / 문장 입력→행동 확인 표시 시간 / 확인→서사 첫 글자 시간 / 판정 실패 횟수 대비 위협 시계 진행 횟수 / 플레이어가 실제로 친 문장 + 시스템의 제안 + 플레이어의 확인 여부.

- **D-12:** 사건마다 **판 번호(스키마 버전)를 붙인다.** 이미 쓴 기록은 고치지 않는다(append-only 유지). 모양이 실제로 바뀔 때 읽는 쪽에 "옛 판은 이렇게 읽는다"를 추가한다.
  - *이유:* Phase 5는 1세션과 2세션 사이가 1주다. 그 사이에 코드를 고치면 두 기록의 모양이 달라질 수 있는데 Phase 6은 둘 다 읽어야 한다. 붙이는 비용은 항목 하나이고, 변환 코드는 필요해질 때만 쓴다. 예전 기록을 고쳐 쓰는 방식은 "이미 쓴 건 안 고친다"를 깨서 재구성을 믿을 수 없게 만든다.

- **D-13:** 모든 사건에 **"누가 볼 수 있는지" 항목**을 두되, M0에서는 값이 항상 "전체 공개"다. 귓속말 기능은 만들지 않는다.
  — **Reversibility:** costly — 나중에 추가하려면 판 번호를 올려야 하고, 이미 쌓인 기록에는 값이 없다.
  - *이유:* 자리를 비워두는 비용은 항목 하나다. 설계 문서 §3.7이 이미 모양을 정해뒀고, M4의 시야 계산도 같은 장치를 재사용한다.

- **D-14:** **"AI를 불렀다" 사건 종류를 지금 정의한다** — 어느 역할이, 어느 모델로, 토큰 몇 개를 썼고, 몇 초 걸렸는지. 실제 AI 호출 코드와 제공자 추상화 계층은 Phase 3이다.
  - *이유:* D-11이 산출해야 하는 여섯 숫자 중 둘(실제 토큰 소모량, 두 지점의 응답 속도)이 여기서 나온다. 자리가 없으면 Phase 6에서 원가를 계산할 수 없고, 원가는 프로젝트를 멈출 수 있는 조건이다. 반면 제공자 추상화 코드는 실제로 AI를 부를 때 모양이 정해지므로, Phase 1에서 미리 짜면 쓰이지 않는 껍데기를 상상으로 만들고 Phase 3에서 다시 고치게 된다.

### 주사위 되감기

- **D-15:** 주사위는 **"굴리는 도구"를 규칙 코어에 건네주는 방식**으로 굴린다. 진행할 때는 실제로 굴리는 도구를, 되감을 때는 기록에서 눈을 읽어오는 도구를 건넨다.
  - *이유:* 재생이 별도 코드 없이 된다 — 같은 규칙 코어 코드가 그대로 돌면서 같은 결과가 나온다. Phase 2의 룰북 수정치 네 유형 중 **재굴림**이 있는데, 이 방식이면 코어가 필요할 때 한 번 더 부르면 그만이다. 왕복식은 재굴림마다 왕복이 늘고 되감기용 별도 경로를 짜야 한다.
  - *전제:* 잠금 결정이 정한 암호학적 난수는 원래 재현 불가능하게 설계된 물건이라 "씨앗을 남겨두고 나중에 다시 굴린다"가 원리적으로 안 된다. **굴러 나온 눈을 그대로 기록에 남기는 것이 유일한 되감기 수단이다.**

- **D-16:** 판정 한 번에 **계산 과정을 통째로** 남긴다 — 굴러 나온 눈 하나하나, 붙은 수정치가 무엇이고 어디서 왔는지, 목표값, 최종 등급.
  — **Reversibility:** one-way — 남기지 않은 중간 계산은 소급 복원할 수 없고, 재계산은 코드가 바뀐 뒤에는 다른 답을 낸다.
  - *이유:* Phase 2에서 룰북 두 개를 넣으며 규칙 코어를 손대고, Phase 5는 두 세션 사이가 1주다. 눈만 남기고 나머지를 재계산하면 Phase 6이 읽을 숫자가 조용히 틀어진다. "사람이 검산할 수 있다"는 제품 정체성(투명성)과도 맞는다.

- **D-17:** **판정 한 번 = 사건 하나.** 굴림·수정치·등급이 그 사건 안에 다 들어간다. 재굴림이면 굴림이 목록으로 여러 개 들어간다. (서사는 나중에 붙으므로 별도 사건이다 — 15초 초과 시 판정 결과를 먼저 내보내는 규칙 때문에 어차피 분리된다.)
  - *이유:* "굴렸는데 등급이 안 남은" 반쪽 상태가 생길 수 없고, 집계할 때 판정 사건만 세면 끝난다.

### Claude's Discretion

계획·조사 단계에서 판단하되, 위 결정을 뒤집지 않는 선에서:

- 사건 종류의 최종 목록과 각 종류의 필수 항목 이름 — D-11의 역방향 검증(여섯 숫자가 산출되는가)이 정답 기준이다
- 명령 큐와 세션 액터의 구체적 구현 방식(비동기 태스크 / 스레드 등)
- 자동 경계 검사를 무엇으로 거는지(import 검사 도구 / 테스트 / 정적 분석)
- 명령줄 재생 도구의 출력 형태
- 테스트 도구·패키지 관리자 선택
- 2d6 등급식 판정에 M0 실험용으로 넣을 판정 종류의 최소 집합 — EXP-01이 "판정 종류 10개 남짓"이라고 적었으나 그 준비물은 Phase 5 몫이므로, Phase 1은 구조 검증에 필요한 최소한만

</decisions>

## Specific Ideas

**사용자가 직접 세운 원칙:** "웹이든 CLI든 모든 클라이언트에서 사용할 수 있는 코어를 만드는 게 중요하다."

이 원칙이 D-01(명령줄 도구를 첫 손님으로)과 D-06(경계를 자동 검사로 강제)의 직접적인 근거다. 아래 단계들에서도 이 기준을 유지할 것.

**논의 중 정리된 용어 구분** — 이후 문서와 대화에서 이 구분을 지킬 것:

| 말 | 뜻 |
|---|---|
| **백엔드** | 위치 개념. 서버에서 도는 것 전부 |
| **코어** | 역할 개념. 그중 게임의 진실을 다루는 부분. 백엔드가 코어를 품는 관계지 같은 말이 아니다 |
| **규칙 코어** | 코어 중에서도 주사위와 판정만. AI 없음, 입출력 없음, 시각 없음 |
| **매개체 / 전송 어댑터** | 코어의 입력과 출력을 사용자에게 나르는 층. 웹이든 명령줄이든 여기만 갈아끼운다 |

**사용자가 처음에 코어에 포함시켜 생각했으나 잠금된 설계가 분리한 것:** "룰북 파일을 읽어 변환하는 일"(Phase 2)과 "AI를 돌려 게임을 진행하는 일"(Phase 3)은 규칙 코어가 아니다. 특히 **AI는 규칙 코어 바깥에 있어야** 성공 조건 2번("판정 결과가 나오기까지 AI가 끼어드는 지점이 코드 어디에도 없다")이 말이 아니라 코드 구조로 증명된다.
