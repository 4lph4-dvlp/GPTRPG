# Phase 12.2: Code Review Report

**Reviewed:** 2026-08-20T00:00:00Z
**Depth:** standard
**Files Reviewed:** 25
**Status:** issues_found

## Summary

The server-side calculation pipeline (`rules_core/check_calculation.py` →
`web/check_views.py` → `routes_events.py`/`routes_actions.py`) is well
structured and consistent: `total`/`rulebook_id` are correctly threaded from
`ResolveCheck` through the event, both response builders derive
`rulebook_id` from the loaded character (not from client-supplied fields, per
the mid-phase fix), the schema-v10 validator mirrors the existing v5 pattern
correctly, and `_BUILDERS`/`_RESOLVERS` key parity is enforced by a dedicated
test. The frontend's single arithmetic-free `buildCheckSummary` is correctly
consumed identically by `TurnCard`, `CheckBreakdown`, and `DiceModal`, and the
`rollRoles`/`rollDiscarded` index alignment with `check.rolls` is correct and
well tested for both 2d6 and d100 paths, including reroll/bonus-dice cases
that aren't reachable yet in production.

Two robustness/UX gaps are worth fixing before they surface in production:
an unguarded exception path that could brick a session's polling endpoint
once reroll/bonus-dice features land, and a same-gesture race in
`DiceModal` between the reveal-only `pointerdown` listener and the confirm
button that appears at the same screen location. Two minor code-quality
nits round out the list.

## Warnings

### WR-01: `calculation_view_for` failures are unguarded and would brick a session's polling forever

**File:** `src/gptrpg/web/check_views.py:41-66`, `src/gptrpg/web/routes_events.py:100-106`

**Issue:** `calculation_view_for` deliberately lets `UnknownResolutionMethod`
and `MalformedRollRecord` propagate (its docstring says so: "그 밖의 실패는
예외를 그대로 올린다" — everything except `UnknownRulebook`/`total is None`
is a builder bug and should fail loudly). `routes_events.py::poll_events`
calls it inside an unguarded list comprehension over every `check_resolved`
event in the batch:

```python
check_calculations = [
    view
    for event in events
    if event.event_type == "check_resolved"
    and (view := calculation_view_for(event)) is not None
]
```

There is no per-event try/except, so one malformed record turns the *entire*
`/events` response into a 500 — not just the offending calculation. Because
a full page reload always polls from `from_seq=0` (D-41) and `poll_events`
recomputes calculations for the *whole* history on every such request, one
bad `check_resolved` event anywhere in a session's history would make every
future fresh page load (and every subsequent poll once the client catches
up to that seq) fail forever for every browser in that session — a
permanent, session-wide outage from a single row, with no way to recover
short of manually editing the event store.

This is not reachable *today*: `_BUILDERS`/`_RESOLVERS` key parity is
enforced by `test_every_resolver_has_a_segment_builder`, and no live code
path currently produces `BONUS_DICE` modifiers or multi-row rerolls (per
`tests/test_check_calculation.py`'s own docstring — those paths are only
exercised in tests). But that is exactly the gap the follow-up phase
(12.2-03 notes reroll/bonus-dice as not-yet-wired) is expected to close, and
`routes_actions.py::confirm()` has the identical unguarded call
(`calculation_view_for(check_event)` at lines ~1134/1194) — there the blast
radius is only the one request, but it's the same missing safety net.

**Fix:** Catch `UnknownResolutionMethod`/`MalformedRollRecord` per event in
`poll_events` (and log server-side) rather than letting a single bad record
fail the whole batch — e.g.:

```python
check_calculations: list[CheckCalculationView] = []
for event in events:
    if event.event_type != "check_resolved":
        continue
    try:
        view = calculation_view_for(event)
    except (UnknownResolutionMethod, MalformedRollRecord) as exc:
        print(f"경고: 계산 줄을 만들지 못했다 (seq {event.seq}) — {exc}", file=sys.stderr)
        continue
    if view is not None:
        check_calculations.append(view)
```

### WR-02: `DiceModal`'s reveal-via-click and confirm button can land on the same physical click

**File:** `frontend/src/components/DiceModal.tsx:113-126, 172-180, 274-283`

**Issue:** Before the result is revealed, a window-level `pointerdown`
listener calls `reveal()`, which synchronously calls `setShowStamp(true)`
(among other state updates). Once `showStamp` becomes true, the confirm
button renders — centered in the fixed, screen-centered `.dice-modal`
(`justify-content: center; align-items: center`), i.e. at (or very near) the
same screen coordinates a player's pointerdown-to-reveal click typically
lands, since players tend to click the modal itself to skip the animation.

If React commits the `showStamp` state update before the browser dispatches
the trailing `click` event for that same mousedown/mouseup pair, the click
lands on the just-rendered confirm button (`pointer-events: auto`,
`onClick={beginLeaving}`), and the modal closes in the same gesture that was
only meant to reveal it — defeating the explicit design goal stated in the
file's own comment block ("클릭은 「드러내기」에만 쓴다 — 닫기에는 안
쓴다... 결과를 읽는 동안 다음 행동을 치려고 입력칸을 누른 사람의 창이 그
순간 닫혀, 저절로 사라지던 예전 문제가 그대로 돌아온다"). Whether this
reproduces depends on React/browser event-loop timing (state commits from a
non-React `addEventListener` handler aren't guaranteed to land before the
next native event in the same gesture), but the hazard is structural: the
button is deliberately placed where the reveal click is expected to land.

**Fix:** Add a short guard so the confirm button doesn't accept clicks in
the same tick/gesture that triggered `reveal()` — e.g. gate the button's
`onClick` (or the button's mount) behind a `requestAnimationFrame`/short
`setTimeout(0)` after `reveal()` runs, or ignore the `click` that
immediately follows the `pointerdown` that caused the reveal
(`event.detail`/timestamp comparison), so a single physical click can only
ever do one of "reveal" or "dismiss."

## Info

### IN-01: Unused `beginLeaving` dependency in `DiceModal`'s animation effect

**File:** `frontend/src/components/DiceModal.tsx:137-160`

**Issue:** The main tumble/land/reveal `useEffect`'s dependency array is
`[after, beginLeaving, clearTimers, diceCount]`, but `beginLeaving` is never
referenced inside the effect body. It's dead weight — likely left over from
a refactor — that makes the dependency list misleading about what the effect
actually reads.

**Fix:** Drop `beginLeaving` from the dependency array (or, if a future
change intends to schedule an auto-leave from within this effect, add the
actual reference back alongside it).

### IN-02: `Die.tsx`'s gradient id collides across simultaneous same-size dice

**File:** `frontend/src/components/Die.tsx:88-93`

**Issue:** `<linearGradient id={`die-face-${size}`}>` is keyed only by
`size`, not by instance. Every die rendered in the same `DiceModal` (or
`TurnCard`/`CheckBreakdown` if they ever grew SVG dice) shares `size={56}`,
so all of them emit the same DOM id — invalid HTML/SVG (duplicate ids).
Today this is harmless because every gradient definition is byte-identical
(browsers resolve `url(#id)` to the first match), so there's no visible
defect, but it's technically invalid markup and would silently misrender if
a future variant ever needed a per-instance gradient.

**Fix:** Use a stable per-instance key (e.g. `useId()` from React) instead
of `size` for the gradient id.
