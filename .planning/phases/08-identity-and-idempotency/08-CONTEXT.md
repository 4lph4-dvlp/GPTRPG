## Phase Boundary

**서버가 「누가 · 어떤 캐릭터로 · 무엇을 선언·확인했는지」를 위조 불가능하게 확인하고,
같은 선언에 대한 재시도가 두 번 처리되지 않게 한다.**

새 게임 기능은 하나도 만들지 않는다. 이 단계가 손대는 것은 신원·점유·재시도라는 세 가지
경계 규칙과, 그 규칙을 검증할 수 있는 테스트 픽스처다.

**범위 밖 (명시):**

- AI 출력 검증·탈옥 방어 → Phase 10 (서사 자동 재생성 포함)
- 캐릭터 시트 쓰기 경로·자원 변화 → Phase 11·12
- 세션1 기록을 실제로 재생해 같은 상태가 나오는지 확인 → Phase 12 (TEST-04).
  이번 단계는 **그때 읽을 수 있도록 길만 열어 둔다**
- 화면 배치·안내 문구 디자인·캐릭터 선택 화면의 실시간 갱신 → Phase 16 (FE-03)
- 캐릭터 만들기 → **어느 단계에도 배정되어 있지 않다.** 아래 `<deferred>` 참조

<decisions>
## Implementation Decisions

### 신원 증명 — 어떻게 위조 불가능하게 만드나

- **D-01:** **서명한 쿠키(HMAC)로 간다.** 서버가 비밀 열쇠 하나로 `gptrpg_character`
  쿠키에 서명하고, 한 글자라도 변조되면 검증에서 떨어진다. 서버는 상태를 들지 않는다.
  - 지금은 서명 없는 평문 JSON이다 (`src/gptrpg/web/routes_characters.py:156-163`).
  - 탈락한 대안: 서버측 세션 저장소 + 불투명 토큰. 특정 사용자를 즉시 무효화할 수 있다는
    이점이 있으나, 서버 재시작 시 전원이 캐릭터를 다시 골라야 하는 대가가 크다.
  - **알려진 한계 (정직하게 기록):** 서명 쿠키는 개별 무효화가 즉시 되지 않는다.
    이 마일스톤에서 필요하지 않다고 판단했다. M1의 실제 계정 체계에서 재검토한다.
  - — **Reversibility:** reversible — 쿠키 형식과 검증 함수는 `routes_characters.py`와
    새 검증 의존성 한 곳에 갇힌다. 저장된 데이터를 마이그레이션하지 않는다.

- **D-02:** **비밀 열쇠가 없으면 서버가 만들어 파일에 저장하고 다음 실행부터 재사용한다.**
  준비 없이 그냥 켜도 돌고, 세션 중간에 서버를 껐다 켜도 아무도 쫓겨나지 않는다.
  **열쇠를 밖에서 주입하는 경로(환경변수 등)도 함께 연다** — 나중에 실제 서비스로 갈 때
  필요하다. 밖에서 준 열쇠가 있으면 그것이 우선이다.
  - 근거: `docs/session1-code-review.md`가 세션1 중 서버 재시작이 여러 번 필요했음을 기록.
  - 열쇠 파일은 반드시 `.gitignore`에 들어간다.

- **D-03:** **쪽지에 「브라우저 식별자」와 「고른 캐릭터」를 따로 적는다 — 사람과 캐릭터를
  분리한다.** 지금 코드는 `player_id === character_id`로 둘을 같은 값으로 쓰고 있다
  (`frontend/src/screens/SessionScreen.tsx:113`, D-42).
  - **지금은 여전히 한 사람이 한 캐릭터다.** 여러 캐릭터를 조종하는 기능을 만들지 않는다.
    바뀌는 것은 **그릇의 모양뿐**이다.
  - 이유: 친구 초대 링크·계정(M1), 솔로 모드(M2)가 들어올 때 사건 기록 형식을 다시 안
    고쳐도 된다. 지금 넣으면 공짜고 나중에 넣으면 기록을 다시 떠들어야 한다.
  - — **Reversibility:** one-way — 사건 기록에 남는 칸이다. 나중에 되돌리려면 이미 쓰인
    기록의 마이그레이션이 필요하고, 이 프로젝트는 「이미 쓴 기록은 손대지 않는다」(D-12)를
    규약으로 삼는다.

- **D-04:** **거부는 서버 기록(로그)에만 남긴다.** 게임 사건 기록은 「게임에서 실제로
  일어난 일」만 담는다. 화면에는 안내를 띄운다.
  - 기존 관례와 같은 방향이다 (`src/gptrpg/web/routes_actions.py:281-285` — "요청 형식에
    대한 판단은 실패해도 사건을 남기지 않아야 한다. 그렇지 않으면 판정 없는 「확인됨」
    사건이 기록에 영구히 남아 무결성이 깨진다").
  - QUAL-05에 따라 안내 문구·로그 어느 쪽에도 쿠키 값·비밀 열쇠·서명이 실려 나가지 않는다.

### 캐릭터 점유 — 같은 캐릭터를 둘이 고르면

- **D-05:** **먼저 잡은 사람이 임자다.** 이미 잡힌 캐릭터를 다른 브라우저가 고르려 하면
  거부하고, 그 사람은 다른 캐릭터를 고른다. **본인 재접속은 서명 쿠키로 확인되므로 그대로
  통과한다** — 자기 캐릭터에 다시 들어오는 것은 점유 충돌이 아니다.
  - 이유: 점유 규칙이 없으면 신원 검증을 통과해도 서버 입장에서 브람이 넷이라 서사가
    여전히 뒤엉킨다 — 세션1 사고와 같은 결과가 원인만 바꿔 재발한다.

- **D-06:** **점유를 게임 사건으로 기록한다.** 서버를 껐다 켜도 기록을 다시 읽으면 점유가
  복원된다. 「상태는 사건에서 접어 만든다」는 이 프로젝트의 되돌릴 수 없는 구조와 같은
  방식이다 (D3).
  - 새 사건 종류가 하나 늘어난다 → `EVENT_SCHEMA_VERSION`을 올린다 (D-09와 같은 커밋에서).
  - **`reducer.py`의 분기를 같은 커밋에 반드시 동반한다.** 빠뜨리면 세션이 영구히 안 열리는
    사고가 재발한다 (ROADMAP Phase 12 주석이 기록한 위험).
  - — **Reversibility:** one-way — 새 사건 종류이자 기록 형식 번호 상승.

- **D-07:** **한 번 잡으면 놓을 수 없다.** 놓기 경로를 만들지 않는다.
  - **사용자가 대가를 알고 선택했다:** 실수로 잘못 고르면 그 세션 동안 바꿀 수 없고,
    유일한 탈출구는 새 세션 링크를 여는 것이다. 세션 하나가 3~4시간이므로 실제로 아플 수
    있다는 점을 제시한 뒤 내린 결정이다.
  - 얻는 것: 위조 구멍이 원천적으로 없다. 「놓기」가 없으면 놓기를 가장한 공격도 없다.

### 서사 실패와 재시도 — 멱등성

- **D-08:** **주사위 결과를 먼저 보여주고, 그 아래 「이야기를 못 썼다」 안내를 붙인다.**
  이미 일어난 일을 버리지 않는다.
  - 지금은 `routes_actions.py:439-446`이 502를 던져 이미 기록된 판정 결과를 통째로
    버린다. 그래서 플레이어가 다시 누르면 주사위가 또 굴러간다 — 이것이 세션1에서
    재시도가 문제가 된 정체다.
  - **이미 확정된 응답 속도 규칙과 같은 방향이다** (D33 — "15초 초과 시 판정 결과를 먼저
    내보내고 서사를 뒤이어 붙인다"). 실패는 「무한히 늦은 응답」의 극단이다.
  - 응답에서 **「주사위 굴림 실패」와 「서사 생성 실패」가 구분되어야 한다** (TRUST-06).

- **D-09:** **다시 시도를 누르면 이야기만 다시 쓴다.** 주사위는 이미 굴렀으니 그대로 두고
  AI에게 서사만 다시 부탁한다. 성공하면 그 턴이 정상적으로 완성된다.
  - **AI가 자동으로 한 번 더 써 보는 것(SAFE-04)은 Phase 10의 몫이다.** 이 단계가 정하는
    것은 **사람이 다시 눌렀을 때**의 동작뿐이다.

- **D-10:** **멱등성 열쇠 = 요청에 이미 들어 있는 선언 번호(`declare_seq`).** 서버는 사건
  기록에서 「이 선언은 이미 확인됐다」를 확인한다. 브라우저가 새로 만들어 보내는 요청
  번호를 도입하지 않는다.
  - 이유: 화면 코드를 전혀 안 고쳐도 되고, 브라우저가 열쇠를 틀릴 구석이 없다.
    `ConfirmRequest.declare_seq`가 이미 필드로 있다 (`routes_actions.py:246`).
  - 이미 확인된 선언에 대해 **다른 무브·능력치로** 들어온 확인도 거부 대상이다 —
    "마음이 바뀌었다"가 주사위를 다시 굴리는 경로가 되면 안 된다.

- **D-11:** **신원·점유·멱등성 검사는 라우트 계층과 `SessionActor` 양쪽에 둔다.**
  라우트 검사만으로는 우회 경로가 남는다 (TRUST-03이 명시). 세션당 단일 쓰기 주체
  안에서의 검사가 최종 방어선이다.
  - `SessionActor._validate_caused_by`(`actor.py:366-376`)는 지금 「그 순번이 존재하는가」만
    본다. 「그 선언의 주인이 지금 확인하는 사람과 같은가」와 「이미 확인됐는가」가 여기에
    붙는다.

### 기록 형식과 옛 기록

- **D-12:** **판정 기록(`CheckResolved`)에 「사람」과 「캐릭터」를 둘 다 필수 칸으로
  넣는다.** 「이 브라우저가 · 브람으로 · 굴렸다」가 다 남는다.
  - D-03(사람·캐릭터 분리)이 기록에서도 살아난다. 나중에 한 사람이 캐릭터 둘을 움직여도
    기록 형식을 다시 안 고쳐도 된다.
  - — **Reversibility:** one-way — 필수 칸 추가는 기록 형식 번호 상승을 강제한다.

- **D-13:** **옛 형식(번호 2)으로 쓰인 기록을 읽는 경로를 낸다.** 새 기록에는 사람·캐릭터
  칸을 반드시 받고, 옛 기록은 「그 시절에는 안 적었다」로 해석해 읽어낸다.
  - **`.gptrpg/events.db`에 세션1 기록 895건이 실제로 살아 있다** — 판정 38건 · 선언 47건 ·
    확인 39건 · 서사 682조각 · 시계 4건 · AI 호출 85건. 전부 형식 번호 2다.
  - 전례를 그대로 따른다: 형식 1→2 때 `counts_as_failure`를 필수 칸으로 올리면서
    `rules_core/reducer.py:98-99`에 옛 판 해석 경로를 냈다.
  - Phase 12의 TEST-04(세션1 기록 재생 회귀 픽스처)가 이 경로 위에서 돈다.

- **D-14:** **점유 기록이 없는 옛 세션은 다시보기만 되고 새 행동은 못 보낸다.** 옛 기록과
  새 규칙이 섞이지 않는다.
  - ⚠️ **구현 시 반드시 구분할 것:** 「사건이 아예 없는 세션」(= 새 세션, 정상적으로
    캐릭터를 잡을 수 있어야 한다)과 「사건은 있는데 점유 사건만 없는 세션」(= 옛 세션,
    다시보기 전용). 이 둘을 같게 다루면 **아무도 새 세션을 시작하지 못한다.**

### Claude's Discretion

사용자가 명시적으로 위임하지 않았으나, 요구사항이 이미 답을 정해 두어 논의 대상이
아니었던 것들 — 계획 단계에서 Claude가 판단한다:

- **QUAL-04 (입력 길이 상한):** `routes_actions.py`에는 이미 상한이 있다
  (`MAX_RAW_TEXT_LEN=2000`, `MAX_ID_LEN=64`). **`routes_characters.py`의
  `SelectCharacterRequest.character_id`에는 상한이 없다** — API 경계 전수 훑기 대상.
- **QUAL-05 (예외 관례):** 예외 문구에 쿠키 값·비밀 열쇠·서명·API 키가 실려 나가지 않는다.
- **TEST-01 (테스트 픽스처):** `"p1"` 상수가 **13개 파일 44군데**에 있다. 실제 캐릭터
  여러 명으로 도는 픽스처로 바꾸고, 각자의 발화에 각자의 이름이 붙는지 단언한다.
  전면 교체할지 공유 픽스처를 하나 만들고 점진 교체할지는 계획 단계 판단.
- **TEST-02 (겹치는 요청):** 같은 선언에 대한 확인이 동시에 두 번 들어오는 상황,
  두 브라우저가 같은 캐릭터를 동시에 고르는 상황을 재현한다.
- HTTP 상태 코드 선택, 함수·모듈 이름, 서명 알고리즘 세부.

### Established Patterns

  점유도 이 규칙을 따른다 (D-06).

- **요청 형식 검증 실패는 사건을 남기지 않는다** (`routes_actions.py:281-285`).
  D-04가 이 관례 위에 앉는다.
- **판정이 서사보다 먼저 기록되는 것은 조건 분기가 아니라 코드 순서다**

- **주사위·판정 계산에 AI가 끼어드는 지점을 만들지 않는다** (D14). 이 단계는 AI를 새로
  부르지 않는다.

## Specific Ideas

- **「도장 찍은 쪽지」** — 사용자가 고른 비유. 서버 비밀 열쇠로 서명한 쿠키를 뜻한다.
  용어를 문서에 남길 때 이 표현을 쓰면 사용자와의 소통이 끊기지 않는다.
- **재시도의 정체를 사용자가 순서로 이해했다** — ① 확인 누름 → ② 주사위 굴러가고 기록됨
  → ③ 이야기 실패 → ④ "다시 시도해 주세요"만 돌아옴 → ⑤ 다시 누르면 ②부터 반복.
  계획서와 커밋 메시지가 이 순서를 그대로 쓰면 나중에 다시 읽을 때 맥락이 붙는다.
- **사용자가 「한 번 잡으면 끝」의 대가를 알고 선택했다** — 3~4시간 세션에서 잘못 고르면
  새 세션 링크 말고는 방법이 없다는 것을 명시적으로 제시한 뒤의 결정이다. 계획·실행
  단계에서 이 결정을 「사용자가 몰랐을 것」으로 간주해 놓기 경로를 슬쩍 넣지 않는다.
