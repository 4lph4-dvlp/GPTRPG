## 실시간 동기화 강도

| Option | Description | Selected |
|--------|-------------|----------|
| 즉각 반영 (WebSocket) | 모두가 같은 순간 보는 감각. 구현이 가장 무거움, 재접속·연결끊김 처리를 직접 짜야 함 | |
| 짧은 폴링 (1~2초) | 브라우저가 주기적으로 새 사건을 조회. read_events(from_seq)를 그대로 씀 — 재접속이 "새로 고침" 개념이 아니라 폴링의 자연스러운 일부가 됨 | ✓ |
| 서사는 SSE 푸시 + 행동은 HTTP POST | 서버→클라 단방향만 상시 연결, 플레이어 액션은 일반 POST로 | |

**User's choice:** 짧은 폴링(1~2초). 사용자가 먼저 "너는 어떤 방식으로 구현하는게 좋다고 생각해?"라고 물어 Claude가 폴링을 추천(재사용 가능한 코드, 재접속이 거의 공짜, AI 응답 자체가 2~15초라 동기화 지연이 체감되지 않음, 실험 도구 규모에 WebSocket이 과함)했고 사용자가 그대로 수락.
**Notes:** 후속 질문 — 폴링으로 문장 여러 개가 한꺼번에 모여 보이는 것이 Phase 3이 증명한 "문장 단위로 흘러나온다" 체감과 달라도 되는지 확인. 사용자: "괜찮다 — 문장들이 모여 나와도 괜찮음." 폴링 주기를 0.5초로 낮추자는 대안은 기각.

## 연결 유지·재접속 규칙

| Option | Description | Selected |
|--------|-------------|----------|
| 10초 정도(폴링 몇 번 연속 실패) 표시 | 오휴가능한 민감도. 4명이 같은 방에 있을 가능성이 높아 구두로도 인지 가능 | ✓ |
| 표시하지 않는다 | 화면이 단순해지지만 플레이어가 직접 새로고침해야 끊김을 알 수 있음 | |

**User's choice:** 10초 정도(폴링 몇 번 연속 실패) 표시.
**Notes:** 재접속 범위(브라우저 새로고침/완전 종료 후 재접속 시 어디서부터 보여줄지)도 함께 질문. 옵션: (1) 세션 전체 역사를 처음부터 다시 불러와 마지막까지 스크롤 (2) 브라우저에 마지막 seq를 저장해 그 이후부터만. 사용자: 옵션 (1) 선택 — "세션 전체 역사를 다시 불러와 마지막까지 스크롤."

## 세션 종료 집계의 출력 형태

| Option | Description | Selected |
|--------|-------------|----------|
| CLI 명령으로 조회 | 기존 서브커맨드 패턴 확장. 운영자만 봄 | (부분 선택) |
| 세션 종료 시 파일로 자동 저장(JSON/CSV) | 누가 조회 명령을 안 쳐도 파일이 남음 | (부분 선택) |

**Notes:** 후속 질문으로 자동 저장 파일 형식(JSON vs CSV)을 물었고, 사용자는 JSON을 선택.
