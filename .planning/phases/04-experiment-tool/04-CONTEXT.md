## Phase Boundary

네 명이 링크 하나로 3~4시간 같은 세션 화면을 보며 플레이할 수 있고, 그동안 여섯 가설에 답할 숫자(MEAS-01·MEAS-03)가 저절로 쌓이는 것을 만든다. RIG-04·RIG-05·RIG-07·MEAS-01·MEAS-03이 이 단계의 요구사항이다.

**이 단계가 만드는 것:** Phase 1~3이 CLI로만 증명했던 것(사건 기록, 판정, AI 턴 루프)을 처음으로 **웹 화면 + 여러 명 동시 접속**으로 감싼다. 구체적으로 — 같은 세션을 여러 브라우저가 보는 폴링 기반 동기화, 끊겼다 재접속해도 이어지는 히스토리 재조회, 위협 시계·실패 카운터 화면 표시(실패 3회 시 자동 진행), 캐릭터 시트 읽기 전용 뷰, 세션 종료 시 자동 집계(CLI 조회 + JSON 파일 저장).

**이 단계가 만들지 않는 것:** 캐릭터 만들기 화면, 매칭·로비(링크 하나로 대체), 안전 장치 UI(구두로 대체), 결제·계정, 코스메틱, 룰북 저작 도구, 리캡 자동 생성.

**이 단계의 유일한 숙제(로드맵 원문):** 연결 유지 신호의 주기와 실패 횟수, 그리고 서사가 흘러나오는 도중에 끊겼다 다시 붙었을 때 이어붙이는 규칙 — 최소한만 정한다. 이번 논의로 해소했다 (D-40·D-41).

**이미 잠금 결정으로 풀려 있어 이번 논의에서 다시 열지 않은 것:** D10("조율은 외부 메신저에서 끝난다 — 발언권 락·순서 강제·짧은 타이머 폐기")이 §3.3 진행 정책 표(턴 타이머·순서 강제)를 이미 무효화한다. 이 단계는 턴 타이머·순서 강제 UI를 만들지 않는다. `session_actor`의 단일 쓰기 주체 + 명령 큐(D-09)가 동시 입력의 유일한 조율 장치다.

## Implementation Decisions

### 실시간 동기화 강도

- **D-38:** 여러 브라우저 사이의 동기화는 **짧은 폴링(1~2초 간격)** 으로 한다. WebSocket·SSE는 이번 단계에 넣지 않는다.
  - *이유:* `EventStore.read_events(session_id, from_seq)`가 이미 순번 기반 조회를 완벽히 지원한다 — 폴링은 이 함수를 주기적으로 부르기만 하면 되고 새 재생 로직이 필요 없다. AI 응답 자체가 2~15초 걸리므로 1~2초 폴링 지연은 체감상 의미가 없다. 실험 도구는 두 세션·네 명이 쓰고 끝나므로 WebSocket의 연결 상태 관리·재연결 로직 비용이 회수되지 않는다.

- **D-39:** 폴링 한 번에 여러 문장이 한꺼번에 모여서 보여도 된다 — 문장 단위 스트리밍 체감을 유지하려고 폴링 주기를 더 짧게(0.5초) 하지 않는다.
  - *이유:* 사용자가 직접 확인 — "괜찮다, 문장들이 모여 나와도 문제없다." Phase 3의 CLI가 이미 "문장 단위로 흘러나온다"는 성공 조건을 증명했으므로, 웹에서는 완전히 같은 체감을 재현할 필요가 없다.

### 연결 유지·재접속 규칙

- **D-40:** 폴링이 **약 10초(폴링 몇 번 연속 실패)** 동안 이어지지 않으면 화면에 "연결이 끊겼음"을 표시한다.
  - *이유:* 너무 민감하면 오히려 1회성 끊김을 "끊김"으로 오인식하게 만든다. 4명이 같은 방에 있을 가능성이 높아 구두로도 끊김을 알 수 있다는 점을 감안해 여유 있게 잡았다.

- **D-41:** 브라우저를 새로고침하거나 완전히 닫았다 다시 열면 **세션 전체 역사를 처음부터 다시 불러와(`from_seq=0`) 마지막까지 스크롤**한다. 브라우저에 마지막으로 본 순번을 저장해 그 이후만 불러오는 방식은 쓰지 않는다.
  - *이유:* 구현이 가장 단순하고, "처음부터 다시 시작하지 않는다"(RIG-07)는 성공 조건을 가장 확실하게 만족한다. 세션 하나에 사건 수천 개 규모(01-CONTEXT.md D-07)라 전체 재조회 비용이 문제되지 않는다.

### 링크 하나가 사람·캐릭터를 잇는 방식

- **D-42:** 네 명이 받는 링크는 **전부 같은 하나의 링크**다. 그 링크로 들어온 사람이 입장 시 자기 캐릭터를 고른다. 사람별로 다른 개인 링크는 만들지 않는다.
  - *이유:* ROADMAP이 이미 "매칭·로비는 링크 하나로 대체"라고 확정했다 — 개인별 링크를 만들면 그 링크를 네 개 만들어 따로 보내야 하는 운영자 수고가 늘어 "링크 하나"의 취지가 흐려진다.

- **D-43:** 캐릭터 선택 결과는 **브라우저 쿠키에 저장**한다. 같은 브라우저로 돌아오면 새로고침해도 이름을 다시 묻지 않고 자동으로 같은 캐릭터가 선택된다.
  - *이유:* 별도 계정·로그인 개념 없이(결제·계정은 이 단계 범위 밖) 신원을 "기억"하는 가장 가벼운 방법이다.

### 세션 종료 집계의 출력 형태

- **D-44:** 집계 결과(MEAS-01·MEAS-03)는 **CLI 조회 명령과 세션 종료 시 파일 자동 저장을 둘 다** 제공한다.
  - *이유:* 사용자가 직접 두 옵션을 합쳐서 요청했다 — "1번과 2번 옵션 두 가지를 합한 방식으로." CLI는 운영자가 세션 도중에도 확인할 수 있게 하고, 자동 저장 파일은 누가 조회 명령을 안 쳐도 Phase 5·6이 쓸 숫자가 남게 한다. 별도 웹 요약 화면은 만들지 않는다 — 이번 단계에 화면을 하나 더 만드는 비용이 든다.

- **D-45:** 자동 저장 파일 형식은 **JSON**이다. CSV는 쓰지 않는다.
  - *이유:* 이번 단계의 사건·상태가 이미 pydantic/JSON 중심이라 그대로 이어진다. 판정 사건의 `modifiers` 목록처럼 중첩 구조를 담아야 할 수 있어 평면 구조인 CSV보다 적합하다. Phase 6이 여러 세션 결과를 프로그램적으로 합쳐 계산하기도 JSON이 더 쉽다.

### Claude's Discretion

계획·조사 단계에서 판단하되, 위 결정을 뒤집지 않는 선에서:

- 폴링 API의 정확한 엔드포인트 설계(REST 형태, 응답 스키마)
- 실패 3회 도달 시 시계를 강제로 진행시키는 로직을 어느 층에 둘지 — `session_actor`가 `ResolveCheck` 처리 직후 자동으로 `AdvanceClock(trigger="fail_counter")`를 주입하는 방식이 유력하나 최종 구조는 계획 단계 판단
- 쿠키의 정확한 키 이름·만료 기간·직렬화 형식
- 자동 저장되는 JSON 집계 파일의 정확한 필드 스키마와 저장 경로/파일명 규칙
- 웹 프레임워크 선택(FastAPI 등 Python 백엔드 생태계 내에서) — PROJECT.md의 "Python 백엔드 + TypeScript 프런트엔드" 제약 안에서 리서치 단계가 정한다
- 프런트엔드 기술 스택 세부(빌드 도구, 상태 관리 등) — 화면 배치·컴포넌트 설계는 M0 범위 밖(ROADMAP 원문)이므로 최소한만
- "연결이 끊겼음" 표시의 정확한 문구·위치
- 캐릭터 선택 화면(입장 시 뜨는 것)의 정확한 모양

## Existing Code Insights

### Reusable Assets
- `src/gptrpg/event_log/store.py`의 `EventStore.read_events(session_id, from_seq)` — 폴링(D-38)과 재접속(D-41) 둘 다 이 함수 하나로 해결된다. 경계는 포함이므로 `from_seq=마지막으로_본_seq+1`로 폴링, `from_seq=0`으로 전체 재조회
- `src/gptrpg/rules_core/reducer.py`의 `GameState.failure_count`/`clock_segment`/`clock_advances` — RIG-04가 요구하는 화면 표시값이 이미 리듀서에서 계산되어 나온다. 새 집계 로직을 짤 필요가 없다
- `src/gptrpg/rules_core/entities.py`의 `Entity`/`StatEntry` — RIG-05(캐릭터 시트 읽기 전용)에 그대로 쓸 수 있다. 상태값 개수 제한이 없어(D-21) 어떤 룰북의 캐릭터든 같은 뷰로 렌더링된다
- `src/gptrpg/session_actor/actor.py`의 `AdvanceClock` 커맨드와 `_VALID_CLOCK_TRIGGERS`(`fail_counter`/`condition`/`ai_choice`) — 실패 3회 자동 진행(RIG-04)이 낼 자리가 이미 스키마에 있다. 트리거를 감지해서 커맨드를 주입하는 코드만 새로 필요하다

### Established Patterns
- `session_actor`의 단일 쓰기 주체 + 명령 큐(01-CONTEXT.md D-09) — 폴링 클라이언트 여럿이 동시에 명령을 보내도 이 계층이 그대로 직렬화한다. 웹 계층이 새로 조율 로직을 짤 필요가 없다

## Specific Ideas

**동기화 방식 결정 과정:** 사용자가 먼저 "너는 어떤 방식으로 구현하는게 좋다고 생각해?"라고 직접 물어, Claude가 폴링(1~2초)을 근거와 함께 추천했고 사용자가 그대로 수락했다(D-38). WebSocket/SSE/폴링 세 옵션 중 폴링이 이 규모(4명, 두 세션)에 맞다는 판단이 핵심 근거다.

**집계 출력 형태 결정 과정:** 제시된 세 옵션(CLI만 / 파일 자동저장만 / 웹 요약 화면) 중 사용자가 "1번과 2번 옵션 두 가지를 합한 방식으로"라며 두 옵션을 직접 조합해 새 선택지를 만들었다(D-44). 웹 요약 화면은 명시적으로 제외됐다.

</specifics>
