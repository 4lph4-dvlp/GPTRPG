# Phase 12.1 Plan 02: 값 결정 유형 완성과 인원 범위 검증 Summary

**일곱 가지 캐릭터 값 결정 조작(pick_one·pick_many·allocate_points·place_fixed_values·roll_to_fill·free_text·derive) 전부를 선언·실행 두 시점에서 검증하고, 던전월드류·OpenQuest·Cairn 세 룰북이 실제로 서로 다른 조합을 등록 시점에 강제하며, 인원 범위를 룰북이 데이터로 적고 4d6k3 keep 표기를 굴리고 재현한다.**

## Performance

- **Duration:** 정확히 측정 안 됨(단일 연속 세션)
- **Tasks:** 3 (계획서 원안) + 시험 보강 커밋 1건
- **Files modified:** 13 (신설 1 + 수정 12)

## Accomplishments

- `CreationStepDecl.__post_init__`이 일곱 kind 전부(나머지 넷 pick_many·allocate_points·roll_to_fill·derive를 이 계획이 채움)의 필수/금지 칸 조합을 `StatEntry._validate_form_payload`와 같은 형식으로 검증하고, `Rulebook.__post_init__`이 `depends_on`/`default_from`이 존재하지 않거나 뒤에 선언된 단계를 가리키면 거절해 순환을 구조적으로 없앴다
- `resource_change._DICE_EXPR`에 keep 표기(`k<K>`/`kl<K>`)를 더하고 `parse_dice_expr` 공개 함수와 `roll_amount`의 keep 처리를 추가 — D22 원문 예시 `4d6k3`(넷 굴려 높은 셋)이 표현·굴림·재현된다(눈 전부가 사건에 남는다)
- `session_actor.actor._prepare_complete_creation_step`이 나머지 네 kind를 실행 시점에도 검증한다 — `pick_one`/`pick_many`는 닫힌 목록 재대조, `allocate_points`는 예산 합계·항목 상한, `roll_to_fill`은 브라우저 값을 무시하고 주입된 `Roller`로만 굴리며(D14), `derive`는 의존 단계의 확정된 축 값으로 계산한다
- `PartySizeRange`/`InvalidPartySizeRange`/`PartySizeOutOfRange`/`validate_party_size`/`narrow_party_size_range`를 `rules_core/rulebook.py`에 세우고, `Rulebook.party_size_range` 선언과 `_prepare_fix_party_size`의 실제 범위 대조를 연결했다. `PARTY_MEMBER_LIMIT` 절대 안전 밸브는 층 규약(`session_actor`가 `agents`를 못 본다)에 따라 `web/routes_creation.py`에 두었다
- `build_creation_stats` 순수 함수로 `StatEntry` 조립 규칙을 한 자리로 모았다 — `_prepare_create_character`가 이제 이 함수를 호출한다
- 세 룰북에 실제로 다른 조합을 채웠다 — 던전월드류(대본 6단계 전체: pick_one·free_text·place_fixed_values·derive·pick_one·free_text), OpenQuest(roll_to_fill 하나 + allocate_points 네 개 다중 풀 + free_text), Cairn(roll_to_fill 둘 + pick_one + free_text). `validate_registered_rulebooks()`가 세 kind 집합이 전부 같으면 거절하고, `creation_steps`/`party_size_range` 미선언도 거절한다
- `tests/test_creation_script_fixture.py`(신설) — 대본 1~4단계가 정확히 어느 `CreationStepDecl`에 대응하는지, 5·6단계는 대응이 없다는 것을, 그리고 대본의 항목 이름·선택지 문구·숫자가 `rules_core`/`session_actor` 소스 어디에도 없다는 것을 자동으로 단언한다(CHAR-01의 유일한 실증 시험)

## Decisions Made

- **Task 순서 충돌 해소(계획 자체의 내부 모순):** 계획 Task 2의 액션 ④는 "party_size_range가 None이면 CommandRejected"를 액터에 요구했는데, 실제 세 룰북 값 채우기는 Task 3의 몫이다. 문자 그대로 순서대로 하면 Task 2 직후 던전월드류로 하는 모든 기존 `FixPartySize` 호출(12.1-01의 트레이서 시험 포함)이 즉시 깨진다. 등록 시점 필수 검사(계획 액션 ⑤)를 Task 3으로 미루고, 던전월드류의 최종 범위(3~5, 어차피 Task 3이 같은 값을 다시 선언하므로 재작업 없음)만 Task 2에서 앞당겨 채워 이 충돌을 해소했다.
- **PARTY_MEMBER_LIMIT의 위치:** 계획의 `<behavior>` 절은 액터가 검사한다고 적었지만 같은 계획의 `<action>` 절은 "session_actor가 agents를 import할 수 없다"는 층 규약(`.importlinter` contract:2)을 근거로 `web/routes_creation.py`가 검사해야 한다고 명시적으로 못박았다 — 두 절이 서로 다른 자리를 가리키는 자기모순이라, 아키텍처 규약이 이기는 쪽(web 계층)으로 구현했다.
- **build_creation_stats의 max/depleted_effect_ref 처리:** 계획 텍스트는 "각 축의 form·max·depleted_effect_ref는 룰북 선언에서 가져온다"고 적었지만 `ResourceAxisDecl`에는 애초에 max/depleted_effect_ref를 선언할 칸이 없다(존재하지 않는 필드를 참조하는 계획 서술). 축 이름으로 "체력이면 상한 있음"을 추측하면 `validate_entity_axes`가 세운 "축 이름 문자열을 코드가 해석하지 않는다" 규약을 어기게 되므로, 두 칸은 `None`으로 남기고 알려진 한계로 문서화했다 — 기존 `_prepare_create_character`의 손 조립과 동일한 동작이라 이번 변경으로 새로 생긴 갭이 아니다.
- **CHAR-04를 REQUIREMENTS.md에서 Complete로 찍지 않았다(원 설계 의도 대조):** 이 계획의 PLAN.md frontmatter는 `requirements: [CHAR-01, CHAR-04]`라고 적었지만, REQUIREMENTS.md의 CHAR-04 원문은 "`characters_data.py`의 손으로 적은 파이썬 상수를 이 절차의 산출물로 대체"까지 요구한다 — 이 계획은 `characters_data.py`를 한 글자도 안 건드렸다(그 대체는 D-12가 명시적으로 12.1-05에 배정한 일이다). 12.1-01-SUMMARY.md가 이미 "여러 계획에 걸친 요구사항 조기 완료 표시"를 경고했으므로, 표준 절차(`gsd_run query requirements.mark-complete CHAR-01 CHAR-04`)가 일단 둘 다 Complete로 찍은 뒤 이 어긋남을 발견하고 **CHAR-04만 되돌려 Pending으로 남겼다**(CHAR-01은 원문이 요구하는 것을 이 계획이 실제로 전부 채웠으므로 Complete 유지). REQUIREMENTS.md의 CHAR-04 행에 "그릇 절반은 12.1-02가 검증했다, 대체는 12.1-05 몫" 메모를 남겼다.
