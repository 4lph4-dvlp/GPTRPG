### WR-01: 자동 호출로 바뀐 `announce()`가 언마운트 뒤 상태 갱신을 막는 가드가 없다

**Files modified:** `frontend/src/screens/CreationScreen.tsx`
**Commit:** `89c05b0`
**Applied fix:** `usePolling.ts`의 `beacon()`/`poll()`과 이 파일의 다른 두
effect(방장 재실 신호, 항목 선언 조회)가 이미 지키는 `alive` ref 관례를
`announce()`에도 맞췄다. `announceAliveRef`를 새로 두고, 컴포넌트
마운트/언마운트에 맞춰 `true`/`false`로 돌리는 별도 `useEffect`를
추가했다. `announce()` 내부의 `setPending(true)`/`setError(null)`(진입
시점, 항상 마운트 상태이므로 가드 불필요)는 그대로 두고, `await`
이후에 실행되는 세 지점 — 성공 시 `feed.pollNow()`, 실패 시
`setError(...)`, `finally`의 `setPending(false)` — 앞에 각각
`if (announceAliveRef.current)` 검사를 추가했다. 검토가 제시한 패턴을
그대로 따랐고, 새 `useRef`를 만들지 별칭을 리뷰안대로 `aliveRef`로 할지만
바꿔 이 파일의 다른 지역 변수와 이름이 겹치지 않게 `announceAliveRef`로
명명했다.

**검증:** `npx tsc --noEmit -p .` 통과(에러 없음), `npx vitest run` —
7개 파일 98건 전부 통과. 두 검사 모두 격리된 리뷰-픽스 워크트리
안에서, 메인 체크아웃의 `frontend/node_modules`를 임시 심볼릭 링크로
연결해 실행한 뒤(재현 가능하도록 검사 직후 링크를 제거해 원상복구)
확인했다 — 메인 체크아웃의 `node_modules` 자체는 건드리지 않았다.

### WR-02: 자동 안내 호출이 여러 탭에서 동시에 터지면서, 서버가 이미 알고 있는 「AI 제공자가 두 번 불릴 수 있다」 경쟁을 훨씬 더 자주 건드리게 됐다

**File:** `frontend/src/screens/CreationScreen.tsx:359-401`(자동 호출
effect), `src/gptrpg/web/routes_creation.py:787-800`(`announce_creation`
사전 검사), `src/gptrpg/session_actor/actor.py:1874-1888`(`_prepare_gm_spoke`
도크스트링)

**Reason:** 기계적으로 닫을 수 있는 결함이 아니라 이 계획이 결정한 적
없는 제품 판단이 필요한 자리라 코드를 건드리지 않고 남긴다. 리뷰가 직접
검토한 두 갈래 모두 이번 실행에서 스스로 고를 수 없다:

1. **근본 수정** — `announce_creation`(그리고 같은 패턴을 쓰는
   `nominate`/`follow_up`/`wrap_up`)의 큐 밖 사전 검사를 큐 안 검사로
   대체하거나 세션당 뮤텍스로 좁히는 것. 리뷰 스스로 "이번 계획의
   범위를 넘는 별도 작업"이라고 적었다 — 네 경로 모두를 건드리는
   별도 계획감이다.
2. **완화책(프런트엔드 쪽 경합 창 좁히기)** — `shouldAnnounce`에
   `youAreHost` 인자를 추가해 방장 탭만 자동 호출하게 만드는 것. 리뷰
   본문이 제시한 코드 스니펫이지만, 리뷰 자신이 바로 옆에 "방장이
   아예 탭을 닫아 버리면 아무도 안 부르는 새 결함이 생긴다"고 명시해
   뒀다 — 즉 이 완화책은 "여러 탭이 동시에 부른다"는 문제를 "아무도
   안 부를 수 있다"는 새 문제로 바꿀 수 있다. 방장이 탭을 닫아도
   서버가 대신 안내를 진행할 방법이 이 계획 안에는 없다.

두 선택지 모두 "어떤 클라이언트가 이 AI 호출을 책임질 것인가"라는
아직 정해지지 않은 제품 결정을 전제로 한다 — 코드를 고치기 전에
사람이 먼저 답해야 할 질문이다. 사건 자체는 여전히 하나만 남는다(D-12
`AlreadyGmSpoken` 재검사가 보장) — 이번에 남기는 것은 AI 제공자
호출이 여러 번 나가는 비용/지연 문제뿐이며, 이는 이번 계획이 만든
새 결함이 아니라 기존 문서화된 한계(actor.py 1874-1888행 도크스트링)가
더 자주 발현되게 된 것이다.

**Decision needed (사람이 결정할 것):**
- (a) 지금은 그대로 두고(비용 증가를 감수하고) 근본 수정을 별도 계획으로
  분리한다, 또는
- (b) 이번 계획 안에서 `youAreHost` 완화책을 적용하되 "방장이 탭을 닫으면
  아무도 자동 안내를 못 부른다"는 새 결함을 어떻게 처리할지(예: 방장이
  아닌 다른 탭도 일정 시간 뒤 대신 부르게 하는 타임아웃 등) 함께
  결정한다.

이번 실행은 (a)/(b) 중 하나를 임의로 골라 세션 동작을 조용히 바꾸는
대신, 코드를 리뷰가 관찰한 상태 그대로 남겨 뒀다.
