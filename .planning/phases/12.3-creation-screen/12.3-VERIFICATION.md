## 결론 먼저

**4차가 재현한 gap(흘려보냄 판정이 사람에게 영구히 들러붙어 새 지목을 한 번도 못 받음)은 진짜로 닫혔다.** 12.3-09가 「판정은 사람이 아니라 그 사람의 그 차례에 대한 것」이라는 원칙으로 `_forfeited_at`에 지목 순번을 함께 적고, `forfeited_nomination_mark`로 중복 방지 키에 흘려보냄 표시를 이어 붙였다. 이번 5차 검증이 관련 코드(`creation_state.py`·`routes_creation.py`)를 직접 읽고, 12.3-09가 더한 회귀 시험 셋을 직접 재실행해 통과를 확인했다.

**하지만 그 수정 자체가, 방금 돈 코드 리뷰(`12.3-REVIEW.md`)가 지목한 새 CR-01만큼 실질적인 새 결함을 열어 놓았다 — 그리고 이번 검증이 그것을 소스 한 글자도 안 고친 채 직접 재현해 독립 확인했다.** 흘려보냄 표시(`forfeited_nomination_mark`)는 「지금 흘려보낸 상태인가」만 이진으로 본다. 회복 지목이 성공적으로 기록되어 흘려보냄 판정이 풀리는 순간, 이 표시는 빈 문자열로 되돌아간다. 그런데 이미 항목 값을 낸 사람이 흘려보내진 경우(정확히 12.3-09 자신이 고치려던 시나리오)에는 후보 목록 자체가 안 바뀌므로, 표시가 빈 문자열로 돌아가면 중복 방지 키도 **흘려보내지기 전과 완전히 같은 키**로 되돌아간다. 그 키는 리듀서가 지우지 않고 영구 보관한 **옛(흘려보내지기 전) 지목 기록**을 그대로 가리킨다 — 그래서 회복이 끝난 뒤 같은 상황에서 지목을 한 번 더 부르면(재시도·이중 클릭·경쟁 폴링), 서버가 새 사건을 만드는 대신 그 옛 기록을 그대로 돌려준다.

**중요한 단서 — 이번 검증이 코드 리뷰가 다루지 않은 자리까지 추적해서 확인한 것이다.** `frontend/src/panes/CreationPane.tsx:527`을 직접 읽어 보면, 화면에서 이 API(`/creation/nominate`)를 부르는 자리는 오직 한 곳뿐이고, 그 자리는 응답값(`character_id`/`say`)을 **전혀 안 쓰고** 곧바로 다시 폴링만 한다(`.then(() => pollNow())`). 그리고 문제의 옛 기록 반환 경로는 `actor.submit(...)`(사건 기록에 실제로 남기는 자리)에 도달하기 **전에** 조기 반환한다 — 즉 사건 기록 자체는 이 결함으로 오염되지 않는다. 그래서 이번에 재현한 결함은 **서버가 특정 조건에서 API 응답으로 잘못된(오래된) 값을 돌려준다는 것은 확실히 참**이지만, 지금 이 저장소의 유일한 화면 소비 방식(응답을 버리고 다시 폴링) 위에서는 그 잘못된 응답이 화면에 곧바로 드러나지는 않는 것으로 보인다 — 폴링이 참조하는 진짜 상태(`creation_gm_said`)는 회복 기록(seq=3)을 그대로 유지하기 때문이다.

**그렇다고 이것을 gap에서 빼지는 않는다.** 세 가지 이유다. 첫째, `12.3-09-PLAN.md` 자신이 `must_haves.prohibitions`에 「회복이 영구 배제로 바뀌지 않는다」를 명시했고, 이 결함은 그 원칙을 API 응답 수준에서 정면으로 어긴다 — 지금 화면이 우연히 그 응답을 안 쓴다는 사실이 계약 위반 자체를 지우지는 않는다. 둘째, 이 공개 HTTP 경로에 의존하는 소비자가 앞으로 하나라도 더 생기면(다른 화면 기능, 재시도 로직, 시험 도구) 그 즉시 옛 값을 진짜로 사용하게 된다 — 「지금 화면이 안 쓴다」는 안전장치가 아니라 우연이다. 셋째, 근본 원인(리듀서가 지우지 않는 영구 보관 + 이진 표시)은 다른 경쟁 상황에서도 같은 종류의 오응답을 계속 만들 구조적 취약점이다. 그래서 이 항목은 이번에도 정식 gap(FAILED)으로 남긴다 — 다만 위 단서를 아래 §CR-01 절과 결론에 명시해, 다음 라운드가 「화면이 당장 막혀 있다」와 「응답 계약이 깨져 있다」를 혼동하지 않게 한다.

## CR-01 독립 재현 (이번 검증이 소스 무변경으로 직접 실행)

시나리오는 12.3-REVIEW.md가 재현한 것과 같은 구조다 — **이미 `name` 항목 값을 낸 사람이 흘려보내지는 경우**(후보 앞줄에 있어 후보 목록이 안 바뀜)로 재현해야 실제 결함이 드러난다. 값만 없는 사람으로 시도하면(후보 뒤쪽, 재실 신호에서만 나온 후보) 흘려보냄이 순서 정렬 자체를 영구히 바꿔 버려 후보 목록 문자열이 달라지므로 이 결함이 가려진다 — 이번 검증이 이 두 경로를 모두 직접 실행해 차이를 확인했다.

```python
# creation_state.py / routes_creation.py의 실제 함수를 그대로 호출 (소스 무변경)
sid = "verifier-repro3"
creation_state.mark_character_present(sid, "pc-1")  # + pc-2, pc-3
step_values = {("pc-1", "name"): CreationStepFold(seq=1, kind="text", text_value="Aria", ...)}

def dedupe_key(state, sid):
    candidates = creation_state.present_candidates(state, sid)
    base = f"nominate:{candidates}"
    mark = creation_state.forfeited_nomination_mark(state, sid)
    return base + mark, candidates

# CALL 1 — 첫 지목(실제로는 routes_creation.py가 이 키로 사건을 남긴다, seq=2)
state = GameState(session_id=sid, party_size_fixed=3, creation_step_values=step_values)
key_call1, _ = dedupe_key(state, sid)
state = replace(state, creation_gm_said={key_call1: CreationGmLineFold(seq=2, kind="nominate",
                                                                        target_character_id="pc-1", ...)})

# pc-1이 흘려보내진다 (시계만 되감아 판정)
forfeited_nominee(state, sid)
_nomination_watermark[(sid, "pc-1")] = (2, time.monotonic() - NOMINATION_IDLE_S - 5)
forfeited_nominee(state, sid)  # -> "pc-1" (흘려보냄 판정)

# CALL 2 — 회복 지목 (routes_creation.py가 #after 표시 붙은 새 키로 사건을 남긴다, seq=3)
key_call2, _ = dedupe_key(state, sid)   # "...#after:pc-1:2" — CALL 1과 다름 (정상 동작)
state = replace(state, creation_gm_said={**state.creation_gm_said,
                                          key_call2: CreationGmLineFold(seq=3, kind="nominate",
                                                                         target_character_id="pc-1", ...)})

# CALL 3 — 회복이 끝난 뒤, 같은 상황에서 지목을 한 번 더 부른다 (재시도/이중 클릭/경쟁 폴링)
key_call3, _ = dedupe_key(state, sid)
already_said = state.creation_gm_said.get(key_call3)
```

**실제 실행 결과(이번 검증이 직접 돌림):**
```
CALL 1 dedupe key:                       nominate:('pc-1', 'pc-2', 'pc-3')
CALL 2 dedupe key (recovery, differs):   nominate:('pc-1', 'pc-2', 'pc-3')#after:pc-1:2   True
CALL 3 dedupe key:                       nominate:('pc-1', 'pc-2', 'pc-3')
CALL 3 key == CALL 1 key (STALE)?        True
CALL 3 would return already_said record: CreationGmLineFold(seq=2, kind='nominate', ...)
Its .seq: 2   (실제 최신 사건은 seq=3)
```

**세 번째 호출이 실제 최신 사건(seq=3, 회복)이 아니라 그보다 오래된 사건(seq=2, 흘려보내지기 전)을 돌려준다.** `12.3-09-SUMMARY.md`가 근거로 대는 유일한 끝-끝 회복 시험
(`test_a_forfeited_participant_who_already_submitted_a_value_gets_another_turn_and_unblocks_the_roster_lock`)을 직접 읽어 보면(`tests/test_creation_screen_state.py:955-1090`), 회복 지목 **전에** `pc-recover-2`가 캐릭터를 완성해 후보 목록이 바뀐다 — 그래서 이 정확한 충돌(회복 뒤 같은 상황에서 세 번째로 부르는 경우)을 밟지 않는다. `test_a_forfeited_ruling_holds_for_the_same_nomination_but_a_new_one_starts_the_clock_over`도 「새 지목이 옛 판정을 안 물려받는다」(CALL 1→CALL 2 전이)만 보고, 「회복 뒤 세 번째 호출이 CALL 1로 되돌아가는가」는 안 본다.

**단, 이번 검증이 추가로 확인한 것 — 이 결함이 화면까지 닿는 경로.** `frontend/src/panes/CreationPane.tsx:520-536`의 유일한 호출 자리:

```typescript
void nominateCreationSpeaker(sessionId, rulebookId)
  .then(() => pollNow())   // 응답값(character_id/say)을 안 쓴다 — 그냥 다시 폴링만 한다
  .catch(() => undefined)
  ...
```

그리고 `routes_creation.py`의 결함 경로는 `already_said`가 있으면 `actor.submit(...)`(사건에 실제로 기록하는 자리) **전에** 조기 반환한다 — 즉 이 3번째 호출은 사건 기록을 훼손하지 않는다(`creation_gm_said`는 여전히 seq=3을 최신으로 유지). 그래서 이 결함으로 서버가 **API 응답으로는** 확실히 잘못된(오래된) 값을 돌려주지만, 지금 이 저장소의 유일한 화면 소비 방식 위에서는 다음 폴링이 곧바로 진짜 최신 상태(회복된 pc-1)를 다시 그려서 화면에 오래 남는 오작동으로는 이어지지 않는 것으로 보인다. **그렇다고 이 결함을 gap에서 빼지 않는 이유**는 위 「결론 먼저」 절에 적은 세 가지(계획 자신의 금지 조항 위반, 미래 소비자에게 열린 함정, 근본 원인의 구조적 취약성)를 그대로 따른다.

**다만 이번 검증이 추가로 확인한 중요한 단서가 있다.** 이 API(`/creation/nominate`)를 부르는 화면 쪽 자리는 오직 하나이고, 그 자리는 응답값을 전혀 안 쓰고 다시 폴링만 한다 — 그리고 결함 경로는 사건 기록(`actor.submit`) 전에 조기 반환해 진짜 상태는 안 건드린다. 그래서 코드 리뷰가 우려한 「파티가 영구 교착에 빠진다」는 서술은, **이 저장소의 현재 화면 소비 방식 위에서는** 그대로 재현되지 않는 것으로 보인다 — 오응답은 API 계약 수준에서 확실히 참이지만, 화면까지 곧바로 닿지는 않는다. 그럼에도 이 항목을 gap에서 빼지 않은 이유는 (1) 계획 자신의 명시적 금지 조항을 API 응답 수준에서 정면으로 어기고, (2) 화면이 우연히 안 쓴다는 사실이 미래의 다른 소비자(재시도 로직, 새 화면 기능, 시험 도구)에게는 안전장치가 아니며, (3) 근본 원인(리듀서의 영구 보관 + 이진 표시)이 구조적으로 남아 있기 때문이다.

**남은 사람 확인도 아직 끝나지 않았다.** 동의 관문의 교차 전파(화면 쪽)는 이번에도 QA 도구의 구조적 한계로 라이브 확인이 안 됐고, `12.3-05-SUMMARY.md`의 14개 체크리스트도, ROADMAP.md가 명시한 「처음부터 끝까지 화면 조작만으로」 확인 관문도 아직 한 번도 사람이 연속으로 수행하지 않았다.
