## 결론 먼저

**5차 검증이 재현한 새 CR-01(회복 뒤 옛 지목 기록으로 되돌아가는 결함)은 진짜로 닫혔다.** 12.3-10이 흘려보냄 표시(`forfeited_nomination_mark`)를 「지금 흘려보낸 상태인가」(이진, 회복되면 뒤로 돌아감)에서 「이 세션에서 마지막으로 판정된 흘려보냄」(단조, 앞으로만 감)으로 재정의했다. 이번 6차 검증이 `creation_state.py`의 실제 함수 본문을 직접 읽어 조기 반환이 완전히 사라졌고 표시가 `_forfeited_at`의 세션 내 최대 `applied_seq` 항목 하나로 조립된다는 것을 확인했다. 12.3-10이 더한 끝-끝 회귀 시험(`test_a_third_nominate_call_after_recovery_returns_the_latest_nomination_not_the_pre_forfeit_one`)과 WR-01까지 닫도록 재작성된 경계 시험(`test_a_forfeited_nomination_changes_the_dedupe_mark_but_a_healthy_one_leaves_it_untouched`)을 직접 재실행해 통과를 확인했고, 5차 검증이 통과로 확인한 여섯 시험(#4·#15·#16·#17·#19·#20·#21에 해당)도 함께 재실행해 회귀가 없음을 확인했다. `routes_creation.py`의 실제 실행 코드가 한 줄도 안 바뀌었다는 것(주석만 갱신)도 `git diff -U0`으로 직접 확인했다.

**그런데 이번 검증이 CR-01보다 훨씬 심각한, 이미 사람이 실제로 겪은 결함 하나를 함께 확인했다.** `12.3-UAT.md`(5차 검증과 12.3-10 계획 사이에 실행됨, 커밋 `460b86d`)가 서버를 돌리는 기계가 아닌 다른 브라우저·다른 기기·시크릿 모드로 세션 링크를 열면 **화면이 아예 안 뜬다**는 것을 사람이 직접 겪고 기록했다. 근본 원인은 `frontend/src/session/browserIdentity.ts:70`의 `crypto.randomUUID()` 호출이다 — 이 Web API는 브라우저가 「안전한 맥락(secure context)」일 때만 존재하는데, README §실험 당일 실행 절차가 참가자 넷에게 나눠 주라고 명시적으로 지시하는 링크 형태(`http://{서버 기기 주소}:8000/?session={식별자}`, 평문 http + LAN·tailscale IP)는 secure context가 성립하지 않는다. `frontend/src/screens/CreationScreen.tsx:144`가 이 함수를 컴포넌트 렌더 본문에서 곧바로 부르므로 화면의 첫 렌더 자체가 예외를 던지고, `frontend/src/main.tsx`에 오류 경계가 없어 그 예외가 조용히 삼켜져 빈 화면만 남는다.

**이번 검증이 이 UAT의 근본 원인 서술을 소스 코드로 독립 재확인했다.** `browserIdentity.ts`는 Phase 12.3-04(`git log` 최종 커밋 `65ec374`) 이후 한 줄도 안 바뀌었고, 12.3-10도 계획서 자신이 명시한 대로 `frontend/` 아래를 전혀 안 건드렸다(`git diff --name-only e46fcae..3546cc6 -- frontend`가 빈 출력). 즉 이 결함은 지금 이 순간 이 저장소에 **그대로** 살아 있다 — 대체 식별자 경로도, 오류 경계도 여전히 없다.

**왜 다섯 라운드의 자동 검증이 이것을 못 잡았는가.** 자동 시험·QA 도구(`browse` 헤드리스, `vitest`, `tsc`)가 전부 `127.0.0.1`로만 화면을 열었다 — 유일하게 secure context가 성립하는 주소다. 그래서 이 실패 경로가 다섯 라운드 내내 한 번도 실행되지 않았다. 이번 검증도 소스 코드 대조만으로는 발견하지 못했을 것이다 — `12.3-UAT.md`가 실제 사람이 실제 기기로 시도해 먼저 잡았고, 이번 검증은 그 발견을 코드로 재확인하는 역할을 했다.

**이 결함이 CHAR-06을 정면으로 막는다.** CHAR-06과 이 phase의 목표 문장(「사람이 브라우저만으로 끝까지 할 수 있게 한다」)은 참가자 각자의 기기·브라우저를 전제한다 — README가 정한 실제 사용 형태 그대로다. 그런데 그 형태로 접속하는 참가자 전원이 빈 화면만 본다. 화면이 보이는 것은 서버를 돌리는 기계 하나뿐이다. CR-01(#22, API 응답 계약 결함)은 화면이 우연히 그 응답을 안 쓴다는 완화 요인이라도 있었지만, 이번 결함에는 그런 완화가 전혀 없다 — 렌더 자체가 막힌다.

**목표는 이번에도 완전히는 성립하지 않는다. CHAR-06을 완료로 표시할 수 없다** — 5차 검증이 발견한 gap은 닫혔지만, 그보다 근본적인 새 gap이 이미 사람에 의해 발견돼 열려 있다.
