## Critical Issues

### CR-01: 조작 요소 선택자가 DOM에서 0개를 찾아도 "확인 불가"가 아니라 조용히 통과한다

**File:** `scripts/check_narrow_viewport.py:688-702`

**Issue:** `judge()`의 조작 요소 단언(③)은 `TOUCH_TARGETS`의 각 선택자로
`measurement["targets"][selector]`를 꺼내 그 배열을 돈다:

```python
for selector, human_name, check_height in TOUCH_TARGETS:
    entries = measurement["targets"][selector]
    for index, entry in enumerate(entries):
        ...
```

이 배열이 **비어 있으면**(그 선택자가 실제 DOM에서 0개를 찾았으면) `for` 루프가
한 번도 안 돌고, 그 조작 요소에 대해서는 어떤 사유 문장도 안 쌓인다 — 결과적으로
`judge()`는 그 대상을 "확인했더니 문제없다"와 똑같이 취급한다. 그런데 "선택자가
0개를 찾았다"는 이 파일 자신이 여러 번 강조하는 구분(도크스트링 47~53번째 줄,
`missingElements` 처리, `REQUIRED_MEASUREMENT_KEYS` 검사)과 정확히 같은 종류의
빈 값 경계다 — "없음"은 "0"과 다르다.

지금은 고정판(fixture)이 `TOUCH_TARGETS`의 일곱 선택자 전부를 실제로 담고 있어서
이 경로가 안 걸린다(직접 측정값을 찍어 확인함 — 일곱 선택자 모두 `entries.length
>= 1`). 하지만 이 파일의 다른 모든 자리는 "선택자·이름·차례가 어긋나면 즉시
종료 코드 2"를 규율로 삼는데, 조작 요소 선택자 하나만 이 규율 밖에 있다. 다음에
`CreationPane.tsx`/`ChatPane.tsx`의 마크업이 바뀌어 `.composer__row .btn`이나
`.proposal .btn` 같은 조합 선택자가 고정판과 실제 소스 양쪽에서 갈라지면(예:
버튼 클래스 이름이 바뀌거나 구조가 한 단계 더 깊어지면), `check_fixture_still_mirrors_source()`는
`REQUIRED_SOURCE_CLASS_NAMES`에 없는 조합 선택자(`.composer__row .btn`, `.proposal
.btn`, `select`, `input[type="number"]`)는 애초에 감시하지 않으므로 못 잡고,
`judge()`는 그 조작 요소를 "잰 게 없으니 문제없다"로 조용히 통과시킨다. 정확히
이 문서 자신이 "1년 가까이 살아남은 이유"라고 지목한 실패 모양(확인 못 함이
통과로 읽힘)이 이번에 새로 생긴 코드 자리에 남아 있다.

**Fix:** `extract_measurements()`(또는 `judge()` 진입부)에서 `TOUCH_TARGETS`의
각 선택자에 대해 `len(measurement["targets"].get(selector, [])) >= 1`을 확인하고,
하나라도 0개면 사람이 읽을 사유와 함께 `None`을 돌려줘 호출자가 종료 코드 2로
끝내게 한다:

```python
missing_targets = [
    selector for selector, _name, _check in TOUCH_TARGETS
    if len(item["targets"].get(selector, [])) == 0
]
if missing_targets:
    print(
        f"{item['name']} 측정값에서 다음 선택자가 요소를 하나도 못 찾았다"
        f"(확인 불가): {missing_targets}",
        file=sys.stderr,
    )
    return None
```

## Warnings

### WR-01: `--self-test`가 "그 함정이 겨눈 단언"이 아니라 "아무 단언이나"가 빨강이면 통과로 본다

**File:** `scripts/check_narrow_viewport.py:868-875`

**Issue:** `run_self_test()`는 함정마다 `judge(target)`을 부르고 `passed`(사유가
하나도 없는가) 하나만 본다:

```python
passed, reasons = judge(target)
if passed:
    print(f"{trap_name} · {target_shape} · 초록(단언이 죽었다)")
    dead_assertions.append(trap_name)
else:
    first_reason = reasons[0] if reasons else "(사유 없음)"
    print(f"{trap_name} · {target_shape} · 빨강 · {first_reason}")
```

`run_self_test()`의 도크스트링은 "함정 셋을 스스로 얹어 **각 단언이** 실제로
빨강을 내는지 뒤집어 확인한다"고 적혀 있다. 그런데 실제로는 "그 함정이 겨눈
바로 그 단언"이 아니라 "판정 전체에 사유가 하나라도 남는가"만 본다. 실제로
돌려서 확인한 결과, 함정 셋 중 둘이 겨눈 단언이 아닌 **다른** 단언과 함께
빨강을 냈다:

- `pixel-floor`(넘침 단언 ②를 겨눔)는 ②뿐 아니라 조작 요소 단언(③) 일곱 개
  전부를 함께 빨강으로 냈다.
- `starved-story`(서사 최소선 단언 ①을 겨눔)는 ①뿐 아니라 상태 칸 상한
  단언(⑥)도 함께 빨강으로 냈다.
- `clipped-composer`만 겨눈 단언(③) 하나로 깔끔하게 빨강이 났다.

이것이 뜻하는 것 — 만약 미래에 넘침 단언(②)이 다시 죽어도(예: `shellScrollHeight`
비교가 실수로 지워져도), `pixel-floor` 함정은 여전히 조작 요소 단언(③)이
대신 빨강을 내 주므로 `--self-test`는 여전히 통과(0)를 찍는다. 죽은 것은 ②인데
"단언들이 살아 있다"는 초록 결과가 나온다 — 이 문서가 이번 라운드에서 정확히
막으려던 모양("초록만 내는 그물은 아무것도 증명하지 않는다")이 `--self-test`
자신의 판정 방식 안에 그대로 남아 있다.

**Fix:** `TRAPS`에 "이 함정이 겨눈 단언의 사유 문장에 반드시 있어야 하는
표식"을 넷째 칸으로 추가하고, `run_self_test()`가 `passed`뿐 아니라 그 표식이
`reasons` 안에 실제로 있는지도 확인한다:

```python
TRAPS: list[tuple[str, str, str, str]] = [
    ("pixel-floor", ..., "844x390", "골격 내용"),       # 넘침 단언 ②의 사유 접두어
    ("clipped-composer", ..., "844x390", "잘려 화면"),   # 닿을 수 있음 단언 ③
    ("starved-story", ..., "390x844", "서사 칸이"),      # 서사 최소선 단언 ①
]
...
passed, reasons = judge(target)
hit = any(marker in r for r in reasons)
if not hit:
    dead_assertions.append(trap_name)   # 겨눈 단언이 안 울렸다 — 죽었을 수 있다
```

### WR-02: 상태 칸 25% 상한 단언이 실제 CSS 분기 기준(폭 1080px)이 아니라 형태 이름과의 문자열 비교로 갈린다

**File:** `scripts/check_narrow_viewport.py:732-738`

**Issue:** 상태 칸 상한 단언(⑥)은 `measurement["name"] != WIDE_SHAPE`로
"좁은 형태인가"를 가른다. 그런데 실제 CSS는 `@media (max-width: 1080px)`로
갈린다(`frontend/src/styles.css:175`). 지금 `SHAPES`에는 1080px보다 넓은 형태가
`"1440x900"` 하나뿐이라 우연히 결과가 같지만, 이 판정은 **형태의 실제 폭**이
아니라 **형태의 이름**을 본다. `_validate_shape_name_constants()`가 `WIDE_SHAPE`
이름이 `SHAPES`에 있는지는 검사하지만, 그 형태의 `width`가 실제로 1080을
넘는지는 검사하지 않는다 — 다음에 `SHAPES`에 폭 1080 초과의 새 형태를
`"1440x900"`이 아닌 다른 이름으로 추가하면, 그 형태는 데스크톱 CSS를
쓰면서도 이 스크립트에서는 "좁은 형태"로 분류돼 25% 상한을 강제로 걸어
버린다(실제로는 그 상한 자체가 CSS에 없는데도).

**Fix:** 이름 비교 대신 폭 비교로 바꾼다. CSS의 분기 기준(1080px)을 상수로
한 번 적어 두 자리(이 스크립트와 사람이 읽을 주석)가 같은 숫자를 보게 한다:

```python
# frontend/src/styles.css:175의 @media (max-width: 1080px)과 같은 값.
NARROW_BREAKPOINT_PX = 1080
...
if measurement["innerHeight"]... # (기존 로직)
if shape_width_for(measurement) > NARROW_BREAKPOINT_PX:
    ... # 상한 단언 건너뜀
```

## Info

### IN-01: `className=` 안에서 이름을 찾는 정규식이 중첩 중괄호(템플릿 리터럴 안 `${...}`)를 못 넘는다

**File:** `scripts/check_narrow_viewport.py:203-211`

**Issue:** `_CLASS_NAME_ATTR_RE = re.compile(r'className=(?:\{[^}]*\}|"[^"]*")', ...)`의
`[^}]*`는 첫 `}`에서 멈춘다. `className={\`chat-line ${cond ? "a" : "b"}\`}`처럼
중괄호가 중첩된 JSX(템플릿 리터럴 안에 `${...}`가 있는 경우)를 만나면 정규식이
바깥 `className={...}`의 진짜 닫는 중괄호보다 먼저 멈춰서, 그 뒤에 오는 클래스
이름을 못 찾는다. 지금 `ChatPane.tsx`·`CreationPane.tsx`·`StatusPane.tsx`·
`StoryPane.tsx`를 실제로 돌려 확인한 결과 이런 패턴이 없어(`_class_name_present_in_jsx`가
빈 배열을 돌려줌) 지금 당장 걸리는 자리는 없다. 방향도 안전한 쪽(찾아야 할
이름을 못 찾으면 "사라졌다"로 보고 종료 코드 2 — 통과로 새지 않는다)이라
급하지 않다. 다만 이 정규식이 왜 중첩을 못 넘는지, 그래서 어떤 JSX 패턴이
오면 오탐(거짓 "확인 불가")이 나는지를 도크스트링에 한 줄 적어 두면 다음에
그 패턴을 실제로 쓰는 사람이 원인을 바로 알 수 있다.

**Fix:** 지금 당장 고칠 필요는 없다. `_class_name_present_in_jsx()`의
도크스트링에 "중첩된 `{}` 안에 이름이 있으면 못 찾을 수 있다(현재 소스에는
없음, 확인 완료)"를 한 줄 남겨 다음 사람이 놀라지 않게 한다.

### IN-02: README의 실패(1) 설명이 "상태 칸 25% 상한 초과" 사유를 빠뜨렸다

**File:** `README.md:40`

**Issue:** README 40번째 줄은 둘째 명령(`check_narrow_viewport.py`)의 종료
코드 1을 "서사 칸이 죽거나 골격이 넘치거나 조작부가 안 닿거나 3컬럼이
무너짐"으로 설명한다. 그런데 실제 `judge()`에는 이번 라운드(12.3-18)가 더한
여섯째 사유 — 좁은 형태에서 상태 칸이 뷰포트의 25%를 넘김 — 가 있고,
스크립트 자신의 모듈 도크스트링(`scripts/check_narrow_viewport.py:46`)에는
이미 이 사유가 적혀 있다. README만 못 따라갔다. 실험 당일 이 명령이 "1"을
찍었을 때 진행자가 README만 보고 원인을 좁히면, 상태 칸 상한 초과가 그
목록에 없어 예상 밖의 실패로 오인할 수 있다.

**Fix:** README 40번째 줄의 실패 사유 나열에 "좁은 형태에서 상태 칸이
뷰포트의 25%를 넘김"을 추가해 모듈 도크스트링과 맞춘다.
