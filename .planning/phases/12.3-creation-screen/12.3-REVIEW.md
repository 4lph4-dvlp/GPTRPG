## Summary

이번 리뷰는 12.3-09가 고치려 한 결함(「차례를 흘려보냄」 판정이 특정 지목
순번이 아니라 사람 전체에 영구히 들러붙던 CR-01)의 수정 자체는 제대로

`forfeited_nominee`의 조기 반환을 그 순번에만 걸리게 한 부분은 검증
문서가 요구한 「같은 차례는 유지, 새 차례는 처음부터」를 정확히 지킨다.

그 회복 지목과 후보 목록이 완전히 같은 상태에서 `/creation/nominate`를
한 번 더 부르면(재시도·중복 클릭·경쟁 폴링 등) 서버가 **회복 지목이
아니라 흘려보냄이 일어나기 전의 옛 지목 기록을 그대로 돌려준다** — 응답의
`seq`가 실제 최신 사건보다 낮은 값으로 되돌아가고, 실제 AI를 쓰는
환경에서는 `character_id`/`say`까지 옛 값으로 되돌아갈 수 있다. 아래
BLOCKER 항목에 이 트레이서 검증 스위트 자체로 직접 재현한 결과를 남긴다

또한 12.3-09가 새로 추가한 시험 중 하나(`forfeited_nomination_mark`의
세 경계 시험)에 의미 있는 검증력이 없는 단언이 하나 섞여 있다 — WARNING
항목 참조.

## Critical Issues

### CR-01: 회복 뒤 `/creation/nominate`를 다시 부르면 옛(흘려보내지기 전) 지목 기록이 되돌아온다

**File:** `src/gptrpg/web/creation_state.py:204-231` (`forfeited_nomination_mark`)와
`src/gptrpg/web/routes_creation.py:814-820` (중복 방지 키 조립)이 함께
만드는 결함. 근본 원인은 `src/gptrpg/rules_core/reducer.py:538-539`가
`creation_gm_said`를 `dedupe_key`로 **영구히** 보관하는 것과 맞물린다.

**재현(실제로 실행해 확인함):**

1. 참가자 셋(`pc-1`/`pc-2`/`pc-3`)이 재실 신호를 보내고 인원을 3으로
   고정, 안내를 부른다.
2. `pc-1`이 `name` 항목 값을 하나 낸다(그래서 `unfinished_candidates`
   앞줄에 선다).
3. 첫 `/creation/nominate` 호출 → `pc-1` 지목, `seq=4`로 기록된다
   (이하 예시 번호는 재현에서 실제로 관측된 값).
4. 폴링으로 `_nomination_watermark`를 처음 찍은 뒤, 시계만 되감아
   `NOMINATION_IDLE_S`를 넘긴 것으로 만든다 — `pc-1`이 차례를
   흘려보낸 것으로 판정된다(`_forfeited_at[("...", "pc-1")] = (t, 4)`).
   폴링의 `creation_current_speaker_id`가 `None`으로 바뀐다.
5. **후보 목록이 그대로인 채로**(아무도 그 사이 완성하지 않았다) 두
   번째 `/creation/nominate`를 부른다 — 이것이 12.3-09가 의도한 회복
   경로다. `forfeited_nomination_mark`가 `"#after:pc-1:4"`를 키에
   덧붙여 새 사건을 만든다 → `pc-1` 재지목, `seq=5`로 기록된다. 폴링의
   `creation_current_speaker_id`가 다시 `pc-1`로 돌아온다 — 여기까지는
   12.3-09의 시험(`test_a_forfeited_participant_who_already_submitted_
   a_value_gets_another_turn_and_unblocks_the_roster_lock`)이 확인하는
   그대로다.
6. **여기서 상태를 하나도 안 바꾸고 `/creation/nominate`를 세 번째로
   부른다.** 후보 목록이 그대로이므로(아무도 완성하지 않았다)
   `forfeited_nominee`는 이제 `None`을 돌려준다(5단계의 회복 지목이
   자기 관측 시계를 방금 새로 맞췄으므로) → `forfeited_nomination_mark`
   도 `""`로 되돌아간다 → 중복 방지 키가 **표시가 안 붙은 원래 키**로
   되돌아간다. 그런데 이 원래 키는 **3단계에서 이미 기록됐다**(리듀서가
   `dedupe_key`로 영구 보관, `reducer.py:538-539`) — 그래서 세 번째
   호출은 AI를 부르지 않고, 3단계의 **옛(흘려보내지기 전) 지목 기록**을
   그대로 돌려준다.

   실제로 관측된 값: 세 번째 호출 응답 `seq=4`, 다섯 번째 단계(회복)
   응답은 `seq=5`였다 — 세 번째 호출이 실제 최신 사건(`seq=5`)보다
   **더 오래된 사건**을 돌려준 것이다. 이 트레이서에서는 폴백 문구가
   결정론적이라 `character_id`/`say`는 우연히 같았지만, 실제 AI
   제공자를 쓰는 환경에서는 3단계와 5단계의 AI 호출이 서로 다른
   결과(다른 `character_id`, 다른 `say`)를 냈을 수 있다 — 그 경우 세
   번째 호출의 응답이 **회복되기 전 사람**을 다시 지목한 것처럼 보이는
   응답을 낸다.

**왜 12.3-09의 시험이 이걸 못 잡았는지:** 유일한 끝-끝 회복 시험
(`test_a_forfeited_participant_who_already_submitted_a_value_gets_another_
turn_and_unblocks_the_roster_lock`)에서는 회복 지목이 일어나기 전에
`pc-recover-2`가 캐릭터를 완성한다 — 이 완성이 `present_candidates`가
계산하는 후보 목록의 구성(`created_characters` 크기, 남은 자리 예산)을
바꿔서, 흘려보내지기 전 지목의 중복 방지 키와 회복 지목의 중복 방지
키가 **우연히 서로 다른 값**이 된다. 그래서 이 결함이 가려진다. 실제
운영에서는 「아무도 그 사이 완성하지 않은 채로 회복이 일어나는」 경우
(예: 셋 중 지목된 한 명만 늦고 나머지는 아직 자기 차례를 기다리는 상황,
또는 프런트가 네트워크 재시도·이중 클릭으로 `/nominate`를 한 번 더
부르는 흔한 경우)가 오히려 더 흔하다.

**근본 원인:** `forfeited_nomination_mark`(창-닫힘 표시)는 「지금
흘려보낸 상태인가」만 보고 이진 판단을 한다. 흘려보냄 판정이
`forfeited_nominee`의 관측 시계 재설정으로 풀리는 순간, 중복 방지 키가
표시 없는 원래 키로 되돌아가는데, 그 원래 키는 리듀서가 지우지 않고
영구 보관한 옛 기록을 그대로 가리킨다. 즉 이 수정은 「흘려보냄이 선
동안」에는 옳지만, 「흘려보냄이 풀린 뒤에도 후보 목록이 우연히
그대로인 상태」를 원래 상태(한 번도 안 흘려보낸 상태)와 구별하지
못한다.

**Fix (방향 제안):** 중복 방지 키가 「지금 흘려보낸 상태인가」가 아니라
「이 나열 순서로 마지막까지 기록된 지목 사건이 무엇인가」를 반영하게
한다 — 가장 단순한 결은 `_gm_dedupe_key("nominate", ...)`가 후보 목록
문자열에 더해 `latest_nomination(state)`의 순번(있으면)을 **항상**
포함시키는 것이다:

```python
# creation_state.py, forfeited_nomination_mark 대신/함께
def nominate_dedupe_suffix(state: GameState, session_id: str) -> str:
    """흘려보냄 여부와 무관하게, 지금까지 기록된 마지막 지목 사건
    자체를 키에 새긴다 — 그래야 흘려보냄이 풀린 뒤에도 회복 지목이
    남긴 사건이 그보다 앞선 옛 사건과 같은 키로 뭉치지 않는다."""
    nomination = latest_nomination(state)
    if nomination is None:
        return ""
    _, nominated_seq = nomination
    return f"#seq:{nominated_seq}"
```

이렇게 하면 3단계(seq=4)와 5단계(seq=5, 회복)의 키가 처음부터 다른
값이 되어, 3번째 호출이 「후보 목록만 같으면 무조건 옛 키로 되돌아가는」
경로를 아예 안 밟는다. `forfeited_nomination_mark`를 완전히 대체하지
않아도(그 함수가 지금 나르는 `"#after:{nominee}:{nominated_seq}"`
문자열 안에 이미 `nominated_seq`가 있으므로), **핵심은 이 표시를
「흘려보낸 동안만」이 아니라 「지목 사건이 하나라도 기록된 뒤로는
항상」 붙이는 것**이다 — 즉 `if forfeited_nominee(...) is None: return
""` 조기 반환을 지우고 지목이 있으면 늘 `f"#seq:{nominated_seq}"`류
표시를 붙이도록 바꾼다.

## Warnings

### WR-01: `forfeited_nomination_mark` 경계 시험의 단언 하나가 실제로는 검증력이 없다

**File:** `tests/test_creation_screen_state.py:680`

**Issue:** `test_a_forfeited_nomination_changes_the_dedupe_mark_but_a_
healthy_one_leaves_it_untouched`에서

```python
assert mark != ""
assert "pc-mark-1" in mark          # 679
assert "1" in mark                  # 680 — 의도: nominated_seq(=1)가 표시에 실렸는지 확인
```

`mark`는 `"#after:pc-mark-1:1"` 모양이다. 679번 줄이 이미
`"pc-mark-1"`이 들어 있는지 확인하는데, 그 문자열 자체에 `"1"`이
포함돼 있다(`pc-mark-1`의 `-1`) — 그래서 680번 줄의 `assert "1" in
mark`는 `nominated_seq`가 표시에 실제로 실렸는지와 무관하게, 심지어
`forfeited_nomination_mark`가 순번을 아예 안 붙이거나 틀린 순번을
붙여도 `"pc-mark-1"`이라는 글자만으로 통과한다. 즉 이 줄은 순번이
표시에 실제로 실리는지를 못 잡는 시험이다.

**Fix:**

```python
assert mark == "#after:pc-mark-1:1"
```

처럼 표시 전체 모양을 정확히 못박거나, 최소한

```python
assert mark.endswith(":1")
```

로 바꿔 `nominated_seq` 부분을 캐릭터 식별자와 분리해서 검증한다.
