직접 확인했다. WR-02도 `onChange`/`disabled` 두 자리가 실제로 값을
1 미만으로 못 내려가게 막는 것을 확인해 **닫힘으로 처리한다**.

이번 라운드가 새로 잡은 것은 `scripts/check_insecure_origin.py` — 이
계획의 진짜 산출물이자 프롬프트가 최우선으로 지목한 파일이다. 이 스크립트가

확인하지 않는다.** 포트가 이미 다른 프로세스에 점유돼 있으면(가장 흔한
경로: 이전 실행이 비정상 종료해 좀비로 남은 자기 자신의 이전 인스턴스),

검사를 계속 진행하고, 그 낡은 서버가 마침 정상 화면을 서빙하고 있으면
**지금 코드가 아니라 옛 코드를 확인해 놓고 종료 코드 0(통과)을 낸다.**
이것이 정확히 이 스크립트가 막으려던 바로 그 모양의 침묵이라 BLOCKER로
분류했다. 그 밖에 예외 처리 누락 두 건과 사소한 품질 항목 둘을 함께
적는다.

## Critical Issues

### CR-01: `check_insecure_origin.py`가 자신이 띄운 서버 프로세스의 생존을 확인하지 않아, 포트가 이미 다른 프로세스에 점유돼 있으면 무관한/낡은 서버를 검사하고도 통과(exit 0)를 낼 수 있다

**상태: 닫힘 (커밋 `afaba1c`).** 고치기 전에 이 시나리오를 실제로 재현했다 — 포트 8973에 uvicorn을 따로 띄워 두고 스크립트를 돌리자 자기 서버가 죽은 채로 `EXIT=0`(「통과」)을 찍었다. 처방은 두 겹이다: (1) 시작 전 `port_is_free()`가 실제로 bind해 보고 선점돼 있으면 종료 코드 2로 끝낸다 — 경합 자체를 없애는 근본 차단이다. (2) `wait_for_server`가 매 회전마다 `proc.poll()`로 띄운 프로세스의 생사를 확인한다 — 선점 검사와 spawn 사이의 경합에 대비한 이중 안전장치. 서버가 죽은 경우와 시간 초과를 구분해 알리고, 죽은 경우 서버가 남긴 출력을 함께 보여 준다. 재현 조건에서 `EXIT=2` 확인.

**File:** `scripts/check_insecure_origin.py:222-296` (`main`의 서버 기동·대기 구간)

**Issue:** `server_proc = subprocess.Popen([... "uvicorn", ...])`로 서버를
띄운 뒤, 이 프로세스가 실제로 살아서 그 포트를 잡았는지는 한 번도 검사하지
않는다. `wait_for_server(host, args.port, STARTUP_TIMEOUT_S)`는 오직
`http://{host}:{port}/`에 `urlopen`이 200을 주는지만 본다(118-131행). 만약
그 포트(기본 8973)에 **이미 다른 프로세스가 떠 있다면** — 가장 현실적인
경로는 이 스크립트의 이전 실행이 `SIGKILL`이나 강제 종료로 `finally`
(288-294행)를 못 거치고 죽어 좀비 `uvicorn`이 남은 경우다 — 새로 `Popen`한
`uvicorn`은 `Address already in use`로 즉시 죽지만, `wait_for_server`는
포트에 응답하는 **그 낡은/무관한 프로세스**를 "서버가 떴다"로 오인해 다음
단계로 넘어간다. 그 낡은 서버가 (고쳐지기 전이든 후든) 정상 렌더되는
화면을 물려 갖고 있으면, `dump_dom`이 그 서버를 열어 `캐릭터 만들기`를
찾고 **종료 코드 0을 낸다** — 정작 지금 작업 디렉터리의 소스는 한 번도
열어 본 적이 없는데도. 이 계획서 자신이 정의한 계약("확인 못 한 것과
통과를 절대 안 섞는다", `<threat_model>` T-12.3-44)이 정확히 막으려던
경로가 이 자리 하나만 빠져 있다.

`try/finally`(288-294행)로 스크립트가 정상 종료하거나 예외로 끝날 때는
자기 프로세스를 확실히 정리하므로 이 경로가 자주 일어나지는 않는다 —
그러나 `SIGKILL`/전원 손실/컨테이너 강제 종료, 또는 같은 스크립트를
두 터미널에서 동시에 실행하는 실수처럼 흔히 일어나는 운영 실수로도
같은 포트 충돌이 재현된다. `Popen`의 반환값(자식 프로세스가 실제로
살아 있는지)을 한 번도 확인하지 않는 것이 근본 원인이다.

**Fix:** 대기 루프 안에서 `server_proc.poll()`이 `None`이 아니게 되면
(=자식이 이미 죽었으면) 그 즉시 "이 프로세스가 아닌 다른 무언가에
응답했을 수 있다"로 종료 코드 2를 내도록 명시적으로 거절한다. 완전한
안전장치는 아니지만(포트가 정상 바인딩된 뒤에도 다른 프로세스로 갈아
치워지는 극단적 경합까지는 못 막는다), 가장 흔한 경로(자식이 바인딩
실패로 즉시 죽는 경우)를 확실히 잡는다:

```python
def wait_for_server(host: str, port: int, timeout_s: float, proc: subprocess.Popen) -> bool:
    import time

    deadline = time.monotonic() + timeout_s
    url = f"http://{host}:{port}/"
    while time.monotonic() < deadline:
        if proc.poll() is not None:
            # 자식이 이미 죽었다 — 이후 200 응답은 이 프로세스가 아닌
            # 다른(무관하거나 낡은) 프로세스가 같은 포트에서 준 것일 수
            # 있다. 통과로 이어지게 두지 않는다.
            print(
                f"띄운 uvicorn(pid={proc.pid})이 시작 중에 죽었다(returncode="
                f"{proc.returncode}). 포트 {port}가 이미 다른 프로세스에 "
                "점유돼 있을 수 있다. 종료 코드 2.",
                file=sys.stderr,
            )
            return False
        try:
            with urllib.request.urlopen(url, timeout=1) as resp:
                if resp.status == 200:
                    return True
        except (urllib.error.URLError, ConnectionError, TimeoutError, OSError):
            pass
        time.sleep(0.5)
    return False
```

그리고 호출부(240행)를 `wait_for_server(host, args.port, STARTUP_TIMEOUT_S, server_proc)`로 바꾼다.

### WR-03: `build_frontend`/`dump_dom`이 잡지 않는 예외(`npm`/크로미움 실행 파일이 사라진 경우)가 나면 계약이 정한 "확인 불가"(2)가 아니라 파이썬 기본 종료 코드 1로 떨어져, "확인 불가"가 "확인해서 실패"로 오분류될 수 있다

**상태: 닫힘 (커밋 `afaba1c`).** `build_frontend`는 `OSError`를 잡아 `False`(→ 종료 코드 2)로, `dump_dom`은 `OSError`를 잡아 `None`(→ 종료 코드 2)으로 접는다. 파이썬 기본 종료 코드 1로 새어 나가 「확인해 봤더니 실패」와 섞이던 경로가 사라졌다.

**File:** `scripts/check_insecure_origin.py:97-115` (`build_frontend`), `134-162` (`dump_dom`)

**Issue:** 이 스크립트의 종료 코드 계약은 `2`를 "확인 자체를 못 함"으로,
`1`을 "확인했는데 화면이 안 뜸"으로 엄격히 가른다(모듈 docstring 19-29행).
그런데 `build_frontend()`의 `subprocess.run(["npm", "run", "build"], ...)`와
`dump_dom()`의 `subprocess.run([chromium, ...], ...)`는 자식 프로세스가
**비정상 종료 코드로 끝나는 경우**(`result.returncode != 0`)만 처리하고,
**실행 파일 자체를 못 찾는 경우**(`FileNotFoundError`)나 권한 문제
(`PermissionError`)는 아무 데도 안 잡는다. 이 예외가 나면 파이썬이 처리
안 된 예외로 트레이스백을 찍고 **기본 종료 코드 1**로 끝난다 — 계약상
"화면이 확인됐는데 안 떴다"는 뜻인 바로 그 코드다. `find_chromium()`이
사전에 `shutil.which`로 존재를 확인하므로 크로미움 쪽은 위험이 낮지만,
`build_frontend()`는 `npm`의 존재를 사전에 확인하지 않는다 — `.venv`는
있는데 Node/`npm`이 PATH에 없는 환경(예: 파이썬만 있는 CI 러너, 또는
`nvm`을 새 셸에서 안 연 경우)에서 이 스크립트를 돌리면 "빌드 도구가
없어 확인 못 함"이 아니라 겉보기에 "화면이 확인됐는데 안 떴다"로 잘못
읽힌다.

**Fix:**

```python
try:
    result = subprocess.run(["npm", "run", "build"], cwd=REPO_ROOT / "frontend", capture_output=True, text=True)
except OSError as exc:
    print(f"'npm'을 실행할 수 없다({exc}) — 이 확인을 계속할 수 없다. 종료 코드 2.", file=sys.stderr)
    return False
```
`dump_dom`도 같은 방식으로 `subprocess.run([chromium, ...])` 호출을
`try/except OSError`로 감싸 `None`을 돌려주게 한다(이미 있는
`probe_dom is None or control_dom is None` 검사가 자동으로 종료 코드 2로
보낸다).

### WR-04: 대조군(loopback)이 실패하면 본 검사(non-loopback) 결과와 무관하게 항상 실패(1)로 확정한다 — 대조군이 어떤 이유로든 흔들리면 실제로 통과한 성질을 실패로 보고할 수 있다

**상태: 닫힘 (커밋 `afaba1c`).** 대조군 실패는 `return 1`이 아니라 `return 2`다 — 검사한 적 없는 성질을 실패로 단정하지 않는다.

**File:** `scripts/check_insecure_origin.py:258-287`

**Issue:** `control_ok`(loopback)이 거짓이면 `probe_ok`(본 검사, 실제로
확인하려는 성질)의 값을 아예 안 보고 곧바로 `return 1`한다(266-275행).
수리가 끝난 오늘 코드에서는 두 주소가 같은 정적 파일을 서빙하므로 정상
상황에서는 둘의 결과가 갈릴 이유가 없지만, 크로미움 헤드리스 호출 하나가
일시적으로 흔들리는 것(타임아웃 문턱, 가상 시간 예산 8초를 살짝 넘기는
것 등)은 원리적으로 배제할 수 없다. 그런 경우 `dump_dom(control_url)`
하나만 우연히 실패하고 `probe_dom`(진짜 확인하려는 자리)은 정상으로
`캐릭터 만들기`를 찾았어도, 이 코드는 그 사실을 무시하고 "대조군이
실패했으니 서버·빌드가 통째로 망가진 것"이라는 문구와 함께 종료 코드
1을 낸다 — 정작 이번 계획이 고치려는 그 성질(비-루프백 주소에서 화면이
뜨는가)은 확인됐는데도 실패로 보고되는 것이다. 이것은 (이번 계획이
가장 경계하는) "확인 못 한 것이 통과로 보이는" 방향의 반대지만, 같은
계열의 결함이다 — **판정 로직이 실제로 관측한 값(`probe_ok`)보다 진단
편의를 우선한다.**

**Fix:** `control_ok`이 거짓이고 `probe_ok`도 거짓이면 지금처럼 "서버·빌드가
통째로 망가졌다" 문구로 실패(1) 처리하되, `control_ok`이 거짓인데
`probe_ok`가 참이면 별도 문구("대조군만 흔들렸고 본 검사는 통과했다 —
재실행해서 재현되는지 볼 것")와 함께 **종료 코드 2**(확인 불가, 재시도
필요)로 분리한다:

```python
if not control_ok and not probe_ok:
    print("대조군(127.0.0.1)조차 실패했다 — ...", file=sys.stderr)
    print(extract_app_div(control_dom), file=sys.stderr)
    return 1
if not control_ok and probe_ok:
    print(
        "대조군만 실패하고 본 검사(비-루프백)는 통과했다 — 크로미움 호출이 "
        "일시적으로 흔들렸을 수 있다. 재실행해서 재현되는지 볼 것. 종료 코드 2.",
        file=sys.stderr,
    )
    sys.exit(2)
```

### IN-02: `--host`로 IPv6 루프백(`::1`)이나 `0.0.0.0`을 주면 "루프백"으로 안 걸러진다

**상태: 닫힘 (커밋 `afaba1c`).** `::1`·`localhost`·`0.0.0.0`·빈 문자열을 전부 루프백으로 거절한다. 네 이름 모두 종료 코드 2를 확인했다.

**File:** `scripts/check_insecure_origin.py:70-73` (`find_non_loopback_ipv4`)

**Issue:** 명시적 `--host`가 주어졌을 때의 검사는 `explicit_host.startswith("127.")`
하나뿐이다. `--host ::1`(IPv6 루프백)이나 `--host 0.0.0.0`(모든 인터페이스
바인드 주소, 클라이언트가 접속할 대상 주소로는 의미가 없다)을 주면 걸러지지
않고 통과해, 이후 IPv4 전용으로 짠 URL 조립(`http://{host}:{port}/`)이나
소켓 코드와 안 맞는 값으로 진행된다. 실제로는 이후 단계(서버 연결 시도)에서
실패해 결국 종료 코드 2로 끝날 가능성이 높아 통과(0)로 새는 경로는 아니지만,
"루프백을 스스로 거절한다"는 이 스크립트의 명시적 성질이 IPv4 표기 하나만
알아본다는 점은 적어 둘 가치가 있다.

**Fix:** `explicit_host in ("::1", "0.0.0.0", "localhost")`도 함께 걸러
같은 문구로 거절한다.
