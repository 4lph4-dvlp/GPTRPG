## Summary

이번 리뷰는 이전 `12.3-REVIEW.md`가 남긴 CR-01(회복 뒤 옛 지목 재사용)과
WR-01(경계 시험 단언 하나가 검증력이 없던 문제)이 plan `12.3-10`에서 실제로
닫혔는지부터 직접 확인했다. 두 건 다 코드를 추적하고, 관련 회귀 시험
(`test_a_third_nominate_call_after_recovery_returns_the_latest_nomination_not_the_pre_forfeit_one`,
`test_a_forfeited_nomination_changes_the_dedupe_mark_but_a_healthy_one_leaves_it_untouched`)을
직접 돌려 통과를 재현했다 — **두 건 모두 닫힌 것으로 확인했다.**

`forfeited_nomination_mark`는 "지금 흘려보낸 상태인가"(이진, 회복되면 뒤로
돌아감)에서 "이 세션에서 마지막으로 판정된 흘려보냄이 무엇인가"(단조, 앞으로만
감)로 재정의됐다. `_forfeited_at`을 절대 지우지 않고 세션 안의 모든 항목 중
적용 대상 지목 순번(`applied_seq`)이 가장 큰 것 하나로 표시를 조립하는 방식이,
회복 뒤 표시가 원래 키로 되돌아가 리듀서가 영구 보관한 옛 지목 기록을 다시
꺼내 주던 근본 원인을 실제로 제거한다 — `nominated_seq`가 사건 순번에서
나와 세션 안에서 항상 단조 증가한다는 전제 위에서, "마지막으로 판정된
흘려보냄"이 곧 시간순으로도 마지막이라는 등식이 성립한다. 13개 관련 시험
(`forfeit`/`stale`/`recovery`/`nominat` 키워드)과 phase 전체 시험
(`test_creation_screen_state.py`/`test_creation_consent_host.py`/
`test_creation_screen_tracer.py`/`test_event_schema_migration.py`, 92건)을
직접 재실행해 전부 통과를 확인했다.

이번 리뷰가 새로 잡은 것은 파이썬 쪽 상태 기계가 아니라 **프런트엔드
`CreationPane.tsx`/`CreationScreen.tsx`의 두 UX 결함**이다. 둘 다 서버가
스스로를 보호하므로 데이터 손상이나 보안 문제는 아니지만, 사람이 정상적인
조작을 하다가 이해할 수 없는 오류 문구를 만나는 실제 결함이다. `tsc
--noEmit`·`ruff check`·`vitest run`(80건)·관련 파이썬 시험은 전부 초록이다.

## Warnings

### WR-01: 끼어들기 입력이 "지금 아무도 말하지 않을 때"와 "내 차례일 때" 항상 자기 자신을 대상으로 보내 서버에 거절당한다

**File:** `frontend/src/panes/CreationPane.tsx:802`

**Issue:** `InterjectBox`에 넘기는 `duringCharacterId`가
`state.creation_current_speaker_id ?? myCharacterId`로 계산된다. 이 끼어들기
입력창은 "남의 차례에도 항상 열려 있다"(D-08)는 설계대로 `myTurn` 여부와
무관하게 항상 렌더된다(636~805행, 조건부 렌더 아님). 그런데 폴백값이
`myCharacterId`이므로:

- `creation_current_speaker_id`가 `null`인 동안(예: 지목된 사람이 방금 차례를
  흘려보내 판정이 풀렸지만 다음 지목이 아직 안 온 사이, 혹은 재지목 대기창) —
  대상이 나 자신이 된다.
- 지금이 실제로 **내 차례**여도(`creation_current_speaker_id === myCharacterId`)
  — 대상이 여전히 나 자신이 된다.

두 경우 다 서버(`session_actor/actor.py::_prepare_interjection`)가
`command.speaker_character_id == command.during_character_id`를 보고
`CommandRejected("자기 차례에는 끼어드는 것이 아니라 말하는 것이다")`로
거절한다(409). 아직 항목을 하나도 낸 적 없는 새 참가자가 이 상태에서
시도하면 `during_character_id`가 `known_character_ids`(완성됐거나 항목을
하나라도 낸 사람)에도 없어 400("이 세션에 없는 캐릭터의 차례를 가리켰다")이
난다. 화면은 `creationErrorMessage`로 서버의 이 문구를 그대로 보여주는데
(`session/creationView.ts:63-73`, D-15), 사용자 입장에서는 "그냥 아무 데도
안 끼어든 방금 한 말"에 뜬금없는 거절 사유가 붙어 보인다 — 실제 결함(값이
잘못 실렸다)을 오류 메시지가 가린다.

**Fix:** "지금 남의 차례"일 때만 대상을 확정하고, 아닐 때는 끼어들기 조작
자체를 비활성화하거나 안내로 대체한다:

```tsx
// CreationPane.tsx
const otherSpeakerId =
  state.creation_current_speaker_id !== null && state.creation_current_speaker_id !== myCharacterId
    ? state.creation_current_speaker_id
    : null;

{otherSpeakerId !== null ? (
  <InterjectBox
    sessionId={sessionId}
    browserId={browserId}
    myCharacterId={myCharacterId}
    duringCharacterId={otherSpeakerId}
    pollNow={pollNow}
    onError={setError}
  />
) : null}
```

### WR-02: 인원 확정 입력에 최소값 검사가 없어 "0명"을 보내면 무슨 문제인지 안 보이는 문구로 떨어진다

**File:** `frontend/src/screens/CreationScreen.tsx:89-124` (`PartySizeControl`)

**Issue:** `<input type="number" min={1} ...>`의 `min` 속성은 스피너 버튼만
막을 뿐, 사람이 값을 지우거나(`Number("")` → `0`) 마이너스 부호를 직접
입력하는 것은 그대로 통과시킨다. `count`가 갱신될 때도, 확정 버튼
(114~121행)의 `disabled` 조건도 `busy`만 보고 `count`의 값 자체는 전혀
검사하지 않는다 — 같은 파일의 다른 조작(`AllocatePointsControl`이
`Number.isNaN(next) ? 0 : next`로 최소한 `NaN`은 막는 것)과도 결이 다르다.
`count=0`으로 `fixPartySize`를 부르면 서버(`FixPartySizeRequest.
player_character_count: int = Field(ge=1)`)가 라우트 핸들러에 닿기도 전에
FastAPI 자체 검증에서 422로 막는데, 이때 응답 본문의 `detail`은 문자열이
아니라 pydantic 오류 객체 배열이다. `postJsonWithDetail`(`api/client.ts:81-101`)
은 `typeof errorBody.detail === "string"`일 때만 그 문구를 쓰므로 이 경우
`detail`이 `undefined`가 되고, `creationErrorMessage`가 `COPY.creationFailed`
("만들기 요청을 처리하지 못했어요")라는 원인을 알 수 없는 문구로 떨어진다 —
서버가 이미 "인원은 1명 이상이어야 한다"는 정확한 이유를 갖고 있는데도 화면이
그것을 사람에게 전달하지 못한다.

**Fix:** 최소값을 화면에서도 강제해 애초에 잘못된 값을 보내지 않게 한다:

```tsx
const clamped = Math.max(1, count);
// ...
<button
  type="button"
  className="btn btn--primary btn--wide"
  disabled={busy || count < 1}
  onClick={() => void confirm()}
>
```

또는 최소한 `onChange`에서 `Math.max(1, Number(event.target.value) || 1)`로
저장 값 자체를 1 미만으로 못 내려가게 한다.
