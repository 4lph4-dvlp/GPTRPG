## 요약

이번 라운드의 핵심 산출물은 `scripts/check_narrow_viewport.py`다. 이것은
**시험 그물(test gate)**이고, 그물의 값어치는 「깨진 화면에서 빨강을 낸다」
하나뿐이다. 그래서 읽는 데서 멈추지 않고 **직접 돌려 봤다** — 현재 코드,

결과는 이렇다. 옛 CSS에서는 그물이 제대로 빨강을 낸다(서사 0px 세 형태 →

**원리적으로 절대 실패할 수 없는 단언**이다(CR-01). 즉 CSS 주석이
"check_narrow_viewport.py가 문서 넘침을 같이 재서 이 처방을 거절한다"고 적은
바로 그 보호가 존재하지 않는다.

더 나쁜 것은 오늘 CSS 자체에 있다. 고정판에는 없지만 실제 `.pane--chat`에는
있는 `.chat__head` · `.chat` · `.composer` · `.proposal`을 실제 마크업대로

안 된다 — 플레이어가 제안에 답을 못 한다(CR-02). 그물은 이 형태를 「통과」로
찍는다. 고정판이 대화 칸의 조작부를 통째로 안 담고, 드리프트 감시 목록

정리하면 12.3-15는 「서사 칸 0px」이라는 진짜 결함을 실제로 닫았고

## Critical Issues

### CR-01: 넘침 단언(②)이 원리적으로 절대 실패할 수 없다 — 그물이 자기가 막겠다는 함정을 통과시킨다

**File:** `scripts/check_narrow_viewport.py:217`, `scripts/check_narrow_viewport.py:318-324`
**Issue:**
`judge()`의 단언 ②는 `doc.documentElement.scrollHeight`를 뷰포트 높이와
비교한다. 그런데 `frontend/src/styles.css:146-150`의 `.shell`은
`height: 100dvh; overflow: hidden`이다. 자식이 아무리 넘쳐도 `.shell`이
잘라 버리므로 `documentElement.scrollHeight`는 **항상 정확히 뷰포트 높이**가
된다. 실측으로도 네 형태 · CSS 세 판본 전부에서 `scrollHeight == innerHeight`였다
(900/1080/844/390 그대로).

실제로 CSS 주석(`frontend/src/styles.css:184-189`)이 "이 그물이 거절한다"고
이름 붙인 함정 처방을 얹어 돌려 봤다:

```
# grid-template-rows: auto minmax(240px, 1fr) minmax(240px, 40dvh)
844x390 · 상태 33.0px · 서사 240.0px · 대화 240.0px · 문서높이 390.0px · 통과
```

세 행의 합이 513px인데 뷰포트는 390px다. 골격이 123px 넘쳤는데도 **통과**다.
넘침 단언은 한 번도 발화하지 않았다. 「확인을 못 한 것이 통과로 보이는 것」을
막으려고 만든 스크립트가, 정작 자기 단언 하나를 장식으로 달고 있다.

**Fix:** 문서가 아니라 **골격 자신의 넘침**을 재야 한다. `.shell`은 스크롤을
안 만들지만 `scrollHeight`/`clientHeight`는 잘린 내용을 그대로 보고한다.
세 칸의 아래끝을 뷰포트와 직접 비교하는 편이 더 직관적이다.

```js
// build_host_html의 measure() 안
var shellEl = doc.querySelector(".shell");
results.push({
  // ...
  shellScrollHeight: shellEl.scrollHeight,
  shellClientHeight: shellEl.clientHeight,
  chatBottom: chatEl.getBoundingClientRect().bottom,
});
```

```python
# judge() 단언 ②
if measurement["shellScrollHeight"] > measurement["shellClientHeight"] + OVERFLOW_TOLERANCE_PX:
    reasons.append(
        f"골격 내용({measurement['shellScrollHeight']:.1f}px)이 골격 상자"
        f"({measurement['shellClientHeight']:.1f}px)를 넘어 잘렸다"
    )
if measurement["chatBottom"] > viewport_height + OVERFLOW_TOLERANCE_PX:
    reasons.append(
        f"대화 칸 아래끝({measurement['chatBottom']:.1f}px)이 화면 밖"
        f"({viewport_height}px)으로 나갔다"
    )
```

고친 뒤 위 함정 CSS로 다시 돌려 844×390이 **실패(1)**로 바뀌는지 확인할 것 —
그게 이 단언이 살아 있다는 유일한 증거다.

### WR-01: `iframe.onload`가 `about:blank`에서 한 번 더 불린다 — 지금은 잡히지 않은 TypeError 덕분에 우연히 넘어간다

**File:** `scripts/check_narrow_viewport.py:198-225`
**Issue:**
`iframe.onload`를 `appendChild` **전에** 붙이고 `srcdoc`을 **뒤에** 준다.
크로미움은 삽입 시점의 초기 `about:blank` 항해에 대해 `load`를 한 번 더
발화한다 — 실측으로 확인했다(형태마다 `about:blank` → `about:srcdoc` 두 번).

지금 이 코드가 살아남는 유일한 이유는 `about:blank` 회차에서
`statusEl`이 `null`이라 `statusEl.getBoundingClientRect()`가 **TypeError를
던져 핸들러가 중단되기 때문**이다. 즉 「잡히지 않은 예외」가 사실상 제어
흐름 노릇을 하고 있다. 누군가 "견고하게 만들자"며 null 가드를 넣으면
그물이 `about:blank`를 재고 `done()`을 불러 **빈 문서의 값으로 판정**하게
된다.

**Fix:** 의도를 코드로 적는다. srcdoc 문서인지 확인하고, 아니면 `done()`을
**부르지 않고** 그냥 돌아간다(진짜 로드가 곧 다시 온다).

```js
iframe.onload = function () {
  var doc = iframe.contentDocument;
  // 삽입 직후의 about:blank 로드가 한 번 먼저 온다 — 그 회차는 그냥 흘린다
  // (여기서 done()을 부르면 빈 문서를 재고 다음 형태로 넘어간다).
  if (!doc || !doc.querySelector(".shell")) { return; }
  // …이하 측정
};
```

### WR-03: 44px 단언이 잘려서 아예 안 보이는 조작 칸도 통과시킨다

**File:** `scripts/check_narrow_viewport.py:329-338`
**Issue:**
`getBoundingClientRect().height`는 조상이 `overflow: hidden`으로 잘라 버려
화면에 한 픽셀도 안 보이는 요소도 원래 크기를 그대로 보고한다. 함정 CSS
실측에서 844×390의 상태 칸이 33px로 짓눌렸는데도 그 안의 44px `select`가
**통과**했다. 「손가락으로 누를 수 있다」를 확인하겠다는 단언이 「누를 수
없는 것」을 통과시킨다.

### WR-07: CSS 주석의 「3행 바닥을 0으로 내려 콘텐츠가 없을 때는 안 가져가게 한다」가 사실과 다르다

**File:** `frontend/src/styles.css:181-183`
**Issue:**
주석은 대화 행이 내용이 없으면 높이를 안 가져간다고 설명한다. 그러나
`minmax(0, 40dvh)`는 최대값이 확정값이라 그리드의 "Maximize Tracks" 단계에서
**내용과 무관하게 40dvh까지 자란다.** 실측: 짧은 대화 두 줄뿐인 고정판에서
대화 행이 정확히 40dvh였다(390×844 → 337.6px, 844×390 → 156px, 960×1080 →
432px).

주석의 결론(서사가 35dvh를 받는다)은 **맞다.** 다만 그 근거로 적힌 기전이
틀렸고, 서사 35dvh 보장은 오히려 「대화 행이 항상 40dvh를 가져간다」에
의존한다. 이 파일의 주석은 길고 사람이 실제로 근거로 삼기 때문에, 틀린
전제를 남겨 두면 다음 사람이 "내용이 없으면 안 가져간다니 바닥을 다시
올려도 되겠다"로 잘못 추론한다.

**Fix:** 주석에서 해당 문장을 사실대로 고친다.

```
3행은 `minmax(0, 40dvh)`라 내용과 무관하게 정확히 40dvh를 가져간다(그리드가
확정 최대값까지 먼저 채운 뒤 남은 것을 1fr에 준다). 바닥을 0으로 내린 이유는
「안 가져가게」가 아니라, 40dvh보다 화면이 짧을 때 240px 바닥이 골격을
터뜨리는 것을 막기 위해서다. 그래서 2행(서사)은 100 - 25 - 40 = 35dvh를 받는다.
```
