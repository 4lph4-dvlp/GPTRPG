## Summary

이번 검토는 캐릭터 만들기 화면(브라우저 구동) 줄기를 대상으로 한다. 이벤트 스키마
판 11(세 가지 신설 사건: `creation_gm_spoke` · `creation_consent_recorded` ·
`creation_host_claimed`)과 그에 대응하는 리듀서 분기, 방장 승계 로직, 프런트엔드
와이어링을 집중적으로 봤다.

리듀서(`apply_event`)의 세 신설 분기, `EVENT_SCHEMA_VERSION` 11 못박기, 옛 판 하위
호환 처리는 모두 정확하다 — 설계 의도(동의·재오픈을 한 사건으로 묶기, 방장 승계를
비교 후 교체로 처리하기 등)와 실제 코드가 일치한다.

하지만 **프런트엔드 와이어링에 캐릭터 만들기 진행 자체를 막는 결함이 있고**,
**방장 신원 비공개라는 명시적 보안 설계(T-12.3-05)가 사건 스트림을 통해 실제로는
새고 있으며**, **`dedupe_key`가 문서가 약속하는 "AI를 다시 안 부른다"는 보장을
동시 요청 아래에서는 지키지 못한다.** 이 셋 다 검토 지시가 명시적으로 짚은
초점 영역과 정확히 겹친다. 아래 Critical Issues에 넷을 적었다 — 이 상태로는
CHAR-06(캐릭터 만들기가 브라우저에서 끝까지 되는가)이 성립하지 않는다.

### CR-01: 아무도 지목되지 않아 항목 확정 화면이 영원히 안 열린다

**File:** `frontend/src/panes/CreationPane.tsx:432,440` (근거: `frontend/src/session/creationView.ts:80-82`, `src/gptrpg/web/routes_creation.py:753-822`, `frontend/src/api/client.ts:227-235`)

**Issue:**
`CreationPane`의 항목 확정 UI(줄 목록·`StepControl`·되묻기 관문)는 전부
`stepEditingEnabled = myTurn || myReopenedRow !== null` 하나로 감싸여 있다
(`CreationPane.tsx:440`, 렌더는 608행). `myTurn`은 `isMyTurn(state, myCharacterId)`이고,
이 값은 오직 `state.creation_current_speaker_id === myCharacterId`로만 참이 된다
(`creationView.ts:80-82`). `creation_current_speaker_id`는 서버가 `kind: "nominate"`인
`creation_gm_spoke` 사건 중 가장 최근 것의 `target_character_id`로만 채운다
(`routes_events.py:182-195`) — 그리고 그 사건을 만드는 유일한 경로는
`POST /creation/nominate`(`routes_creation.py:753-822`, `nominate_creation_speaker`)다.

프런트엔드 쪽에서 이 경로를 부르는 함수 `nominateCreationSpeaker`가
`frontend/src/api/client.ts:227-235`에 선언돼 있지만, `grep -rn nominateCreationSpeaker
frontend/src`로 확인한 결과 **정의 자리 말고는 어디에서도 import되거나 호출되지
않는다** — `CreationScreen.tsx`도 `CreationPane.tsx`도 이 함수를 부르지 않는다.

결과: `creation_current_speaker_id`가 이 세션 안에서 영원히 `null`로 남고,
`myReopenedRow`도 첫 캐릭터가 완성되기 전에는 항상 `null`이므로(다시 열림은 동의
관문을 거쳐야만 생긴다), `stepEditingEnabled`가 참이 될 방법이 구조적으로 없다.
누구도 `CompleteCreationStep`을 제출할 UI를 볼 수 없다 — 캐릭터 만들기 화면의
핵심 조작(항목 채우기)이 실 사용자 경로에서 절대 열리지 않는다.

`tests/test_creation_screen_state.py`의 `test_nominate_*` 시험들은 `/creation/nominate`를
**직접 HTTP로** 호출해 백엔드 동작만 확인한다 — 프런트엔드가 실제로 이 경로를
부르는지는 어느 시험도 확인하지 않는다(이 저장소는 RTL을 쓰지 않고 순수 함수만
시험하므로 이런 배선 누락을 잡을 시험 자리가 애초에 없다).

**Fix:**
`CreationScreen.tsx` 또는 `CreationPane.tsx`에 `nominateCreationSpeaker` 호출을
배선한다 — 예를 들어 대화 줄기가 비어 있고(`gmLines`에 `nominate` 종류가 없고)
아직 완성 안 된 후보가 있으면 자동으로 부르거나, 방장에게 "다음 사람 지목" 버튼을
보인다. 배선한 뒤 `frontend/tests`가 아니라 실제 두 브라우저 수동 확인
(12.3-05-SUMMARY.md §사람 확인이 필요합니다, CHAR-06)으로 처음부터 끝까지 항목이
채워지는지 반드시 재확인해야 한다.

### CR-02: 「안내」 버튼이 정작 필요한 순간 사라진다

**File:** `frontend/src/screens/CreationScreen.tsx:325-329`

**Issue:**
```tsx
{gate === "done" && !stepsLoaded ? (
  <button type="button" disabled={pending} onClick={() => void announce()}>
    {COPY.creationAnnounce}
  </button>
) : null}
```
안내(`announceCreation`) 버튼은 `gate === "done" && !stepsLoaded`일 때만 보인다.
그런데 `CreationPane`은 정확히 그 반대 조건(`stepsLoaded === true`)일 때만
렌더된다(261~318행의 삼항식). `fetchCreationSteps`는 AI를 부르지 않는 단순 조회라
보통 안내를 실제로 눌러 보기도 전에 이미 완료되어 `stepsLoaded`가 `true`로
바뀐다 — 그 순간 버튼이 사라지고 `CreationPane`이 대신 그려지는데,
`CreationPane`은 어디에서도 `announceCreation`을 부르지 않는다(파일 전체에
import가 없다). 안내가 아직 한 번도 안 된 세션에서는 `conversation.length === 0`

CR-01(지목 배선 누락)과 별개의, 같은 화면의 또 다른 진행 차단 지점이다 — 둘 다

**Fix:**
버튼 조건을 반전하거나(`gate === "done" && gmLines.length === 0`), `CreationPane`
쪽에 안내가 아직 없을 때 자동으로 `announceCreation`을 부르는 effect를 추가한다.
어느 쪽이든 "안내가 없다"는 조건으로 트리거해야지 `stepsLoaded` 여부로 트리거하면
안 된다 — 두 값은 서로 무관하다.

### CR-03: 방장 브라우저 신원이 사건 스트림으로 새어 나가 T-12.3-05 보호가 무너진다

**File:** `src/gptrpg/web/routes_events.py:247-250` (근거: `src/gptrpg/event_log/schema.py:676-689`, `frontend/src/screens/CreationScreen.tsx:267-272`, `src/gptrpg/web/routes_creation.py:299-321`)

**Issue:**
`GameStateView`는 방장 브라우저 식별자를 절대 싣지 않도록 명시적으로 설계됐다
(`routes_events.py:100-104,148-152`, T-12.3-05: "방장의 식별자가 새면 그 값을 그대로
넣어 승계를 가로챌 수 있다"). 그런데 이 보호는 `state` 칸에만 적용됐고,
같은 응답의 `events` 목록에는 적용되지 않았다. `poll_events`는
```python
all_events = store.read_events(session_id)
...
events = [event for event in all_events if event.seq >= from_seq]
```
로 원본 `GameEvent` 객체를 가공 없이 그대로 돌려주는데, `CreationHostClaimed`
사건(`schema.py:676-689`)은 `browser_id: str` 칸을 그대로 담고 있다. 이 사건은
`visibility: Visibility = "public"` 기본값을 쓰므로(공개 필터링 없음) **폴링하는
모든 브라우저가 `GET /events` 응답의 `events` 배열에서 지금 방장의 `browser_id`를
평문으로 읽을 수 있다.**

실제로 이 유출은 이미 프런트엔드 코드가 스스로 증명한다 —
`CreationScreen.tsx:267-272`:
```ts
const hostTookOver = feed.events.some(
  (event) =>
    event.event_type === "creation_host_claimed" &&
    event.browser_id === myBrowserId &&
    ...
```
이 값을 읽을 수 있다는 것은 다른 참가자도 똑같이 읽을 수 있다는 뜻이다.

`FixPartySizeRequest.browser_id`는 서명 쿠키가 아니라 클라이언트가 그대로 보내는
문자열 필드이고(`routes_creation.py:269-277`), 방장 검사는 단순 문자열 비교다
(`routes_creation.py:305-307`, `if host is not None and host != body.browser_id:
raise HTTPException(403, ...)`). 즉 이 세션에 낀 아무 참가자나 `GET /events`
응답에서 방장의 `browser_id`를 읽어 `POST /creation/party-size`에 그대로 실어
보내면, **방장이 아닌 브라우저가 방장 전용 조작(인원 확정)을 통과한다** — 검토
지시가 명시적으로 물은 "비방장 브라우저가 방장 전용 조작을 할 수 있는가"에 대한
답은 "그렇다"다.

**Fix:**
`poll_events`가 응답에 실을 `events` 목록에서 `creation_host_claimed` 사건의
`browser_id`를 가리거나(별도의 얇은 뷰로 다시 감싸기), 아예 이 사건 종류를
폴링 `events` 목록에서 제외하고 `GameStateView.creation_host_claimed`(여부만)로만
알린다. 어느 쪽을 택하든 "방장 식별자는 어떤 폴링 응답 필드에도 평문으로 담기지
않는다"는 T-12.3-05의 불변조건이 `state`뿐 아니라 `events`에도 똑같이 적용돼야
한다. 시험은 `tests/test_creation_consent_host.py`의
`test_host_response_never_leaks_a_browser_id`(POST 응답만 확인)와
`test_claiming_host_makes_creation_host_claimed_true_with_no_identifier`(`state`
칸만 확인) 옆에 **`GET /events`의 `events` 배열 전체**를 훑어 `browser_id`가
안 새는지 확인하는 시험을 반드시 추가한다.

### CR-04: `dedupe_key`가 동시 요청 아래에서 AI 중복 호출을 못 막는다

**File:** `src/gptrpg/web/routes_creation.py:719-722,782-789,893-895,1020-1022` (근거: `src/gptrpg/session_actor/actor.py:1844-1866`)

**Issue:**
네 GM 경로(`announce`/`nominate`/`follow_up`/`wrap_up`) 전부 같은 패턴을 쓴다 —
예를 들어 `announce_creation`:
```python
key = _gm_dedupe_key("announce", actor.state)
already_said = actor.state.creation_gm_said.get(key)
if already_said is not None:
    return AnnounceCreationResponse(message=already_said.say, seq=already_said.seq)
...
message = await asyncio.to_thread(announce_requirements, rulebook, provider, model)
try:
    seq = await actor.submit(RecordGmSpoke(kind="announce", ...))
```
이 "이미 말했나" 조회는 `actor.state`(일반 속성 읽기)를 직접 보는 것이지,
`SessionActor`의 단일 소비자 큐(`_queue`)를 지나는 것이 아니다. 두 요청이 겹쳐
들어오면(예: 두 탭이 거의 동시에 안내 버튼을 누르거나, 네트워크 재시도로 같은
요청이 두 번 나가는 경우) **둘 다 `already_said is None`을 보고, 둘 다
`await asyncio.to_thread(...)`로 AI 제공자를 부른 뒤, 둘 다 `actor.submit(RecordGmSpoke(...))`
를 제출한다.**

`_prepare_gm_spoke`(`session_actor/actor.py:1844-1866`)는 이 명령을 받아 **무조건**
새 `creation_gm_spoke` 사건을 만든다 — 같은 `dedupe_key`가 이미 기록에 있는지
확인하지 않는다. 이는 같은 파일이 다른 명령에 이미 세운 관례
(`_prepare_confirm`의 `AlreadyConfirmed`, `_prepare_resolve_check`의
`AlreadyResolved`, `_prepare_record_resource_change`의 `AlreadyChanged` —
모두 단일 소비자 큐 **안에서** 멱등 단락을 건다)와 다르다. `SessionActor`는
세션당 쓰기 주체가 하나뿐이라는 사실 자체가 정확히 이런 경합을 닫기 위한
설계인데, `RecordGmSpoke`만 그 보호를 안 쓴다.

결과: 두 번째 사건도 저장소에 그대로 append되고(리듀서는 `dedupe_key`로 덮어써
`creation_gm_said`엔 하나만 남지만, `events` 테이블엔 둘 다 남는다), **AI
제공자는 실제로 두 번 불린다.** 이는 `schema.py`의 `CreationGmSpoke` 도크스트링이
명시하는 불변조건("서버가 같은 키로 다시 불려도 AI를 다시 부르지 않는다", D-12)을
정면으로 어긴다. `tests/test_creation_screen_state.py`의
`test_*_called_twice_in_the_same_state_does_not_call_the_provider_again` 시험들은
**순차** 호출(`first = _nominate(...)`가 완전히 끝난 뒤 `second = _nominate(...)`)만
확인하므로 이 경합을 못 잡는다.

**Fix:**
`_prepare_gm_spoke`에 `self.state.creation_gm_said.get(command.dedupe_key)`를
확인하는 멱등 단락을 추가한다 — 이미 있으면 새 사건을 만들지 않고 기존 기록을
가리키는 예외(다른 `Already*` 패턴과 같은 모양)를 던져 라우트가 그 값을 그대로
재사용하게 한다. 이렇게 하면 AI 호출 자체는(라우트 층에서) 여전히 두 번 일어날
수 있지만, 최소한 **사건 기록과 최종 상태**는 항상 하나로 수렴한다 — 더 엄격히
막으려면 AI 호출과 `dedupe_key` 조회를 함께 액터 큐 안으로 옮기는 재구성이
필요하지만, 그건 이번 리뷰의 최소 수정 범위를 넘는다. 최소한 위 단락 하나는
반드시 추가해야 한다. 시험은 `asyncio.gather`로 진짜 겹치는 두 요청을 만들어
`provider.calls`가 여전히 1인지 확인하는 것을 추가한다.

**그 숫자 자체가 지금도 틀렸다**(실제로는 19종) — 있지도 않은 정확성의 인상을
준다. `character_occupied`는 CHAR-05(자동 점유) 때문에 모든 정상 세션에서
반드시 한 번은 발생하는 사건이라, 폴링 응답에 실제로 섞여 온다.

**Fix:** 세 `interface`를 추가하고 `GameEvent` 유니언에 포함시키거나, 최소한 머리말
주석의 사건 종수를 실제 값(19)으로 고친다.
