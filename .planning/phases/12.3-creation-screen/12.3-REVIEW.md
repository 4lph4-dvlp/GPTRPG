## Warnings

### WR-02: 상태 칸 25% 상한 단언이 실제 CSS 분기 기준(폭 1080px)이 아니라 형태 이름과의 문자열 비교로 갈린다

**File:** `scripts/check_narrow_viewport.py:786`

**Issue:** 상태 칸 상한 단언(⑥)은 여전히 `measurement["name"] != WIDE_SHAPE`로
"좁은 형태인가"를 가른다.

```python
if measurement["name"] != WIDE_SHAPE:
    max_status_height = viewport_height * MAX_STATUS_HEIGHT_RATIO
    if measurement["statusHeight"] > max_status_height + OVERFLOW_TOLERANCE_PX:
        reasons.append(...)
```

실제 CSS는 `@media (max-width: 1080px)`(`frontend/src/styles.css:175`)로 갈리는데,
이 판정은 **형태의 실제 폭**이 아니라 **형태의 이름**을 본다. 지금 `SHAPES`에는
1080px보다 넓은 형태가 `"1440x900"`(=`WIDE_SHAPE`) 하나뿐이라 우연히 결과가
같다. `_validate_shape_name_constants()`가 `WIDE_SHAPE` 이름이 `SHAPES`에 있는지는
검사하지만, 그 형태의 `width`가 실제로 1080을 넘는지는 검사하지 않는다 — 다음에
`SHAPES`에 폭 1080 초과의 새 형태를 `"1440x900"`이 아닌 다른 이름으로 추가하면,
그 형태는 데스크톱 CSS를 쓰면서도 이 스크립트에서는 "좁은 형태"로 분류돼 25%
상한을 강제로 걸어 버린다(실제로는 그 상한 자체가 CSS에 없는데도) — 오탐으로
실험 당일 진행자를 혼란시킬 수 있다.

**Fix:** 이름 비교 대신 폭 비교로 바꾼다. CSS의 분기 기준(1080px)을 상수로
한 번 적어 두 자리(이 스크립트와 사람이 읽을 주석)가 같은 숫자를 보게 한다:

```python
# frontend/src/styles.css:175의 @media (max-width: 1080px)과 같은 값.
NARROW_BREAKPOINT_PX = 1080
...
def _is_narrow(measurement: dict) -> bool:
    shape = next(s for s in SHAPES if s["name"] == measurement["name"])
    return shape["width"] <= NARROW_BREAKPOINT_PX

if _is_narrow(measurement):
    ...  # 기존 로직
```

## Info

### IN-01: `className=` 안에서 이름을 찾는 정규식이 중첩 중괄호(템플릿 리터럴 안 `${...}`)를 못 넘는다

**File:** `scripts/check_narrow_viewport.py:220`

**Issue:** `_CLASS_NAME_ATTR_RE = re.compile(r'className=(?:\{[^}]*\}|"[^"]*")', ...)`의
`[^}]*`는 첫 `}`에서 멈춘다. `className={\`chat-line ${cond ? "a" : "b"}\`}`처럼
중괄호가 중첩된 JSX를 만나면 바깥 `className={...}`의 진짜 닫는 중괄호보다 먼저
멈춰서 그 뒤에 오는 클래스 이름을 못 찾는다. 지금 `ChatPane.tsx`·`CreationPane.tsx`·
`StatusPane.tsx`·`StoryPane.tsx`에는 이 패턴이 없어(`check_fixture_still_mirrors_source()`가
정상 실행에서 빈 배열을 돌려줌 — 직접 실행해 재확인) 지금 당장 걸리는 자리는
없다. 방향도 안전한 쪽(찾아야 할 이름을 못 찾으면 "사라졌다"로 보고 종료 코드
2 — 통과로 새지 않는다)이라 급하지 않다.

**Fix:** 지금 당장 고칠 필요는 없다. `_class_name_present_in_jsx()`에 "중첩된
`{}` 안에 이름이 있으면 못 찾을 수 있다(현재 소스에는 없음, 확인 완료)"를
도크스트링으로 남겨 다음 사람이 놀라지 않게 한다.

### IN-02: README의 본 경로(인자 없음) 실패(1) 설명이 "상태 칸 25% 상한 초과" 사유를 여전히 빠뜨렸다

**File:** `README.md:40`

**Issue:** README 40행은 `check_narrow_viewport.py`(인자 없이 부르는 본 경로)의
종료 코드 1을 "서사 칸이 죽거나 골격이 넘치거나 조작부가 안 닿거나 3컬럼이
무너짐"으로 설명한다. 실제 `judge()`에는 12.3-18이 더한 여섯째 사유 — 좁은
형태에서 상태 칸이 뷰포트의 25%를 넘김 — 가 있고, 스크립트 자신의 모듈
도크스트링에는 이미 이 사유가 적혀 있다. 이번 라운드(12.3-20)는 `--self-test`
경로의 종료 코드 1 문단만 넓혔고(48행 근처, 실제로 확장돼 있음을 확인), 40행
근처 본 경로 문단은 의도적으로 그대로 뒀다. 실험 당일 이 명령이 본 경로에서
"1"을 찍었을 때 진행자가 README만 보고 원인을 좁히면, 상태 칸 상한 초과가 그
목록에 없어 예상 밖의 실패로 오인할 수 있다.

**Fix:** README 40행의 실패 사유 나열에 "좁은 형태에서 상태 칸이 뷰포트의
25%를 넘김"을 추가해 모듈 도크스트링과 맞춘다.
