## Warnings

### WR-01: 자동 호출로 바뀐 `announce()`가 언마운트 뒤 상태 갱신을 막는 가드가 없다

**File:** `frontend/src/screens/CreationScreen.tsx:346-357` (`announce`), `367-401` (자동 호출 effect)

**Issue:** 12.3-14 이전에는 `announce()`가 오직 사람이 단추를 눌러야만
불렸다 — 그 단추가 화면에 떠 있다는 것 자체가 컴포넌트가 마운트돼
있다는 뜻이라, 언마운트 뒤에 `announce()`의 `then`/`catch`/`finally`가
실행될 경로가 없었다. 지금은 `useEffect`(368-401행)가 조건
(`shouldAnnounce`)이 참이 되는 즉시 `void announce()`를 스스로 부른다
(377-380행). 이 컴포넌트가 도는 동안 `feed.state.party_roster`가
채워지면(다른 브라우저가 명단을 잠그는 등) 325-329행의 별도 effect가
`onEntered(myCharacterId)`를 불러 `App`이 이 화면 자체를 다른 화면으로
바꿔치기한다 — 이때 `CreationScreen`이 실제로 언마운트된다.

`announce()` 자신은 `usePolling.ts`의 `beacon()`(295-312행, `alive` ref로
가드)이나 `poll()`(65-126행, `aliveRef.current` 검사)과 달리 언마운트
여부를 확인하지 않는다 — `await announceCreation(...)`이 끝난 뒤
`setPending`/`setError`/`feed.pollNow()`를 조건 없이 부른다(346-357행).
`announceCreation`이 사람 기준으로 몇 초 걸릴 수 있는 AI 호출이므로,
그 몇 초 사이에 다른 탭이 명단을 잠그고 이 탭이 화면 전환을 시작하면
이미 사라진 컴포넌트의 상태를 갱신하려는 호출이 남는다. React 18은
이것으로 콘솔 경고나 크래시를 내지 않지만(구버전의 "unmounted
component" 경고는 React 18에서 제거됨), `feed.pollNow()`가 이미 정리된
`usePolling` 인스턴스를 참조하며 부르는 것이므로 — `feed`(및
`feed.pollNow`)는 `useCallback`으로 감싸인 클로저이고 그 안의 `poll`은
자기 자신의 `aliveRef.current`를 검사해 조용히 무시하므로 실질적인
피해는 없다. 다만 이 파일의 다른 두 유사 effect(방장 재실 신호, 항목
선언 조회)가 모두 지키는 `alive` 관례를 이 자리만 벗어났다는 것은
일관성 결함이고, 이후 이 코드를 고치는 사람이 같은 관례를 기대하고 놓칠
여지가 있다.

**Fix:** `announce`를 `usePolling`의 `beacon()`과 같은 패턴으로 감싼다 —
effect 안에서 `let alive = true`를 두고 정리 함수에서 `false`로 돌린
뒤, `announce()` 내부의 `setPending`/`setError`/`feed.pollNow()` 호출
앞에 그 값을 검사하게 한다:

```tsx
const aliveRef = useRef(true);
useEffect(() => {
  aliveRef.current = true;
  return () => {
    aliveRef.current = false;
  };
}, []);

const announce = useCallback(async (): Promise<void> => {
  setPending(true);
  setError(null);
  try {
    await announceCreation(sessionId, rulebookId ?? DEFAULT_RULEBOOK_ID);
    if (aliveRef.current) {
      feed.pollNow();
    }
  } catch (err) {
    if (aliveRef.current) {
      setError(creationErrorMessage(err));
    }
  } finally {
    if (aliveRef.current) {
      setPending(false);
    }
  }
}, [sessionId, rulebookId, feed.pollNow]);
```

### WR-02: 자동 안내 호출이 여러 탭에서 동시에 터지면서, 서버가 이미 알고 있는 「AI 제공자가 두 번 불릴 수 있다」 경쟁을 훨씬 더 자주 건드리게 됐다

**File:** `frontend/src/screens/CreationScreen.tsx:359-401`(신규 자동 호출 effect), `src/gptrpg/web/routes_creation.py:787-800`(`announce_creation`), `src/gptrpg/session_actor/actor.py:1874-1888`(`_prepare_gm_spoke` 도크스트링이 이 경쟁을 스스로 인정하는 자리)

**Issue:** `routes_creation.py::announce_creation`은 AI 제공자를 부르기
**전에** `_gm_dedupe_key`로 「이미 말했나」를 확인하지만(787-789행), 이
확인은 큐 밖의 일반 속성 읽기라 두 요청이 겹치면 둘 다 통과할 수 있다
— 이 사실은 `actor.py::_prepare_gm_spoke`의 도크스트링(1874-1888행)이
이미 스스로 적어 둔 것이다: "**그래서 이 메서드가 큐 안에서 같은 검사를
다시 한다**... 이 단락이 없으면 겹친 두 요청이 `creation_gm_spoke`를 두
번 append한다... **그보다 먼저 AI 제공자가 실제로 두 번 불린 뒤다(D-12
위반)**." 즉 사건 중복 자체는 큐 안 재검사(`AlreadyGmSpoken`)가 막지만,
**AI 제공자 호출의 중복(비용)은 막지 못한다** — 이것은 이번 계획이 만든
결함이 아니라 이미 문서화된 기존 한계다.

12.3-14가 바꾼 것은 이 경쟁이 **얼마나 자주 실제로 일어나는가**다.
이전에는 `announce()`가 사람이 단추를 눌러야만 불렸으므로, 두 요청이
겹치려면 두 사람이 거의 같은 순간에 각자 단추를 눌러야 했다 — 드문
경로였다. 지금은 `shouldAnnounce`(367-401행)가 인원이 확정되는 순간
**이 세션을 보고 있는 모든 브라우저에서 동시에** 참이 되고, 각 탭은
독립적으로 `announcingRef`(자기 탭 안에서만 중복을 막는다, 375행)로
가드된 `announce()`를 스스로 부른다. 3~5명이 참여하는 세션에서, 인원
확정 직후 1.5초 폴링 주기 안에 여러 탭이 `POST /creation/announce`를
동시에 보내는 것이 이제 **일반적인 경로**가 됐다 — 이전엔 예외적
경합이었던 것이 지금은 매 세션마다 벌어질 수 있는 정상 흐름이다. 사건
자체는 여전히 하나만 남지만(D-12가 보장), AI 제공자가 여러 번 불리면
실제 비용(과금)과 지연이 늘어난다 — 이 프로젝트가 이미 민감하게 보는
항목이다(비용 분석 산출물이 별도로 존재한다).

**Fix:** 근본 수정(라우트가 큐 밖에서 하는 사전 검사를 큐 안 검사로
대체하거나, 세션당 뮤텍스로 좁히는 것)은 `announce_creation`뿐 아니라
`nominate`/`follow_up`/`wrap_up` 네 경로 모두가 공유하는 패턴이라
이번 계획의 범위를 넘는 별도 작업감이다. 이번 계획 안에서 할 수 있는
완화책은 프런트엔드 쪽 경합 창을 좁히는 것이다 — 예를 들어 방장(호스트)
브라우저만 자동 호출하게 `shouldAnnounce`에 `youAreHost`를 추가 인자로
받게 하면, 세션당 최대 한 탭만 자동으로 부르므로 겹칠 여지가 방장이
새로고침한 순간 등 훨씬 좁은 창으로 줄어든다:

```ts
export function shouldAnnounce(
  state: GameStateView,
  announced: boolean,
  lastAttemptFailed: boolean,
  youAreHost: boolean,
): boolean {
  if (!youAreHost) {
    return false;
  }
  // ...기존 네 검사...
}
```
(다만 방장이 아예 탭을 닫아 버리면 아무도 안 부르는 새 결함이 생기므로,
이 처방을 고를 때는 그 대가도 함께 검토해야 한다 — 근본 수정 쪽이 더
안전하다.)

### IN-01: `labels.ts`와 `session/creationView.ts`가 서로를 임포트하는 순환 의존이 새로 생겼다

**File:** `frontend/src/labels.ts:9` (`import type { CreationTurn } from "./session/creationView.ts"`), `frontend/src/session/creationView.ts:16` (`import { COPY } from "../labels.ts"`)

**Issue:** `creationView.ts`는 예전부터 `labels.ts`의 `COPY`를 값으로
가져다 쓴다(`creationErrorMessage` 등). 이번 12.3-14가 `labels.ts`에
`creationTurnLabel`을 추가하면서 `creationView.ts`가 내보내는
`CreationTurn` 타입을 반대 방향으로 가져오게 됐다(9행) — 두 파일이
서로를 임포트하는 순환이 생겼다. `import type`이라 TypeScript가 컴파일
시점에 완전히 지워 런타임 순환 임포트 문제(초기화 순서에 따라 한쪽이
`undefined`를 보는 것과 같은 고전적 ESM 순환 버그)는 실제로 안
일어난다 — `tsc --noEmit`과 `vitest`를 직접 돌려 확인했고 둘 다 통과다.
다만 이후 누군가 `creationView.ts`에서 값(함수·상수)을 `labels.ts`로
가져오게 되면 그 순간 이 순환이 런타임 순환으로 바뀐다 — 지금은
무해하지만 구조적으로는 다음 사람이 밟기 쉬운 자리다.

**Fix:** `CreationTurn` 타입을 `creationView.ts`가 아니라 `labels.ts`
자신이나 별도의 작은 타입 파일에 두고 `creationView.ts`가 그것을
가져다 쓰는 방향으로 뒤집으면 순환이 사라진다. 지금 당장 고칠 만큼
급하지는 않다(무해함을 확인했다) — 이 파일들을 다음에 건드릴 때 함께
정리하면 된다.
