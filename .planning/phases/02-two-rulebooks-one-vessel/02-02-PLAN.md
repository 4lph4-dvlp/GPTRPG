<objective>
02-01이 꿴 얇은 d100 경로에 수정치 네 유형을 전부 붙여, 네 유형이 **같은 감지 하나**
(판정 요청 → 판정 결과)에서 실제로 돈다는 것을 증명한다. 자리만 열어두는 것이 아니라
계산이 바뀐다 (D-23, D-24).

Purpose: 네 유형이 하나의 인터페이스 위에서 전부 도는 것이 "추상화가 옳다"는 가장 강한
증거다(D-24 원문). 특히 주사위 추가·제거와 목표값 변경은 "총합에 더할 숫자"가 아니라
"굴림 절차를 바꾸는 지시"라서, Phase 1의 `_flat_total` 패턴을 복사해서는 만들 수 없다 —
이 태스크가 파이프라인 단계를 나누는 이유가 그것이다 (RESEARCH.md Pattern 2).

Output: 네 유형을 전부 계산하는 `resolve_d100`, `reroll_2d6`과 같은 불변식을 가진
`push_d100`, OpenQuest 난이도 다섯 단계 선언, 그리고 등급 구간이 빈틈·겹침 없음을 증명하는
성질 테스트.

  <action>
  `resolve_d100`을 RESEARCH.md Pattern 2의 세 시점 구조로 다시 짠다. `_flat_total`을 복사해
  유형만 늘리는 접근은 금지다 — 보너스 다이스는 총합에 더할 숫자가 아니라 몇 개를 어떻게
  굴릴지의 문제이기 때문이다.

  ① `resolution_d100.py`에 수정치 유형 상수 셋을 선언한다: `TARGET_SHIFT = "target_shift"`,
  `BONUS_DICE = "bonus_dice"`, `PUSH = "push"`. `FLAT`은 `resolution.py`에서 import해 쓴다
  (다시 정의하지 않는다). 각 상수 옆에 값의 뜻을 한 줄로 남긴다 — `BONUS_DICE`의 `value`는
  양수면 보너스 개수, 음수면 페널티 개수다.

  ② `resolve_d100`의 계산 순서를 이렇게 고정한다:
   - 수정치 목록을 **한 번 훑어** 네 유형으로 분류한다. `FLAT`/`TARGET_SHIFT`/`BONUS_DICE`/
     `PUSH` 넷 중 어느 것도 아니면 그 자리에서 `UnsupportedModifier(type, source,
     resolver="resolve_d100")`를 던진다.
   - **굴리기 전:** `target = skill + (TARGET_SHIFT 값들의 합)`. `PUSH`는 이 시점에 아무
     효과가 없다 — 이것은 "조용한 건너뛰기"가 아니라 명시된 의미이며, Task 2의 `push_d100`이
     이 표식을 실제로 읽는다. 그 사실을 함수 docstring에 적는다.
   - **굴림 자체:** `dice_delta = BONUS_DICE 값들의 합`. 십의 자리를 `1 + abs(dice_delta)`번
     굴린다. `dice_delta > 0`이면 굴린 것 중 **가장 작은** 값을, `< 0`이면 **가장 큰** 값을,
     `0`이면 유일한 값을 채택한다(굴려서 밑도는 방식이므로 작을수록 유리하다). 일의 자리는
     한 번만 굴린다.
   - **굴린 뒤:** `total = percentile_value(채택된 십의 자리, 일의 자리) + (FLAT 값들의 합)`.
   - 등급: `is_doubles = (채택된 십의 자리 == 일의 자리)`, `margin = target - total`,
     `grade_for_margin(margin, is_doubles, bands).name`.
   - `CheckOutcome.rolls`는 **굴린 십의 자리 전부 + 일의 자리** 순서로 담는다(버려진 눈도
     남긴다 — D-16 "계산 과정 전체를 담는다", 그리고 재생이 같은 눈을 같은 순서로 소비해야
     한다). `modifiers`는 받은 것을 그대로 튜플로, `target`은 변경된 목표값.
   - 보너스/페널티 다이스 계산 규칙의 출처를 함수 docstring에 남기되, **OpenQuest SRD가 아니라
     크툴루 계열 장르 공통 관행**임을 명시한다(02-RESEARCH.md 385-393행의 인용과 출처 태그를
     그대로 옮긴다). OpenQuest 원문에는 이 메커닉이 없다.

  ③ `rulebooks/openquest.py`에 난이도 선언을 더한다: `OPENQUEST_DIFFICULTY`를 이름 → 값
  매핑으로 두되 값은 SRD 난이도 표 그대로 — Easy +50, Simple +20, Normal 0, Difficult -20,
  Hard -50. 그리고 `difficulty_modifier(name)`이 `Modifier(type=TARGET_SHIFT, value=그 값,
  source="openquest:difficulty:" + name)`을 돌려주게 한다. SRD 원문은 "판정 하나에 난이도
  수정치는 하나만 쓴다"고 정하지만, 그것은 룰북의 운용 규칙이지 플랫폼의 계산 제약이 아니다 —
  플랫폼은 여러 개를 합산할 수 있어야 하고(다른 룰북은 여러 개를 허용한다), 이 구분을
  docstring에 한 줄로 남긴다. 출처 경로(`openquestrpg.com/srd/skills/difficulty/`)도 적는다.

  ④ `tests/test_resolution_d100.py`를 새로 쓴다. `tests/test_resolution_edges.py`의

  실제로 늘렸는지 단언해야 하므로)를 만든다. 위 `<behavior>` 항목을 전부 덮는다.
