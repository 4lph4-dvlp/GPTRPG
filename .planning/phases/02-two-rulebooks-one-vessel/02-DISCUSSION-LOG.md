## 적/NPC 상태값의 최소 모양

### Q1: 적/NPC 상태값 하나의 모양은 어떻게 푸는 게 좋을까요?

| Option | Description | Selected |
|--------|-------------|----------|
| 이름 + 현재값 + 최대값(선택) + 바닥날 때 효과 참조 | 룰북이 선언하는 값 하나당: {키 이름, 현재값, 최대값(없을 수도 있음 — 모든 상태값이 상한이 있는 건 아님), 바닥날 때 뭐가 일어나는지를 가리키는 효과 참조}. D32 원문의 "특정 값이 바닥나면 무슨 일이 일어나는지를 룰북이 선언한다"를 그대로 따르며, Phase 1의 Modifier처럼 "값 + 출처" 패턴을 재사용한다 | ✓ |
| 순수 키-값 (키:값 쌍만) | {키 이름: 값} 만 가진다. 바닥날 때 뭐가 일어나는지는 이 단계에서 자리조차 안 둔다 — 더 단순하지만, D32 원문이 명시한 "바닥날 때 무슨 일이 일어나는지를 룰북이 선언한다"를 Phase 2가 아직 증명하지 못한다 | |

**User's choice:** 이름 + 현재값 + 최대값(선택) + 바닥날 때 효과 참조
**Notes:** —

### Q2: 적/NPC 하나가 상태값을 몇 개까지 가질 수 있을까요?

| Option | Description | Selected |
|--------|-------------|----------|
| 제한 없음 — 목록으로 | 상태값 묶음을 목록/맵으로 두고 개수를 코드가 제한하지 않는다. 룰북마다 몇 개를 쓸지는 룰북 데이터가 정한다. 플랫폼 코드는 "목록이 있다"만 알고 몇 개인지는 모른다 — D32의 "그릇은 우리가, 내용은 룰북이"를 그대로 따른다 | ✓ |

**User's choice:** 제한 없음 — 목록으로

## "플랫폼 코드를 고쳤는지" 기록 방식

### Q1: 성공 조건 5번(플랫폼 코드를 고쳤는지 명확히 기록)을 어떻게 남길까요?

| Option | Description | Selected |
|--------|-------------|----------|
| 별도 문서로 거지 별로 기록 | Phase 2 종료 시 SUMMARY.md와는 별도로 "d100 룰북을 넣으면서 플랫폼 코드(rules_core·event_log·session_actor)를 고친 곳이 있는가"를 별도 섹션에 모은다. 고친 게 있다면 파일명·이유를 직접 적고, 없다면 "고친 적 없음"을 명시적으로 적는다. HYP-03(룰북을 데이터로 표현할 수 있다)의 판정 증거가 SUMMARY 여러 개에 흩어지지 않고 한 곳에 모인다 | ✓ |
| git 커밋 diff로만 충분 | 별도 문서 없이, "플랫폼 코드를 고친 커밋이 있는지"를 git log로 보면 알 수 있다고 본다. 더 간단하지만, "명확히 기록된다"는 성공 조건 문구와 느슨하게 엇긴다 — git log를 직접 훑어야 확인되는 건 "설명"이 아니라 "추론"에 가깝다 | |

**User's choice:** 별도 문서로 거지 별로 기록
**Notes:** —

### Q2: 그 별도 문서에는 "고친 적/안 고친 점" 외에 무엇을 더 담을까요?

| Option | Description | Selected |
|--------|-------------|----------|
| 고친 곳 + 고치지 않고 버툰 곳 | 둘 다 적는다 — 플랫폼을 고친 곳과, "고치고 싶었지만 데이터로 버틴 곳"을 둘 다 기록한다. 뒤쪽이 중요하다 — "고치고 싶었지만 참았다"가 추상화가 옳다는 가장 강력한 증거이기 때문이다. 예: "수정치 유형을 rules_core에 박을까 고민했지만, 데이터의 type 칸으로 해결했다" 같은 사례가 여기에 쓰인다 | ✓ |
| 고친 것만 짧게 나열 | 고친 파일과 이유만 간결하게 적는다. 더 빠르지만 "거의 고치지 않을 뻔했다"의 증거는 약해진다 | |

**User's choice:** 고친 곳 + 고치지 않고 버툰 곳
**Notes:** —

| Option | Description | Selected |
|--------|-------------|----------|
| 실제 동작까지 — Phase 1의 reroll_2d6과 같은 패턴 | d100 롤언더용 reroll 함수를 실제로 구현한다 — 앞선 눈을 지우지 않고 이어 붙여, 크툴루의 푸시 롤이 실제로 동작하는 모습을 보여준다. "수정치 네 유형이 동작한다"를 가장 강력하게 증명하고, Phase 1이 이미 증명한 패턴(앞선 눈 보존)을 그대로 재사용해 새로 배우는 것이 적다 | ✓ |

**User's choice:** 실제 동작까지 — Phase 1의 reroll_2d6과 같은 패턴

### Q2: 다른 세 수정치 유형(숫자 가감·주사위 추가·제거·목표값 변경)도 같은 수준으로 실제 동작까지 만들까요?

| Option | Description | Selected |
|--------|-------------|----------|
| 네 유형 모두 실제 동작 | 숫자 가감(flat, 이미 Phase 1에 있음)은 그대로 쓰고, 주사위 추가·제거(보너스 다이스)와 목표값 변경(난이도 상승)도 실제 계산에 반영된다. 이렇게 해야 "판정 수학이 같은 그릇에 도는가"를 재굴림 외의 다른 수정치에서도 실물로 증명한다. 네 유형 전부가 같은 감지에서 돈다는 것이 추상화가 옳다는 가장 강력한 증거다 | ✓ |
| 재굴림만 실제 동작, 나머지는 자리만 | 재굴림이 가장 복잡하니 그것만 실물로 만들고, 주사위 추가·제거와 목표값 변경은 자리만 열어둔다. 더 빨리 끝나지만, 성공 조건 3번의 "네 유형이 모두 표현된다"를 자리만 열어둔 것으로 만족할지, 동작까지 요구할지가 애매해진다 | |

**User's choice:** 네 유형 모두 실제 동작
