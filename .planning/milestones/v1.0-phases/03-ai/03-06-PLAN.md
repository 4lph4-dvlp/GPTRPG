<root_cause>
UAT의 진단(`turn_flow.py`가 `last_result()`를 무조건 부른다)은 맞지만 **절반**이다. 계획 단계에서 실제로 돌려 확인한 나머지 절반을 여기 남긴다 — 이걸 모르면 Task 3만 하고 gap이 닫혔다고 착각하게 된다.

사용자는 NIM을 쓰고 있었다. `NimProvider`와 `OpenRouterProvider`는 **위임 어댑터**다 — 자기 `_last_result`를 갖지 않고 `last_result()`를 `self._delegate.last_result()`로 넘긴다. 그런데 `master_gm.narrate()`의 실패 경로는 `provider._last_result = 실패 껍데기`로 **직접 속성을 꽂는다**(현재 187번째 줄, `noqa: SLF001`). 위임 어댑터에서 이 대입은 아무도 읽지 않는 새 속성 하나를 만들 뿐이고, `last_result()`는 여전히 위임 대상의 `None`을 보고 `RuntimeError`를 던진다.

실측(계획 단계에서 실행):

```
NimProvider:        RuntimeError(complete() 또는 stream()을 먼저 불러야 ...)  <- 실패 껍데기 유실
OpenRouterProvider: RuntimeError(complete() 또는 stream()을 먼저 불러야 ...)  <- 실패 껍데기 유실
```

`master_gm.py`의 도크스트링은 "다섯 어댑터 전부가 `_last_result`라는 이름을 함께 써 왔다"는 내부 관례에 기댄다고 적어 두었는데, **그 진술이 다섯 중 둘에 대해 거짓이다.** 자동 시험이 못 잡은 이유도 분명하다 — `test_master_gm.py`의 실패 이중체 세 개가 전부 `_last_result`를 자기가 소유하는 **직접** 어댑터 모양이라, 위임 구멍을 통과해 본 적이 없다. UAT 4번 시험이 남긴 지적("대체 경로의 정확성은 여전히 합성 이중체로만 증명된 상태")과 정확히 같은 종류의 눈속임이다.

그래서 이 계획은 두 층을 함께 고친다:
- **층 1 (Task 1·2):** 실패 껍데기 전달을 `Provider` 프로토콜의 정식 메서드로 올려 위임을 통과하게 만든다. `narrate()`가 남긴 `ok=False`가 실제로 `turn_flow`에 도착한다.
- **층 2 (Task 3):** 그래도 `turn_flow`는 방어한다. 어떤 제공자가 규약을 어기든, 서사 구간에서 나온 어떤 예외든 raw traceback으로 새지 않는다.

층 1만 하면 이번 사고는 막히지만 다른 실패 모양에서 또 샌다. 층 2만 하면 크래시는 막히지만 실패한 호출의 지연·토큰이 기록되지 않아 MEAS-02가 실패 턴을 잃는다.
</root_cause>
