**`agents/context.py`** — 매 턴 에이전트에게 넘기는 것을 네 가지로 못박는다(ROADMAP 성공조건 4, 설계 문서 §3.8). `RECENT_TURNS_LIMIT = 10` 상수, `@dataclass(frozen=True) ClockState` (칸: `clock_id: str`, `segment_index: int`, `segment_count: int`), `@dataclass(frozen=True) TurnContext` (칸: `scene_entities: tuple[Entity, ...]`, `character_state: tuple[StatEntry, ...]`, `clock_state: ClockState`, `recent_turns: tuple[str, ...]`). `TurnContext.__post_init__` 은 `recent_turns` 길이가 `RECENT_TURNS_LIMIT` 를 넘으면 `TooMuchContext` 예외를 던진다 — 조용히 잘라내지 않는다(잘라내면 「열 턴 고정」이 깨진 것을 아무도 모른다). `entities.py` 의 `ENTITY_FIELD_NAMES` 관례를 그대로 따라 `TURN_CONTEXT_FIELD_NAMES = frozenset(f.name for f in fields(TurnContext))` 를 선언해 칸이 넷임을 코드로 고정한다.

**`agents/providers/base.py`** — `Provider` 프로토콜을 세 메서드로 좁게 정의한다: `list_models() -> list[str]`, `complete(*, model: str, system: list[dict], messages: list[dict], max_tokens: int, timeout_s: float) -> AgentResult`, `stream(*, model, system, messages, max_tokens, timeout_s) -> Iterator[str]`. 여기에 `last_result() -> AgentResult` 를 하나 더 둔다 — 스트리밍은 토큰 수를 마지막에야 알 수 있으므로, 반복자를 다 소진한 뒤 이 메서드로 토큰·시간을 가져간다는 규약을 프로토콜 도크스트링에 적는다. 프로토콜에는 클래스 속성 `name: str` 도 둔다(기록에 남길 제공자 이름). 이 파일은 어떤 SDK도 import하지 않는다.

**`agents/providers/anthropic_provider.py`** — `AnthropicProvider` 를 만든다. `name = "anthropic"`. 생성자는 API 키를 인자로 받아 `anthropic.Anthropic(api_key=...)` 를 만든다(환경 변수를 이 파일 안에서 직접 읽지 않는다 — 읽는 자리는 등록소 한 곳뿐이다). `list_models` 는 `self._client.models.list()` 를 그대로 순회해 `m.id` 목록을 돌려준다(자동 페이지 넘김이 있으므로 `.data` 를 인덱싱하지 않는다). `complete` 는 `messages.create` 를 부르고 응답의 `usage.input_tokens`/`usage.output_tokens` 와 직접 잰 경과 시간으로 `AgentResult` 를 채운다. `stream` 은 `client.messages.stream(...)` 컨텍스트 안에서 `stream.text_stream` 을 그대로 흘려보내고, 컨텍스트를 빠져나오기 전에 `stream.get_final_message()` 의 usage 로 `last_result()` 가 돌려줄 값을 채운다. 예외는 삼키지 않는다 — 그대로 위로 올린다(재시도 규칙은 03-03 이 한 자리에 만든다).

**`agents/providers/__init__.py`** — 제공자 이름을 일급 개념으로 만드는 등록소다. `PROVIDER_ENV_VARS: dict[str, str]` 에 다섯 이름과 환경 변수를 전부 적는다: `anthropic`→`ANTHROPIC_API_KEY`, `openai`→`OPENAI_API_KEY`, `gemini`→`GEMINI_API_KEY`, `nim`→`NVIDIA_API_KEY`, `openrouter`→`OPENROUTER_API_KEY`. `available_providers(env)` 는 값이 비어 있지 않은 키를 가진 이름만 정렬해 돌려준다(D-31 의 「존재하는 API 키를 기반으로 감지」). `PROVIDER_FACTORIES` 에는 이번 트레이서가 실제로 만드는 어댑터 하나(`anthropic`)만 등록한다 — 나머지 넷은 03-02 가 같은 자리에 더한다. `get_provider(name, env)` 는 이름이 `PROVIDER_ENV_VARS` 에 없으면 `UnknownProvider`, 키가 없으면 `MissingApiKey`, 어댑터가 아직 등록되지 않았으면 `ProviderNotImplemented` 를 던진다 — 세 경우 모두 조용히 다른 제공자로 대체하지 않는다(`get_rulebook`/`UnknownRulebook` 이 세운 규율과 같은 이유다). 키 값 자체는 어떤 예외 메시지에도 넣지 않는다.

**`rulebooks/moves.py`** — 분류기가 고를 **닫힌 목록**을 룰북 데이터로 선언한다. `@dataclass(frozen=True) MoveDecl` 의 칸은 `move_id: str`, `display_name: str`, `default_stat: str`, `trigger: str`(언제 이 무브가 걸리는지 한 줄 설명 — 프롬프트에 그대로 들어간다). 던전월드 계열 룰북용으로 열 개 남짓(EXP-01 이 「판정 종류 10개 남짓」이라고 적은 규모)을 `DUNGEONWORLD_LIKE_MOVES` 에 선언하고, OpenQuest 룰북용 기술 목록을 `OPENQUEST_MOVES` 에 같은 규모로 선언한다. `MOVE_CATALOGS: dict[str, tuple[MoveDecl, ...]]` 로 `rulebook_id` 에 잇고, `get_moves(rulebook_id)` 는 없는 식별자에 대해 `gptrpg.rulebooks.UnknownRulebook` 을 던진다. 이 파일은 `rulebooks/` 안이므로 플랫폼 코드가 아니라 데이터다 — 세 번째 룰북의 무브 목록은 이 파일에 표를 더하는 것으로 끝나야 한다(HYP-03 이 세운 성질).

**`agents/prompt_assembly.py`** — 이 단계의 숨은 요구사항이 사는 자리다. 순수 함수 두 개를 만든다(`resolution.py` 의 「순수 함수, 명시적 순서, 숨은 전역 상태 없음」 규율을 그대로 따른다). `build_classifier_prompt(*, rulebook_display_name: str, moves: tuple[MoveDecl, ...], ctx: TurnContext, raw_text: str)` 와 `build_gm_prompt(*, rulebook_display_name: str, ctx: TurnContext, check_summary: str)` 는 둘 다 `(system, messages)` 짝을 돌려준다. system 은 정확히 두 조각이다 — ① **영구 고정** 조각(룰북 이름 + 무브 목록 + 에이전트 역할 지시문. 캠페인 내내 안 변한다) ② **세션 고정** 조각(`ctx.scene_entities` + `ctx.character_state` + `ctx.clock_state`. 장면이 바뀔 때만 변한다). 두 조각 모두 끝에 `cache_control` 을 `{"type": "ephemeral"}` 로 붙인다. messages 는 한 조각이다 — **턴마다 변함**(`ctx.recent_turns` + 이번 문장 또는 판정 요약). 시각·플레이어 표시 이름·세션 식별자·추적 번호처럼 호출마다 달라지는 값은 system 안에 한 글자도 넣지 않는다. 두 에이전트가 하나의 매개변수화된 함수를 공유하지 않는 이유를 파일 도크스트링에 적는다: 분류기는 무브 목록만 있으면 되고 진행자는 장면·시계까지 필요하므로 영구 조각의 내용 자체가 다르다(D-32 가 둘을 따로 설정하게 한 것과 같은 이유).

**`agents/action_classifier.py`** — `@dataclass(frozen=True) MoveCandidate` (칸: `move: str`, `stat: str`), `@dataclass(frozen=True) Proposal` (칸: `candidates: tuple[MoveCandidate, ...]`, `ai: AgentResult`). `classify(*, provider: Provider, model: str, ctx: TurnContext, raw_text: str, moves, rulebook_display_name) -> Proposal` 은 프롬프트를 조립해 `provider.complete` 를 부르고, 모델이 돌려준 후보를 `moves` 의 `move_id` 집합과 대조한다. 목록에 없는 이름이 하나라도 오면 `UnknownMove` 예외를 던진다 — 조용히 통과시키면 룰북에 없는 무브가 기록에 남고 이후 어디서도 복원되지 않는다. 후보가 하나도 없으면 예외가 아니라 빈 `candidates` 로 돌려준다(「무브 없음」은 정상 결과다). 모델 출력은 후보 목록 이름 문자열로만 해석한다 — 수치·판정 결과·등급을 모델 출력에서 읽는 코드를 만들지 않는다(D14).

**`agents/master_gm.py`** — `chunk_sentences(deltas: Iterable[str]) -> Iterator[str]` 를 만든다. 조각을 버퍼에 이어 붙이다가 문장 끝 구두점(마침표·물음표·느낌표) 뒤에 공백이나 스트림 끝이 오면 그 지점까지를 한 문장으로 흘려보내고, 스트림이 문장 중간에서 끝나면 버퍼에 남은 것을 마지막 문장으로 흘려보낸다. 공백뿐인 조각은 내보내지 않는다(`AppendNarration` 이 빈 텍스트를 거부한다). `narrate(*, provider, model, ctx, check_summary, rulebook_display_name) -> Iterator[str]` 은 `build_gm_prompt` 로 프롬프트를 만들고 `provider.stream` 의 출력을 `chunk_sentences` 에 물려 문장을 하나씩 흘려보낸다. 호출한 쪽이 반복자를 다 소진한 뒤 `provider.last_result()` 로 토큰·시간을 가져간다.

**`cli/main.py`** — `turn` 하위 명령을 최상위에 더한다(`submit`/`replay` 와 나란히). 인자는 `--db`, `--session`, `--player`, `--text`, `--rulebook`(기본값은 기존 `roll` 파서와 같이 `DUNGEONWORLD_LIKE_ID` 를 import해서 쓴다 — 문자열을 다시 타이핑하지 않는다), `--provider`, `--model`, `--target`, `--modifier`(기존 `roll` 파서와 같은 `유형:값:출처` 형식) 이다. 흐름은 다음 순서로 **기존 여섯 명령을 그대로 재사용해** 돈다(새 명령 종류를 만들지 않는다):
    ① `DeclareAction` 을 제출하고 돌려받은 순번을 기억한다.
    ② `available_providers(os.environ)` 로 키를 확인하고 `get_provider` 로 어댑터를 만든 뒤 `classify` 를 부른다. 반환된 `AgentResult` 를 `RecordAiCall(agent_role="action_classifier", model=..., provider=..., prompt_tokens=..., completion_tokens=..., latency_ms=elapsed_ms, caused_by_seq=①의 순번)` 로 제출한다.
    ③ 후보가 하나도 없으면 판정 없이 진행한다는 한 줄을 찍고 그 자리에서 끝낸다(§4.7 의 「무브 없음」 경로. 이 갈래를 세 단계 확인 화면으로 넓히는 것은 03-04 의 몫이다). 후보가 있으면 첫 후보를 한 줄로 보여주고 표준입력에서 사람의 확인을 받는다. 확인·거부 어느 쪽이든 `ConfirmAction(system_suggestion={"move": 첫 후보의 무브, "stat": 첫 후보의 능력치}, player_confirmed=..., caused_by_seq=①의 순번)` 을 제출한다 — 사람 입력 없이 다음 단계로 넘어가는 갈래를 만들지 않는다(RIG-01). 거부되면 여기서 종료한다.
    ④ `ResolveCheck(caused_by_seq=③의 순번)` 을 제출하고 판정 결과 줄(눈·등급·목표값)을 먼저 출력한다.
    ⑤ `narrate` 가 흘려보내는 문장마다 그 자리에서 화면에 찍고 `AppendNarration(text=문장, chunk_index=0부터 1씩, caused_by_seq=④의 순번)` 를 제출한다.
    ⑥ 반복자가 끝나면 `provider.last_result()` 로 `RecordAiCall(agent_role="master_gm", ..., caused_by_seq=③의 순번)` 을 제출한다.
    `TurnContext` 는 CLI 가 만든다 — 시계 상태는 `rebuild_state` 가 돌려주는 `GameState.clock_segment` 에서, 최근 턴은 저장소에서 읽은 사건 중 선언·서사 텍스트만 뽑아 마지막 `RECENT_TURNS_LIMIT` 개로 잘라서, 장면 대상과 캐릭터 상태는 이번 단계에서는 룰북이 선언한 예시 엔티티에서 채운다(실험 준비물을 손으로 만드는 것은 EXP-01, Phase 5 의 일이다). `CommandRejected`/`SequenceConflict` 는 기존 `_cmd_submit` 과 같이 한 줄 오류 메시지 + 0이 아닌 종료 코드로 바꾼다 — 원시 역추적을 그대로 뱉지 않는다.
