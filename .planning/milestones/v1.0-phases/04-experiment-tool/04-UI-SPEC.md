# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope discipline (read first):** ROADMAP.md is explicit and repeated for this phase: *"화면은 만들지만 화면 설계는 하지 않는다"* — screen layout, componentry, and responsive design are out of scope for M0. This is a 4-person internal experiment tool, not a product. This contract therefore resolves only what's needed to unblock planning/execution without ambiguity (copy, minimal shape for the handful of real surfaces, the two explicitly-deferred discretion items) — it deliberately does not attempt a full design system, and the planner/executor should not read scope creep into it.

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable — 04-RESEARCH.md's Standard Stack locks a plain Vite `vanilla-ts` frontend with **no framework, no component library, no state library** (CONTEXT.md's Claude's-Discretion note: "화면 배치·컴포넌트 설계는 M0 범위 밖이므로 최소한만"). shadcn requires a React/JSX rendering model this stack decision already rejected — initializing it would contradict an upstream-locked technical decision, not add design consistency. | Font | System font stack: `-apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif` — zero custom font loading/build step, consistent with the "minimal frontend" discretion call in RESEARCH.md |

Registry safety gate: **not applicable** (no design-system tool initialized).

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Gap between a character-select row's name and its one-line archetype text |
| sm | 8px | Gap between stacked confirm/reject candidate cards; gap between clock segment digits and fail-counter digits in the header bar |
| md | 16px | Default padding inside cards/rows (character-select item, proposal card, narration feed padding) |
| lg | 24px | Section padding — header bar, action-input row container |
| xl | 32px | Vertical gap between major page regions (header bar → narration feed → action-input row) |
| 2xl | 48px | Top/bottom page margin on the character-select screen (its content is short and centers vertically) |
| 3xl | 64px | Not used this phase — no page is long enough to need page-level spacing at this scale |

Exceptions: one — all clickable targets (character-select rows, 확인/다시 쓰기 buttons, action-submit button, the character-sheet `<summary>` disclosure toggle) get a **44px minimum touch/click target height**, even where visual padding alone would produce something smaller. This is the standard touch-target floor, not a phase-specific design decision, and applies regardless of whether a session is used on a laptop or phone (RIG-07 doesn't constrain device type).

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 14px | 400 (regular) | 1.5 |
| Body | 16px | 400 (regular) | 1.5 |
| Heading | 20px | 600 (semibold) | 1.2 |
| Display | 24px | 600 (semibold) | 1.2 |

Usage mapping (so the executor never has to guess which role a piece of text uses):
- **Display (24/600):** the character-select screen's single top-of-page title only ("캐릭터를 선택하세요") — the one "first impression" moment this phase has.
- **Heading (20/600):** in-session section labels — the threat-clock/fail-counter readout, the character-sheet disclosure summary text ("내 캐릭터 시트").
- **Body (16/400):** narration feed text, the action-input field, character-select row names, confirm/reject button labels, character-sheet stat rows.
- **Label (14/400):** character-select row's one-line archetype/class line, the disconnected banner text, inline loading text ("AI가 생각하는 중…"), any secondary/meta text.

Exactly 4 sizes, exactly 2 weights — no third weight (no "bold" beyond semibold) is introduced anywhere in this phase.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` | Page background, narration feed background |
| Secondary (30%) | `#F1F3F5` | Header bar (clock + fail counter), character-select row background, character-sheet disclosure panel background, **and** the disconnected banner (see note below — no separate warning color is introduced) |
| Accent (10%) | `#2563EB` | Reserved for exactly three elements, nothing else: (1) the character-select screen's "이 캐릭터로 입장하기" button, (2) the propose/confirm card's primary confirm button ("이 행동으로 진행" / per-candidate "{move}"로 진행", see Copywriting Contract), (3) the action-input row's submit button |
| Destructive | `#DC2626` | Reserved, **unused this phase** — see Copywriting Contract's "Destructive confirmation" row: this phase has no delete/irreversible action. Declared for template completeness and to pre-empt any future phase reusing this token without redefining it |

Accent reserved for: the three buttons listed above only — never links, never the confirm/reject card's "다시 쓰기" button (that one uses default text-button styling, not accent, since it is a neutral redirect back to typing, not the primary action), never the disconnected banner.

**Disconnected banner color note:** the banner does not introduce a fourth "warning" color. It reuses the Secondary (30%) surface with bold Label-weight text — keeping the phase's palette exactly at the declared four tokens (60/30/10 + destructive-unused) rather than adding a semantic "amber/warning" color that the checker isn't expecting and that a 4-person experiment tool doesn't need.

## Screen Inventory (resolves CONTEXT.md's two explicit discretion items)

Four real surfaces exist this phase — no others should be built (see ROADMAP's "안 만드는 것" list: no character creation, no matchmaking/lobby, no safety-tool UI, no payments/accounts, no cosmetics).

### 1. Character-select screen (entry point, D-42/D-43)
- Shown only when no valid `gptrpg_character` cookie exists for this session; if the cookie is already present and valid, this screen is skipped entirely and the player lands directly on the session screen (D-43's "새로고침해도 다시 묻지 않는다").
- Layout: single column, vertically centered, `2xl` (48px) top/bottom margin.
- Display-role title: "캐릭터를 선택하세요".
- Below the title: a plain vertical list of `N` rows (N = however many characters are hand-authored per EXP-01, expected 2-4) — each row is a full-width clickable button showing the character's name (Body, 16/400) with its one-line archetype/class text directly beneath (Label, 14/400, `xs` gap). No portraits/images (cosmetics is out of scope).
- Clicking a row is the accent CTA action: "이 캐릭터로 입장하기" is the button's accessible label/tooltip; the row itself is the clickable surface (no separate confirmation step — selection is a single click, matching the "손으로 대체" lightweight spirit of this phase).
- On click: `POST /select-character`, cookie set (D-43), client navigates to the session screen.

### 2. Session/narration screen (main surface, RIG-04/RIG-05/RIG-07)
Single column, top to bottom, in this fixed order — no responsive grid/breakpoints are designed (out of scope):
1. **Disconnected banner** (conditionally rendered, D-40) — fixed to the very top of the viewport, full width, above everything else including the header bar. See Copywriting Contract for exact text and the dedicated note below for behavior.
2. **Header bar** (Secondary background, `lg` padding) — threat clock display ("위협 시계 {clock_segment}/{총 칸수}") and fail counter ("실패 카운터 {fails_since_clock}/3") side by side, `sm` gap between them. Both are plain text (Heading role), no dial/segment graphics — a custom clock-face SVG is explicitly not designed this phase (matches "화면 설계는 하지 않는다").
3. **Narration feed** — scrollable region (`overflow-y: auto`, fixed height = viewport minus header/input rows), `md` padding, chronological top-to-bottom. Auto-scrolls to the newest content on each poll unless the player has manually scrolled up (see UI Considerations row below — this exact behavior is flagged as a backstop, not a plain assertion).
4. **Action-input row** — a text `input` (Body role) plus one accent-colored submit button, `lg` padding, pinned below the feed.
5. **Confirm/reject proposal card** (Pattern 2 from RESEARCH.md) — appears inline directly beneath the action-input row only while a proposal is pending; disappears once confirmed/rejected. See "Confirm/propose interaction" below for the exact shape.
6. **Character sheet toggle** — a persistent `<details><summary>내 캐릭터 시트</summary>` disclosure in the header bar area. Collapsed by default; expanding it fetches and renders the read-only stat list inline (no modal, no separate route/page — native disclosure widget keeps this at zero additional JS/layout complexity, matching the minimal-frontend discretion call).

### 3. Disconnected banner — exact wording and behavior (D-40 discretion item)
- **Trigger:** ~10 consecutive polling failures (~10s at the 1-2s interval, D-40) since the last successful poll.
- **Placement:** fixed top of viewport, full width, above the header bar — the first thing visible, since RIG-07's whole point is "does everyone see the same thing," and a stale narration feed without a visible reason is the single worst experience this phase could ship.
- **Copy:** see Copywriting Contract table, row "연결 끊김 배너."
- **Dismissal:** none manual — the banner disappears automatically and silently on the next successful poll. No separate "재연결됨" success toast is designed; the banner's disappearance is itself the "you're back" signal, which avoids inventing a second transient-copy state for a 4-person tool where over-notifying is worse than under-notifying.
- **Non-goal:** no reconnect button, no manual retry control — the poll loop already retries every 1-2s on its own; a manual retry button would just race the automatic one.

### 4. Confirm/propose interaction — minimal treatment (RESEARCH.md Pattern 2)
This ports Phase 3's already-decided three-tier confirmation (`Proposal.tier`: none/single/several, D-16/D-37, MAX_CANDIDATES=3) from CLI prompts to inline web cards — it does not redesign the underlying tiering logic, only its on-screen shape:
- **Tier `none`** (no move recognized): render only the "인식된 행동이 없어요" copy (see Copywriting Contract) with no confirm button — just the existing action-input row, ready for the player to retype.
- **Tier `single`** (exactly one candidate): one card showing the proposed move + stat, with two buttons — "이 행동으로 진행" (accent) and "다시 쓰기" (default/neutral, not accent, not destructive — declining a proposal is a normal judgment call, not a hazardous action).
- **Tier `several`** (2-3 candidates, capped at MAX_CANDIDATES=3): up to three candidate cards stacked vertically (`sm` gap between them), each with its own confirm button labeled `"{move}"로 진행` — the candidate's move name is embedded directly in the label (e.g. `"강타"로 진행`) so each of the up to three stacked buttons is distinguishable by copy alone, not just position; one shared "다시 쓰기" link/button beneath the stack for "none of these, let me retype."
- While the classifier call is in flight (declare submitted, proposal not yet returned): the submit button shows a disabled state with inline Label-role text "AI가 분류하는 중…" next to it — reuses the same "explain the wait" convention as narration loading (Phase 3's D-26 5-second-progress-indicator idea, ported to web).
- **Classifier failure after retry:** renders identically to tier `none` (Phase 3's D-29 already decided not to distinguish "no match" from "classifier failed" at the UI layer) — no separate error card for this case.
