# Requirements: GPTRPG

**Defined:** 2026-07-30
**Core Value:** 이야기가 어떻게 끝나는지 보고 싶어서 일주일 뒤에 다시 접속한다

---

## ⚠️ 이 마일스톤이 무엇인가

**v1 = 마일스톤 0의 킬 크리테리아 실험.** 제품이 아니다.

설계는 2026-07-30에 닫혔지만 실험은 하지 않았다. 이 문서의 요구사항은 전부 **"AI가 진행하면 재미있나"와 "원가가 사업 가능 범위인가"에 답하기 위해 필요한 최소한**이다. 두 질문 중 하나라도 실패하면 프로젝트가 멈춘다.

요구사항은 새로 만들어낸 것이 아니라, 잠금된 결정 문서(`docs/GPTRPG-M0-decisions.md`)가 **최소 도구 범위 표·측정 표·실험 설계·가설 표 형태로 이미 적어 둔 것**을 항목으로 쪼갠 것이다. 각 항목에 원 위치를 남겼다.

> 원본에 PRD로 분류된 문서는 없다. 출처는 전부 잠금된 결정 문서와 기획 명세서다.

## v1 Requirements

### 실험 도구 (RIG) — 최소 도구 범위의 「필요」 열

> 출처: D30 최소 도구 범위 표 · 기획 명세서 §12.3
> **제품이 아니라 실험 도구다.** 화면이 투박해도 "재미있나"를 재는 데 방해만 안 되면 된다.

- [x] **RIG-01**: 플레이어가 자유 문장으로 행동을 말하면 시스템이 무브와 능력치를 골라 보여주고, 플레이어가 확인하면 진행된다 (AI가 제안하고 사람이 확인하는 혼합형 — 자동 확정 금지)
- [x] **RIG-02**: 주사위와 판정 계산이 순수 코드로만 일어나며 AI가 수치를 바꿀 수 있는 지점이 없다
- [x] **RIG-03**: 판정 결과가 나온 뒤 AI가 그 결과를 서사로 풀어 문장 단위로 흘려보낸다
- [x] **RIG-04**: 위협 시계의 현재 칸과 판정 실패 누적 카운터가 화면에 보이고, 실패 3회 도달 시 시계가 강제로 한 칸 진행된 뒤 카운터가 초기화된다
- [x] **RIG-05**: 플레이어가 자기 캐릭터 시트를 읽기 전용으로 볼 수 있다
- [x] **RIG-06**: 모든 사건이 순서대로 기록되고 현재 상태는 그 기록에서 만들어진다 (제자리 수정 방식이 아니다)
- [x] **RIG-07**: 링크 하나로 여러 명이 같은 세션 화면을 동시에 보고, 끊겼다 다시 들어와도 놓친 부분이 이어 붙는다
- [x] **RIG-08**: 판정 방식이 서로 다른 룰북 두 개(2d6 등급식 / d100 롤언더)와 그 룰북들의 적이 코드 수정 없이 데이터로만 들어간다

### 계측 (MEAS) — 가설에 답할 숫자가 저절로 쌓이게

> 출처: D30 측정 표 · D28 · D33 · D11 · D22
> 사건이 전부 기록에 남으므로 계측은 대부분 공짜다. 빠뜨리면 안 되는 것은 **기록에 필드를 빼먹지 않는 것**뿐이다.

- [x] **MEAS-01**: 세션이 끝나면 실제 토큰 소모량과 실제 턴 수가 자동으로 집계된다 (한국어 기준 실측 — 기존 원가 계산 전체를 이 숫자로 보정한다)
  - 토큰은 **입력·출력·캐시 적중 세 칸으로 나눠** 센다. 합계 하나로는 원가가 안 나온다(단가가 4~5배 다르다). 캐시 적중이 0이면 「적중 없음」과 「제공자 미보고」가 구분되지 않으므로 그때의 원가는 상한선이다
- [x] **MEAS-02**: 두 지점의 응답 속도가 자동 기록된다 — 문장 입력 → 행동 확인 표시, 확인 → 서사 첫 글자. 첫 글자 5초 초과 시 진행 표시가 뜨고, 15초 초과 시 판정 결과가 먼저 나가고 서사가 뒤이어 붙는다
  - 두 지점이 **집계까지 나온다.** 앞엣것은 분류기 호출 시간, 뒤엣것은 `caused_by_seq` 사슬(확인→판정→서사)을 거슬러 두 기록 시각을 뺀 값이다 — `master_gm`의 호출 시간은 서사 **전체** 시간이라 「첫 글자」와 다른 값이므로 섞으면 2초 목표를 판정할 수 없다. 중앙값·최대값과 D-33 두 문턱(5초·15초) 초과 횟수를 함께 낸다
  - **자동 저장본에는 이 칸이 비어 있다** — 세션 후 `gptrpg report`를 한 번 쳐야 채워진다
- [x] **MEAS-03**: 판정 실패 횟수 대비 위협 시계 진행 횟수가 기록에서 자동 집계된다 ("실패는 많은데 시계가 안 돈다"를 사후에 잡아낼 수 있어야 한다)
- [x] **MEAS-04**: 플레이어가 실제로 친 문장이 시스템의 제안·플레이어의 확인 여부와 함께 남아 정답 데이터가 된다 (세션당 약 80개)
- [ ] **MEAS-05**: 1세션이 끝난 시점의 상황을 손으로 쓴 요약으로 만들 수 있고, 2세션 시작 때 참가자가 그것만 읽고 이어할 수 있다
- [x] **MEAS-06**: 캐릭터를 만든 직후 "당신 캐릭터 어떤 사람이에요?"라고 물어 대답을 기록한다 (한 문장으로 말할 수 있으면 애착이 붙은 것이다)

### 실험 운영 (EXP) — 설계대로 돌린다

> 출처: D30 실험 설계 블록 · 기획 명세서 §12.2

- [x] **EXP-01**: 실험 준비물이 손으로 만들어져 있다 — 위협 시계 1개(4칸) / 룰북 1개(판정 종류 10개 남짓) / 캐릭터 4개 중 절반
- [ ] **EXP-02**: 참가자 4명이 모인다 — TRPG 경험자 2명 + **비경험자 2명**(비경험자가 핵심이다. 타깃이 초심자다). 우리는 진행자 노릇을 하지 않고 관찰만 한다 (개입하면 "AI가 진행하면 재미있나"를 못 잰다)
- [ ] **EXP-03**: 1세션 3~4시간 → **1주 간격** → 2세션 3~4시간을 실제로 진행하고, 2세션에 몇 명이 왔는지와 세션을 완주했는지 흐지부지됐는지를 기록한다
- [x] **EXP-04**: 비경험자 2명이 화면 없이 안내만 받아 30분 안에 캐릭터를 만든다 (만들기 화면은 M0에서 만들지 않는다)

### 가설 판정 (HYP) — 계속할지 여기서 정한다

> 출처: D30 가설 표 · 기획 명세서 §12.1
> 각 항목의 실패 조건은 문서가 이미 숫자로 못박아 둔 것이다.

> **채점 규칙은 실험 전에 고정했다** — `docs/experiment/hypothesis-scoring-rules.md`.
> 문턱값은 D30·D28이 정한 그대로 두고, **어떤 숫자를 어디서 뽑아 어떻게 읽는지**를 결과가
> 나오기 전에 못박은 문서다. 아래 항목의 「단, …」 줄은 전부 그 문서에서 온다.

- [ ] **HYP-01** (**진짜 킬**): AI가 진행하면 재미있다 — 참가자 대부분이 두 번째 세션에 왔다. *실패하면 프로젝트를 멈춘다*
  - **단, 이번 두 세션으로는 판정하지 않는다 (제안 D-59, 승인 대기).** 교란 셋 — 간격 1~3일(D-57 이탈) / 무료 티어 모델(D-58) / 오너가 참가자 겸 관찰자라 **실질 표본 3명**(D-55·D-56의 귀결). 어느 방향으로 나와도 D30의 판정 규칙을 적용할 수 없다. **유보는 통과가 아니다** — 조건을 갖춘 재실험이 M1 착수 전에 필요하다
- [ ] **HYP-02** (재설계): 위협 시계가 AI의 봐주기를 막는다 — 시계가 도는 동시에 이야기가 억지스럽지 않다
  - **단, `failure_to_clock_ratio`로 판정하지 않는다 (제안 D-60, 승인 대기).** D-21의 진행 규칙 세 가지 중 ①실패 누적만 구현되어 있어 비율이 **항상 3.0에 고정**되고 정보량이 0이다. 판정은 관찰 기록(시계 진행마다 「이어졌다/억지였다」 한 줄)으로 하고, 시계 진행이 2건 이하면 표본 부족으로 유보한다. ②조건 트리거·③AI 선택 구현은 M1
- [x] **HYP-03** (전략 변경): 룰북을 데이터로 표현할 수 있다 — 두 번째 룰북이 들어간다. *실패하면 유저 콘텐츠 마켓이 소멸한다*
- [ ] **HYP-04** (전략 변경): 자유 텍스트 입력이 쓸 만하다 — 정답 데이터 300개에서 「첫 제안이 맞음(엔터 한 번)」 + 「후보에 있음(클릭 한 번)」 합쳐 **95% 이상**, 「직접 찾아야 함」 **30% 미만**. *실패하면 "말하듯 플레이" 셀링포인트가 소멸한다*
  - **단, 세션 실측값에 문턱을 적용하지 않는다.** 이번 분류기는 무료 8B라 그 성능이 개념 타당성으로 읽힌다. 문턱은 **사람이 라벨을 다시 붙이고 배포 후보 모델로 재분류한 값**에 적용한다(D19·D28이 이미 그 방법을 적어 뒀다). 세션 실측은 `gptrpg report`의 `friction`이 자동으로 낸다 — 참고값
- [ ] **HYP-05** (**진짜 킬**): 원가가 사업 가능 범위 안이다 — 실측으로 1인 1시간당 **$1 이하**이거나, 넘더라도 저가 모델로 내려간다. *두 조건이 함께 실패하면 프로젝트를 멈춘다*
  - **단, 계산식과 기준 단가를 1세션 시작 시각에 못박는다.** 입력·출력·캐시 토큰을 따로 세어 각자의 단가를 곱한다(합계 하나로는 계산이 성립하지 않는다). 최상급·저가 두 기준을 **다 계산한다** — 멈춤 조건이 「$1 초과 **그리고** 저가로도 안 내려감」이라 하나만 계산하면 판정 자체가 불가능하다. 캐시 적중이 0이면 그 값은 **상한선**이다
  - **추가로 낼 숫자(멈춤 판정에는 안 쓴다):** 무료 체험 1팀당 원가 × 1,000팀. D20·D21이 확정한 구조가 「첫 에피소드 무료」이므로 먼저 터지는 것은 유료 유저의 단위 원가가 아니라 획득 원가다 — D21 표가 이미 $2,500~6,000을 적었는데 킬 기준에는 없다. **D-61로 실험 범위를 그 상품 단위에 맞췄으므로 이 값은 추정이 아니라 실측이다** — 집계의 `episodes` 칸이 시계 칸별 누적을 남기므로 1~2칸 줄을 그대로 읽는다(세션 합계를 쓰면 무료 구간 밖의 몫이 섞인다)
- [ ] **HYP-06** (재설계): TRPG 비경험자가 룰북 없이 시작할 수 있다 — 비경험자 대부분이 캐릭터 만들기를 끝냈다
  - **단, 표본이 2명이라** 둘 다 완성=통과 / 한 명=유보 / 둘 다 실패=재설계로 미리 갈라 뒀다

## v2 Requirements

게이트를 통과한 뒤에 다룬다. 지금 로드맵에는 들어가지 않는다.

### M1 — 실시간 파티 (친구 초대 링크)

- **M1-01**: 친구 초대 링크로 방을 열고 파티가 실제로 플레이한다 (공개방 매칭 없음)
- **M1-02**: d20 판정 방식 추가 (유저 콘텐츠 수요 1순위)
- **M1-03**: 시나리오 형식 확장 — 노드 그래프 · 클루 웹
- **M1-04**: 룰북 파일 업로드 + 구조화 초안 생성 + 유저 확인 (확인할 때 구조화 데이터가 아니라 **시험 판정 결과**를 보여준다)
- **M1-05**: 안전 장치 1~3층 — 방 생성 시 톤·선·장막 설정 / 정지 카드 / AI 출력 검사
- **M1-06**: 사람이 오고 가는 세 경우를 다르게 처리 — 잠깐 자리 비움 / 오늘 중도 이탈 / 영구 이탈
- **M1-07**: 자동화율 목표 — 룰북 100개 중 90개가 자동화율 80% 이상, 룰북 등록 시 자동 산출해 표시
- **M1-08**: M1 착수 시 정할 것 — 룰북 데이터 필드 단위 규격 / 효과 원자 연산 최종 목록 / 적 상태값 묶음의 구체 형태 / 검색 기반 기억 주입 여부 / 저가 모델 A/B
- **M1-09**: **위협 시계 진행 규칙 ②조건 트리거 · ③AI 선택 구현.** D-21은 세 가지 병용을 확정했는데 M0에는 ①실패 누적만 있다. 그 결과 `failure_to_clock_ratio`가 항상 문턱값에 고정되어 봐주기 관측 지표로 쓸 수 없다 — D-21이 「①이 관측 지표를 공짜로 만든다」고 적은 것은 ③이 함께 있을 때의 이야기였다. 세션 중에 진행자가 시계를 손으로 돌릴 안전한 경로(웹 경로)도 여기서 같이 만든다 — 지금은 CLI `submit clock`뿐이고 서버와 쓰기 경합이 난다
- **M1-10**: **폴링 읽기 비용.** 매 요청이 사건 전체를 접어 상태를 만든다(D-08, 중간 저장 없음). 요청당 두 번 읽던 것을 한 번으로 줄였지만 구조는 그대로다 — 스냅샷 또는 증분 폴링이 필요하다
- **M1-11**: **재개(D-11)의 검증 기준을 실제로 잰다.** D-11이 검증 기준으로 못박은 것은 「**3주** 뒤에 읽고 이어할 수 있는가」인데, M0 실험은 간격이 1~3일이고 요약도 손으로 쓴 3~5문장이다(MEAS-05). D-11이 「온라인 TRPG 최대 이탈 원인」이라고 규정한 것을 M0에서는 사실상 재지 않고 넘어간다 — 의도된 축소지만 M1이 반드시 되돌아와야 하는 자리다
- **M1-13**: **D-31이 「접지 않는다」고 적은 것이 애초에 주입되지 않는 문제를 푼다.** D-31은 안전장치 절에서 관계 장부(D-11)와 저장소 색인을 「접지 않는 것」으로 명시했는데, **매 턴 넣는 네 가지 안에 둘 다 없다.** 그래서 캐스트의 **이름·상태값**은 매 턴 들어가지만(`THREAT_CAST`) 「그 인물과 무슨 일이 있었는지」는 최근 10턴 밖으로 나가면 사라진다. 3~4시간 세션에서 10턴은 20~30분 분량이다 — 세션 후반에 촌장과 나눈 대화를 AI가 기억하지 못한다. `rulebooks/threat_clocks.py`의 주석이 이미 이 점을 눈치채고 「최근 대화가 10턴만 유지되므로 이 흔적이 사실상 유일한 장기 기억 장치다」라고 적어 뒀다. D-9가 「징조 목록이 곧 복선, 기억이 아니라 DB 행이라 안 잊는다」고 자랑한 성질이 시계 칸 설명에만 걸려 있고 NPC 관계에는 안 걸려 있다. **관계 장부 한 줄 색인을 「세션 고정」 프롬프트 층에 넣는 것이 유력하다** — 그 층은 장면이 바뀔 때만 변하므로 캐싱에도 유리하다. 최근 턴 수(초기값 10)는 D-31이 이미 「실측으로 조정」으로 열어 뒀다
- **M1-12**: **`context_summarizer` 구현.** D-17이 정한 에이전트 넷 중 이것과 `onboarding_agent`가 코드에 없다. `onboarding_agent`는 D30이 「캐릭터 만들기 화면 안 필요」로 잘라 정합하지만, `context_summarizer`가 없으면 D-31의 「턴당 토큰 예산 상한, 넘치면 오래된 대화부터 요약으로 접는다」가 미구현이다(지금은 그냥 10턴 자르기). **M0 원가 실측은 「압축 없는 상태」의 값**이며, 압축이 붙으면 호출 수는 늘고 프롬프트는 줄어 방향이 갈린다 — Phase 6이 그 사실을 알고 읽어야 한다

### 법무로 넘긴 것

문서 스스로 "법적 결론이 아니다"라고 못박은 영역이다. 개발 요구사항이 아니라 외부 판단이 필요한 항목이다.

- **LAW-01** (높음, 출시 전 필수): AI가 실시간으로 만드는 콘텐츠의 게임물 등급 분류 — 사전 심의가 구조적으로 불가능한 서비스다
- **LAW-02** (높음, 수익 모델의 전제): AI 생성물의 권리 귀속을 약관으로 어떻게 설계할 것인가
- **LAW-03** (높음, 유저 업로드 개시 전): 플랫폼 책임 제한 요건 — 신고·삭제 절차의 법적 요건
- **LAW-04** (중간, 출시 전): CC-BY 고지문의 문구와 게재 위치
- **LAW-05** (중간): 해외 서비스 시 각국 요건 — 초기 타깃에 국외가 포함되어 있다
- **LAW-06** (낮음, M2): 낯선 사람 매칭 시 성인 인증 의무

## Out of Scope

| 항목 | 사유 |
|---|---|
| 캐릭터 만들기 화면 | 캐릭터는 손으로 준비하거나 구두 안내로 만든다 (최소 도구 범위 「안 필요」) |
| 매칭·로비 | 링크 하나로 대체 |
| 코스메틱 | 실험이 재미를 재는 데 관여하지 않는다 |
| 룰북 저작 도구 | 룰북 데이터를 손으로 쓴다 |
| 리캡 자동 생성 | 손으로 써서 보여줘도 "이어할 수 있나"는 검증된다 |
| 안전 장치 UI | 실험에서는 구두로 대체 (제품에서는 M1 필수) |
| 결제·계정 | 실험 참가자는 4명이다 |
| 좌표계·전술 그리드·시야 계산 | 첫 타깃 룰북에 그리드가 없어 놓을 보드 자체가 없다 (M4로 이동, 폐기 아님) |
| 파티 채팅·보이스·친구 시스템 | 플레이어 간 대화는 외부 메신저에서 끝난다 |
| 발언권 락 · 순서 강제 정렬 · 짧은 리액션 타이머 | 조율은 외부 메신저에서 끝난다. 선착순 락은 말 많은 사람이 독식한다 |
| 신뢰도 임계값 기반 폴백 화면 | 모든 분류가 어차피 플레이어 확인을 거치므로 임계값이 불필요하다 |
| 검색 기반 기억 주입 | 검색 품질이라는 실패 지점을 추가하면 "재미있나"를 못 잰다 |
| 자체 호스팅 | M0의 결정 사항이 아니다. 규모가 붙기 전까지 API보다 비싸거나 비슷하다 |
| 룰북별 전용 어댑터 | 유저가 룰북을 올릴 때마다 코드를 짤 수 없다 |
| 룰북 100% 재현 / 할루시네이션 완벽 방어 | 구조적으로 불가능하다. 목표를 투명성과 정정 가능성으로 교체했다 |
