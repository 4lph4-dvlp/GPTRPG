## 1. 제품 정의

### 1.1. 타깃 유저

> TRPG를 잘 모르고, 룰북을 읽을 시간도 없지만,
> 회사·학교가 끝나고 **친구들 또는 처음 보는 모험가들과 실시간으로 몰입할 세계**를 원하는 사람.

플레이 시간은 고정 세션이 아니라 **하고 싶은 만큼**이다. 1시간일 수도, 3시간 이상일 수도 있다.

### 1.2. 해결하는 문제

v1은 "구인난, 복잡한 룰북, GM의 독박 노동"을 들었다. 실제 병목을 다시 정의한다.

| 문제 | 우리의 해법 |
|---|---|
| **룰북을 읽어야 시작할 수 있다** | 숫자를 서술로 번역해 보여준다. 룰북 지식 대신 결과를 보여준다 |
| **GM을 할 사람이 없다** | AI가 GM. 단, 판정은 코드가 한다 |
| **언제 다시 모일지 못 정한다** | 세션 개념을 버린다. 언제든 끊고 이어한다 |
| **낯선 사람과 하기가 불안하다** | 안전 장치를 기본으로 (M2) |

### 1.3. 세 가지 전제

1. **플레이어끼리의 대화는 외부 메신저에서 일어난다** (디스코드·카카오톡·텔레그램). 플랫폼은 소셜 레이어가 아니며, 입력창은 행동 선언용이다
2. **언제든 끊고 이어할 수 있다.** 한 단계를 끝내야만 종료할 수 있는 게 아니다
3. **처음 보는 사람과의 플레이를 전제한다** (M2). 매칭·안전 장치·드롭인/아웃이 필수가 된다

### 1.4. 정체성 우선순위

모든 설계 결정은 이 표를 기준으로 채점한다.

| | 요소 | 판정 |
|---|---|---|
| ① | 룰 정합성 (룰대로 정확히 굴러감) | **대체 가능** — 투명성 + 정정 가능성으로 |
| ② | **결과의 무게** (실패가 아프고 캐릭터가 죽을 수 있음) | **양보 불가** |
| ③ | **플레이어 주체성** (뭐든 시도 가능, 시스템이 막지 않음) | **양보 불가** |
| ④ | **불확실성** (주사위가 진짜 무작위, 아무도 못 건드림) | **양보 불가** |
| ⑤ | **공동 창작** (세계가 GM만의 것이 아님) | **양보 불가** |
| ⑥ | 전술적 깊이 (수치·위치 계산으로 이기는 재미) | **연기** — M4 |

### 1.5. 마케팅 전략 (제품 정의 아님)

스트리머 노출을 통한 진입장벽 완화. **채널이며 제품 요구사항을 규정하지 않는다.** 스트리머 관련 요구(짧은 타이머, 관전자 뷰)는 진행 정책의 프리셋 하나로 흡수한다.

관전자는 읽기만 하므로 **원가가 0이다.** 스트리머 전략은 원가 측면에서 공짜다.

## 2. 설계 원칙

### 2.1. 세 개의 층 — 모든 기능은 어느 층인지 밝힌다

| 층 | 무엇 | 예 |
|---|---|---|
| **① 플랫폼 기능** | 룰북과 무관하게 우리가 제공 | 안전 장치, 끊고 이어하기, 이벤트 기록, 매칭 |
| **② 표현 어휘** | 룰북이 말하는 것을 담는 그릇 | 7가지 동작, 판정 방식 인터페이스, 효과 표현 |
| **③ 룰북 규칙** | 룰북 설계자가 정한 것 | 성장·죽음·장비·회복의 구체적 규칙 |

**③을 ①에 올리면 다른 룰북이 망가진다.**

### 2.2. 원칙 1 — LLM은 파서일 뿐, 저지가 아니다

LLM은 **닫힌 집합 분류**와 **서술**만 한다. 판정·연산에는 닿지 않는다.

```
어떤 판정이 발동하는가?   → 분류기 + 재량 판정 계층   (LLM)
무슨 주사위를 굴리는가?   → 판정 방식 + 효과 표현     (순수 코드)
실제 굴림                → 암호학적 난수 생성기       (순수 코드)
결과 해석                → 판정 방식                (순수 코드)
결과 묘사                → GM 에이전트              (LLM, 수치는 못 바꿈)
```

> **LLM은 난수를 만들지 못한다.** "1~20 중 하나"를 시키면 7과 17이 비정상적으로 많이 나온다. 주사위에 LLM이 관여하면 ④ 불확실성이 그 순간 깨진다.

### 2.3. 원칙 2 — 판정 방식은 코드, 룰북은 데이터

판정 방식(커널)은 소수 정예로 유지하며 우리만 추가한다. 룰북은 방식 하나를 선택하고 나머지를 선언적으로 정의한다.

> v1의 "룰북별 전용 어댑터" 방침을 폐기한다. UGC 룰북 공유가 제품에 포함되므로, 유저가 룰북을 올릴 때마다 우리가 코드를 짤 수 없다.

### 2.4. 원칙 3 — 룰북 설계자의 의도를 덮어쓰지 않는다

> 룰북은 설계자의 밸런싱과 세계 설계의 결과물이다. 우리가 표현하지 못하는 규칙은 **"자동화율이 낮다"로 정직하게 표시하고 재량 판정으로 넘긴다.** 편의를 위해 우리 규칙을 대입하지 않는다.
>
> 특히 **성장 속도 · 죽음의 관용 · 자원 관리의 엄격함**은 룰북의 난이도 곡선 그 자체다. 여기에 손대면 게임이 다른 게임이 된다.

- D&D 5e의 경험치는 **적의 난이도 등급과 조우 예산에 묶여 있다**
- **OSR 계열 던전 탐험에서는 횃불과 식량이 게임 그 자체다**
- **크툴루 계열은 조사자가 죽거나 미치는 것이 설계 의도다**

**첫 타깃이 던전월드라는 이유로 던전월드의 규칙을 플랫폼에 박지 않는다.**

### 2.5. 원칙 4 — 재방문 동기는 이야기에서 나온다

> **위협 시계가 돌고 있고, 아직 멈추지 않았다.**

성장·보상 시스템을 재방문 유인으로 설계하지 않는다. **성장이 없는 룰북도 정상 지원해야 한다.**

### 2.6. 원칙 5 — 완벽한 방어가 아니라 투명성

| v1 목표 | v2 목표 |
|---|---|
| 룰북을 100% 정확히 재현한다 | **틀렸을 때 유저가 알아챌 수 있고, 고칠 수 있다** |
| AI 할루시네이션을 완벽 방어한다 | **AI가 계산한 것과 판단한 것이 구분되어 보인다** |

100% 재현은 구조적으로 불가능하다 — 룰북은 자연어로 쓰인 열린 시스템이고 "적절하다고 판단되면" 같은 문구가 곳곳에 있다. 어떤 VTT도 20년간 이걸 못 풀었고, **인간 GM도 100% 재현하지 않는다.**

문제의 성격은 정확도가 아니라 **신뢰**다. 필요한 것은 세 가지다.

1. **판정 근거 표시** — 모든 판정에 근거를 접어둔 채로 붙인다
   ```
   🎲 위험을 무릅쓰다 — 강한 성공 (10+)
     ▸ 판정 내역:  2d6 [4,5]=9 + 민첩 +2 = 11 → 10+ 강한 성공
                  근거: 룰북 p.63 · 자동 처리
   ```
2. **자동/재량 구분 표시** — `🎲 자동 처리` vs `⚖️ GM 재량 판정`
3. **정정 가능성** — 방장이 판정을 뒤집고, 홈브루로 저장할 수 있다

## 3. 아키텍처

### 3.1. 4계층 구조

```
┌──────────────────────────────────────────────────────┐
│  전송 어댑터        (게임 로직 0줄. 교체 가능)          │
│   WebSocket │ REST │ 푸시알림 │ 관전자 뷰              │
└──────────────────────┬───────────────────────────────┘
                       │  명령 투입 ↓ / 이벤트 구독 ↑
┌──────────────────────▼───────────────────────────────┐
│  세션 액터          (세션당 1개, 유일한 직렬화 지점)     │
│   명령 수신 → 검증 → 이벤트 발행                       │
│   진행 정책 주입 (타이머·순서·리액션 윈도우)             │
└──────────────────────┬───────────────────────────────┘
┌──────────────────────▼───────────────────────────────┐
│  규칙 코어          (순수 함수. I/O 없음. 시간 개념 없음)│
│   판정 방식 · 효과 표현 · 주사위 엔진                   │
└──────────────────────┬───────────────────────────────┘
┌──────────────────────▼───────────────────────────────┐
│  이벤트 로그 (append-only) + 파생 상태 스냅샷           │
└──────────────────────────────────────────────────────┘
```

**불변 규칙 3개**

1. **규칙 코어는 시간을 모른다.** 타이머·접속 상태 개념이 들어가면 안 된다
2. **세션 액터가 유일한 쓰기 주체다.** 세션당 단일 직렬화 지점으로 동시성 문제를 구조적으로 제거
3. **모드는 코드 경로가 아니라 진행 정책 설정값이다.** 새 모드 추가 = 표에 열 하나 추가

### 3.2. 이벤트 소싱 — 되돌릴 수 없는 결정

> **모든 사건을 순서대로 기록하고, 현재 상태는 그 기록을 훑어서 만든다.**

CRUD 제자리 변경으로 먼저 짜면 재접속 동기화·리플레이·비동기 참여·관전자 합류·다시보기가 **전부** 나중에 불가능해진다. 이벤트 소싱으로 시작하면 이 다섯이 같은 메커니즘 하나로 해결된다.

**부수 효과:** 계측이 공짜다. 모든 판정·시계 진행·GM 대응 선택이 로그에 남으므로 사후 집계가 가능하다. M0에서 할 일은 **이벤트 스키마에 필드를 빠뜨리지 않는 것**뿐이다.

### 3.3. 진행 정책

| | 스트리머 | 일반 파티 | 솔로 | 비동기 |
|---|---|---|---|---|
| 턴 타이머 | 45~60초 | 180초 | 없음 | 없음 |
| 순서 강제 | ON | ON | 해당없음 | OFF |
| 리액션 윈도우 | 5초 | 15초 | 인라인 | 알림·무기한 |
| 접속 전제 | 전원 | 전원 | 1인 | 없음 |

### 3.4. 에이전트 4개

v1의 서브에이전트 10개를 4개로 축소한다.

| 에이전트 | 티어 | 역할 |
|---|---|---|
| `action_classifier` | 경량 | 자유 텍스트 → 무브 + 능력치 분류 + 신뢰도 |
| `master_gm` | **M0은 최상급** | GM 대응 선택 + 서사 생성 |
| `onboarding_agent` | 중형 | 캐릭터 만들기 안내 |
| `context_summarizer` | 경량 | 배경 압축 + 리캡 생성 |

**삭제·강등된 것:** 전투 파서(통합) / 리액션 분류기(리액션 큐 삭제) / 이니셔티브 정렬기(던전월드에 이니셔티브 없음) / 주사위 서술기(GM에 병합) / 엔티티 장부 관리자(코드로 강등) / 룰 해석기(보류, 대형 룰북 등장 시 부활)

**메시지 버스도 축소.** gRPC + Redis Streams 이중 구성은 과하다. 세션 액터가 유일한 직렬화 지점이므로 인프로세스 함수 호출로 충분하다.

**턴당 LLM 호출: 평균 1.5회** (판정 없는 행동이 절반 이상). v1은 3~4회였다.

### 3.5. 모델 전략

**모델을 하나로 통일해 판단하지 않는다.**

| | `action_classifier` | `master_gm` |
|---|---|---|
| 난이도 | 낮음 | 높음 |
| 검증 | **객관적 가능** (정답률) | 주관적 |
| 원가 비중 | 5% | **95%** |
| 하향 시점 | **M0에서 바로 A/B 가능** | 품질 검증 도구 확보 후 |

- **프로바이더 추상화 계층을 M0에 넣는다.** 에이전트별 모델이 설정값이어야 한다
- **자체 호스팅은 M0의 결정 사항이 아니다.** TRPG는 이용률 패턴이 최악(저녁 8시~자정 집중)이라 실효 원가가 이론값의 3~4배가 된다
- **한국어 서사 품질이 특수 변수다.** 영어 벤치마크는 참고가 안 된다

### 3.6. 통신

- **문장 청크 전송.** 토큰 단위 스트리밍 폐기 (v1 판단 유지)
- 각 패킷에 순번 부여, 재접속 시 누락분 델타 재전송

**응답 속도 목표 — 사람이 기다림을 느끼는 두 지점에 각각 둔다**

| 구간 | 목표 |
|---|---|
| 문장 입력 → 행동 확인 표시 | 0.5초 |
| 확인 → GM 서사 첫 글자 | 2초 |
| 완결까지 | 목표 없음 (스트리밍이므로 체감은 첫 글자에서 결정된다) |

v1의 "E2E 3초"는 완결 기준이었고 달성 불가능하다.

**초과 시 행동** — 목표와 타임아웃 사이의 시간에 화면이 무엇을 하는지 정해두지 않으면 구현 때 아무 동작이나 들어간다.

| 상황 | 화면 |
|---|---|
| 첫 글자가 5초 초과 | 진행 표시를 띄운다 |
| 15초 타임아웃 | **판정 결과(주사위·성공/실패·시계 변화)를 먼저 내보내고, 서사를 뒤이어 붙인다** |

주사위와 판정은 순수 코드라 서사보다 먼저 끝나 있다. 목표는 "AI가 느려도 게임이 멈추지 않는다"다.

### 3.7. 개인 정보 분리

`master_gm` 출력에 가시성 필드를 둔다.

```json
{ "visibility": "public" }
{ "visibility": "private", "to": ["player_3"] }
```

이벤트 소싱과 궁합이 좋다. M4에서 시야 계산이 들어와도 같은 메커니즘을 재사용한다.

### 3.8. 기억 주입 규칙 — 장면에 있는 것만 넣는다

만난 인물·물건·단서는 계속 쌓인다. v1은 이것을 **매 턴 전부 보여준다**고 설계했다. 장기 캠페인에서 프롬프트가 터지고, 목록이 매 턴 바뀌므로 캐싱도 깨져 원가 계산의 전제가 무너진다.

**매 턴 넣는 것은 네 가지다.**

| 매 턴 넣는 것 |
|---|
| 현재 장면에 등장한 대상 |
| 내 캐릭터 상태 |
| 위협 시계 상태 |
| 최근 대화 몇 턴 (초기값 10턴, 실측으로 조정) |

나머지 저장소는 **이름 + 한 줄 색인만** 보인다. AI가 특정 항목의 상세를 필요로 하면 요청하고, 코드가 꺼내서 다음 턴에 넣는다. **AI가 저장소 전체를 훑는 경로는 만들지 않는다.**

턴당 토큰 예산 상한을 안전장치로 둔다. 넘치면 오래된 대화부터 요약으로 접되, 다음 세 가지는 접지 않는다.

| 접지 않는 것 | 왜 |
|---|---|
| 저장소 색인 | 접히면 AI가 무엇을 요청할 수 있는지 모른다 |
| 위협 시계 상태 | 원칙 4 — "시계가 아직 멈추지 않았다"가 재방문 동기다 |
| 관계 장부 | 원칙 4 — 재방문 동기의 재료는 시계만이 아니라 NPC와의 관계와 심어둔 복선이다 |

룰북과 캐릭터 시트는 프롬프트 앞쪽에 고정되어 캐시가 붙고 장면 정보만 뒤쪽에서 바뀐다. **주입량이 세션 길이와 거의 무관해진다.**

매 턴 관련 항목을 검색해서 꺼내오는 방식은 M0에 넣지 않는다 — 검색 품질이라는 실패 지점이 늘면 "AI GM이 재미있나"를 측정할 수 없다.

## 4. 룰북 시스템

### 4.1. 룰북은 세 부분이다

```
① 원문 (자연어)      사람이 쓰고 읽는 것. 백과사전 형태 그대로.
                     게임 중에도 살아 있음 — 재량 판정이 읽는다
② 구조화 데이터       판정 방식 / 만들기 단계 / 라이프사이클 유형 / 효과
③ 연결               ①의 어느 문단이 ②의 어느 항목인가 → 판정 근거 표시에 사용
```

**원문을 버리지 않는다.** 자동화율이 100%가 아니어도 플레이 가능하다는 것은 곧 구조화되지 않은 부분이 원문으로 처리된다는 뜻이다.

### 4.2. 룰북 파일 목차

```
룰북
├─ 메타          이름·설명·버전·저작자·라이선스 / 판정 방식 지정 / 자동화율
├─ 원문          자연어 그대로, 절 단위
├─ 캐릭터 정의    능력치 목록 / 파생값 계산식 / 캐릭터 종류 / 만들기 단계
├─ 판정 정의      판정 종류 목록 / 결과 등급 집합 / 수정치 규칙
├─ 효과 목록      주문·특성·아이템
├─ 라이프사이클    성장 / 회복 / 장비 / 죽음 / 화폐 유형
├─ 적·위협 정의
└─ 원문↔구조 연결표
```

### 4.3. 판정 방식 로드맵

| | 방식 | 판정 | 대표 | 시기 |
|---|---|---|---|---|
| ✅ | **2d6 등급식** | 2d6 + 능력치 → 10+/7-9/6- | 던전월드 계열 | **M0** |
| ✅ | **d100 롤언더** | d100 ≤ 기술값, 성공 등급 | 크툴루 계열 | **M0** |
| ⬜ | d20 롤오버 | d20 + 수정치 ≥ 목표값 | D&D 계열 — **UGC 수요 1순위** | M1 |
| ⬜ | 다이스풀 성공셈 | Nd6/Nd10 중 성공 개수 | WoD, 블레이드 | M2 |
| ⬜ | Year Zero | d6 풀 + 푸시 | 에일리언, 포비든 랜즈 | M2 |
| ⬜ | FATE / 퍼지 | 4dF + 애스펙트 | FATE | M3 |

**6개면 시장의 80~90%를 덮는다.**

**M0에 2개를 넣는 이유:** 판정 방향(높을수록 vs 낮을수록)과 등급 체계가 서로 달라서, 둘이 같은 그릇에서 돌면 추상화가 옳다는 강한 증거가 된다. 하나면 잘못된 추상화를 만들어도 알 수 없다.

### 4.4. 판정 인터페이스

```
판정 요청 { 판정 종류 / 기준값 / 난이도(선택) / 수정치 목록(유형별) }
        ↓  판정 방식 코드 (순수 함수, 룰북 데이터를 읽어 계산)
판정 결과 { 굴림 원본 / 최종값 / 등급 / 그 등급의 효과 }
```

**결과 등급을 코드에 고정하지 않는다.** 2d6식은 3개, d100식은 최대 6개다. 룰북이 자기 등급 집합을 선언한다. 다이스풀 방식은 등급이 **수치**(성공 개수)이므로 목록과 수치 구간을 모두 받아야 한다.

**수정치도 유형 목록이 필요하다.**

| 유형 | 예 |
|---|---|
| 숫자 가감 | +1, -2 |
| **주사위 추가·제거** | 보너스 다이스, 유리·불리 |
| 목표값 변경 | 난이도 상승 |
| **재굴림** | **푸시 롤 — 크툴루의 정체성.** 숫자 수정치만 지원하면 표현 불가 |

### 4.5. 효과 표현

주문·특성·아이템의 효과를 조합 가능한 원자 연산으로 표현한다. 30~50개 규모 목표.

```
피해를 준다 / 상태를 부여한다 / 저항 판정을 요구한다 / 판정을 수정한다 /
이동시킨다 / 자원을 쓴다·회복한다 / 발동 조건을 심는다 / 선택을 요구한다 /
집중을 요구한다  …
```

선례: 카드 게임이 25,000장 넘는 카드를 이 방식으로 구현해왔다.

### 4.6. 자동화율

> **모든 룰북은 플레이 가능하다. 다만 자동화율이 다르다.**
> `자동화율 = 자동 처리된 판정 수 / 전체 판정 수`

| 룰북 | 예상 자동화율 |
|---|---|
| 던전월드 계열 | 95%+ |
| 크툴루 계열 | 90% |
| D&D 5e 클론 | 70~85% |
| 섀도우런 클론 | 50% |

등록 시 자동 산출해 유저에게 표시한다.

```
「크로니클 d20」  자동화율 82%   ★ 완전 지원
「그림자 도시」   자동화율 54%   ⚠ 부분 지원 — 일부 판정은 GM 재량으로 처리됩니다
```

**목표: 룰북 100개 중 90개가 자동화율 80% 이상.**

### 4.7. 재량 판정 계층

**룰북에 없는 상황을 처리하는 통로.** 정통 TRPG의 절반은 규칙이 아니라 재량 판정이다.

```
자유 텍스트
   ↓  ① 무브 분류      [닫힌 집합]
   ↓  ② 능력치 선택     [닫힌 집합]
   ↓  ③ 주사위          [순수 코드]
   ↓  ④ GM 대응 선택    [닫힌 집합]  실패·부분성공 시
   ↓  ⑤ 서술           [자유 생성]
```

**판정 발동 방식: 혼합형.** LLM이 제안하면 플레이어가 확인한다.

> "이건 「위험을 무릅쓰다」 판정이 필요해 보입니다  [민첩으로 굴리기]  [아니오, 그냥 하는 겁니다]"

초보자가 무브 이름을 몰라도 되고, 플레이하면서 무엇이 왜 판정인지 배우며, 잘못된 분류를 그 자리에서 막을 수 있다.

**신뢰도 임계값을 폐기한다.** 모든 분류가 플레이어 확인을 거치므로 임계값이 불필요하다. 신뢰도는 **UI 강도**로만 쓴다.

| 신뢰도 | UI |
|---|---|
| 높음 | 무브가 선택된 상태로 제시. 엔터 한 번 |
| 낮음 | 후보 2~3개 나란히 제시 |
| 무브 없음 | "판정 없이 진행합니다" + 되돌리기 |

**이 계층으로 들어오는 3종:** 룰북에 없는 창의적 행동 / 효과 표현으로 담지 못한 롱테일 / 판정이 필요 없는 그냥 되는 일(**플레이의 절반 이상**).

**재사용:** 자주 나오는 재량 판정은 방장이 홈브루로 굳혀 자동화로 승격시킬 수 있다. **자동화율이 플레이하면서 올라간다.**

### 4.8. 시나리오 형식 (룰북과 독립)

**시나리오는 룰북에 종속되지 않는다.** v1은 종속을 전제했으나 오해였다.

| | 형식 | 구조 | 용도 | 시기 |
|---|---|---|---|---|
| ✅ | **위협 시계** | 위협 + 순서 있는 칸 | 서사 중심, 배후 흑막 | **M0** |
| ⬜ | 노드 그래프 | 장소·상황 노드 + 연결 | 던전, 전통 모듈 | M1 |
| ⬜ | 클루 웹 | 단서 → 단서, 필수 정보 보장 | 조사물, 미스터리 | M1 |
| ⬜ | 테이블·절차 생성 | 랜덤 표 + 절차 | OSR, 헥스크롤 | M2 |

**조합 가능해야 한다.** 실제 모듈은 대부분 "노드 그래프(던전) + 배후 위협 시계(흑막)"다.

### 4.9. 적과 NPC의 숫자는 룰북이 선언한다

v1에는 적을 데이터로 표현하는 방법이 아예 없었다(몬스터 스탯블록 부재, 검증 케이스에 "적의 턴"이 없음). 절반은 첫 타깃 변경으로 풀렸다 — 적의 행동은 닫힌 GM 대응 목록에서 나오므로 **별도의 전투 AI가 필요하지 않다.**

남은 절반, 즉 적의 숫자가 어디에 있느냐를 이렇게 정한다.

| 플랫폼이 정하는 것 | 룰북 데이터가 선언하는 것 |
|---|---|
| 식별자 | 상태값 묶음에 어떤 항목이 있는지 |
| 표시 이름 | 각 값의 뜻 |
| 상태값 묶음 (키-값 그릇) | 특정 값이 바닥나면 무슨 일이 일어나는지 |
| 소속 룰북 | |
| 가시성 (3.7) | |

상태 변경은 효과 표현(4.5)을 통해서만 일어난다. 저장은 캐릭터와 같은 그릇을 재사용하고 유형으로만 구분한다 — 성장·애착·인벤토리는 캐릭터 유형에만 적용된다.

**플랫폼 코드에 체력·피해·태그처럼 룰북 고유의 개념을 넣지 않는다.** 어느 룰북에나 있어 보이는 것도 실제로는 그렇지 않다 — 체력이 숫자가 아닌 룰북, 피해가 등급으로만 표현되는 룰북, 적이 상태값을 갖지 않는 룰북이 있다. 이는 폐기한 룰북별 전용 어댑터와 같은 실수의 다른 얼굴이며, 원칙 3의 마지막 줄이 금지하는 것이다.

**대가.** 코드가 "체력"을 모르므로 값이 바닥났을 때의 처리를 룰북이 직접 선언해야 하고, 자동화율(4.6)이 그만큼 룰북 작성 품질에 의존한다. 이 대가는 원칙 3이 요구하는 것이다 — 죽음의 관용은 룰북의 난이도 곡선 그 자체이므로 우리가 대신 정할 수 없다.

좌표계와 전술 그리드는 M4 유지. H3(룰북을 데이터로 표현할 수 있다) 검증에 **적 표현도 포함한다** — 두 번째 룰북의 적이 같은 그릇에 들어가는지 확인한다.

## 5. 위협 시계

### 5.1. 데이터 구조

**대본이나 분기 트리가 아니라 "나쁜 일 목록 + 순서"만 저장한다.** 칸 사이의 사건과 플레이어 대응은 AI가 즉흥 생성한다.

```
위협 시계
├─ 이름 / 한 줄 요약
├─ 분량 (칸 수)               ← 상품 단위이자 무료 제공분 원가의 기준
├─ 톤 태그 (진지/코믹/호러)     ← 매칭·로비에 사용
├─ 위협의 정체
├─ 그것이 원하는 것            ← AI에게 주는 행동 지침 (한 문장)
├─ 등장인물 [ ]               ← 엔티티 장부와 연결
├─ 시계 칸 [순서 있음]
│    ├─ 순번 / 무슨 일이 일어나나 (한 문장)
│    ├─ 상태: 대기 | 진행됨 | 무효화됨
│    ├─ 진행 조건
│    └─ 진행 후 세상에 남는 흔적  ← 이후 판정 조건에 반영
├─ 파국 (끝까지 갔을 때)
└─ 시작 칸
```

예시:

```
■ 위협:  폐광에서 뭔가 깨어났다        ■ 원하는 것: 삼키고, 퍼뜨린다
■ 등장인물: 광부 반장 톰 / 신부 엘라 / 이름 없는 무언가
■ 시계 칸
   [●] 1  광부들이 하나씩 사라진다
   [○] 2  마을 우물물이 검게 변한다      ← 다음
   [○] 3  신부 엘라가 밤에 사라진다
   [○] 4  지하의 봉인이 부서진다
■ 파국:  마을이 사라진다
```

### 5.2. 진행 규칙 — 세 가지를 함께 쓴다

| # | 방식 | 역할 |
|---|---|---|
| ① | **실패 누적 카운터.** 판정 실패 시 +1, N회(기본 3, 시계별 조절) 도달 시 강제 1칸 진행 후 초기화 | **봐주기 방지 안전장치.** AI 의지와 무관하게 프로그램이 센다 |
| ② | **조건 트리거.** 시간 경과·장소·선행 칸 진행 여부 | 세상의 관성 |
| ③ | **AI 선택.** GM 대응 목록에서 "시계 진행"을 고를 수 있음 | 연출 타이밍 자유도 |

③만 있으면 봐주기가 생기고, ①만 있으면 기계적이 된다.

**①이 관측 지표를 공짜로 만든다.** "실패는 많은데 시계가 안 돈다"(= AI가 봐주고 있다)를 사후에 자동 집계할 수 있다.

**플레이어 승리:** 칸이 무효화되거나 시계 전체가 종료된다.

### 5.3. 위협 시계가 동시에 푸는 문제

| 문제 | 해결 |
|---|---|
| AI가 자꾸 봐준다 | 실패 시 칸이 **기계적으로** 진행 |
| 세상이 멈춰 있다 | 위협에 의도가 있어 플레이어가 안 건드려도 전진 |
| 깔아둔 복선을 잊는다 | 칸 목록이 곧 복선. AI 기억이 아니라 DB 행 |
| 끊고 이어하기 | "몇 칸까지 진행됐나"가 명확한 상태값 |
| 자유도 vs 방향성 | 플레이어가 딴 길로 새도 GM이 억지로 안 끌어옴 |
| 정원 미달 진행 | **시계는 사람 수와 무관하게 돈다** |
| 재방문 동기 | 시계가 아직 멈추지 않았다 |
| 토큰 비용 | 시계 하나가 수백 토큰 |
| 저작 부담 | 분기 트리 불필요 → **UGC 경로가 열림** |

### 5.4. 규격과 저작 주체

**시계 하나 = 4~6칸 / 8~15시간.** 무료 제공 = 1~2칸 (첫 에피소드).

| 주체 | 개수 | 용도 |
|---|---|---|
| **우리** | 3~5개 | 론칭용. 톤 분산(진지/코믹/호러). **초보자 첫 경험은 반드시 이 중에서** |
| **유저** | 무한 | 동일 양식. 공개 시 검수 후 마켓 등록 |
| **AI** | 무한 | 동일 양식 생성. **초보자 첫 경험에는 사용하지 않음** |

**셋이 완전히 같은 양식을 쓴다.** 시스템은 출처를 구분하지 않고 동일하게 실행하며, 저작 도구도 하나면 된다. 우리가 손으로 만드는 3~5개가 **양식의 검증** 역할을 한다.

## 6. 캐릭터

### 6.1. 만들기 — 7가지 동작

어떤 룰북이든 캐릭터 만들기는 7가지 동작의 조합으로 표현된다.

| # | 동작 | 예 |
|---|---|---|
| ① | 목록에서 하나 고르기 | 플레이북, 클래스, 직업 |
| ② | 목록에서 여러 개 고르기 | 기술 3개, 시작 주문 2개 |
| ③ | 숫자를 나눠 담기 | 포인트 27점 배분 |
| ④ | 정해진 숫자를 자리에 배치 | 15·14·13·12·10·8 배치 |
| ⑤ | 주사위 굴려 채우기 | 4d6k3, 3d6 |
| ⑥ | 자유롭게 쓰기 | 이름, 외모, 백스토리 |
| ⑦ | 자동 계산 | 체력, 방어도, 숙련 보너스 |

**룰북 데이터가 "만들기 단계 목록"을 갖고, 시스템은 순서대로 실행한다.** 화면 부품도 7개면 모든 룰북에 재사용된다.

### 6.2. 애착 설계

**문제는 길이가 아니라 선택의 종류였다.**

| 재미있는 것 | 지루한 것 |
|---|---|
| 의미가 즉시 이해되는 선택 | 뜻을 모르는 항목 고르기 |
| 고르면 달라지는 게 보이는 선택 | 결과가 안 보이는 숫자 입력 |
| 내가 누구인지 정하는 선택 | 시스템이 해도 되는 계산 |

v1의 "클래스 13개 중 하나"는 개수가 아니라 **이해할 수 없는 선택**이 문제였다.

**장치 6개**

1. **숫자를 서술로 번역해 실시간 표시**
   ```
   민첩 +2  →  "당신은 그림자처럼 움직인다.
                좁은 틈을 지나고, 소리 없이 다가간다."
   ```
   숫자를 옮기면 문장이 바뀐다. **룰북 지식을 요구하는 대신 결과를 보여준다** — 이것이 "룰북 안 읽어도 된다"의 실제 구현
2. **선택지를 이야기 질문으로 감싼다**
   ```
   (X) 플레이북을 선택하세요  [파이터][시프][위저드][클레릭]
   (O) 당신은 위험을 어떻게 마주합니까?
        ▸ 정면으로 걸어들어간다        → 파이터
        ▸ 그림자에서 기다린다          → 시프
        ▸ 위험의 정체를 먼저 이해한다   → 위저드
        ▸ 남을 먼저 지킨다             → 클레릭
   ```
   고른 뒤에 직업명을 알려주면 그때는 의미를 갖는다
3. **순서를 바꾼다.** 재미있는 것(누구인가 → 무엇을 잘하나 → 무엇을 들었나 → 이름·외모) 먼저, 기계적인 것 뒤로. **기계적 단계는 추천값이 미리 채워진 상태로 제시**
4. **되돌리기 상시 제공**
5. **자유 서술 → AI 추천.** 백스토리를 읽고 추천을 붙인다. **자동 확정 금지, 추천만**
6. **완성 순간 보상.** 캐릭터 카드 — 이름·초상화·한 줄 소개("로빈 — 뒷골목에서 자란, 그림자를 믿는 자")

**경로**

| | 소요 | 애착 |
|---|---|---|
| ~~완성품 집어들기~~ | ~~30초~~ | **없음 — 폐기** |
| 거의 다 된 캐릭터 + 마지막 3~4개 선택 | 2분 | 있음 |
| 전 과정 직접 | 5분 (던전월드 기준) | 강함 |

**30초 경로를 없애는 것이 핵심.** 애착은 투자에서 나오고, 투자가 일어나는 유일한 지점이 캐릭터 만들기다. 30초에 집어든 캐릭터가 죽으면 아프지 않고, 그러면 ② 결과의 무게가 무너진다.

**성공 기준:** 완성 직후 유저가 **"내 캐릭터는 누구다"를 한 문장으로 말할 수 있는가.**

### 6.3. 라이프사이클 — 유형 목록

**각 영역의 유형을 우리가 코드로 구현하고, 어느 유형인지는 룰북이 선언한다.**

**성장**

| 유형 | 대표 |
|---|---|
| 경험치 누적 (**획득 조건은 룰북이 별도 정의**) | D&D(적 격파·목표), 던전월드(판정 실패) |
| 사용 기반 개선 (쓴 기술이 자람) | 크툴루 계열, BRP 계열 |
| 점수 지급 (세션 후 받아서 배분) | WoD, FATE |
| **성장 없음** (설계 의도) | 원샷, 일부 호러 |

**회복**

| 유형 | 대표 |
|---|---|
| 휴식 기반 (짧은/긴 휴식) | D&D 5e |
| 시간 경과 기반 | 크툴루 계열 |
| 치료 판정 기반 | 다수 |
| 안전지대 기반 | 던전월드 |
| **거의 회복 안 됨** (설계 의도) | 호러 계열 |

**장비**

| 유형 | 대표 | 비고 |
|---|---|---|
| **개별 품목 + 무게·슬롯 제한** | D&D, OSR | **1순위 구현.** 자원 관리가 게임의 핵심인 경우가 많다 |
| 추상 회분 ("모험 장비 5회분") | 던전월드 | |
| 하중 등급만 | 일부 룰북 | |
| 관리 없음 (서사적으로만) | 일부 서사 룰북 | |

> **도라에몽 주머니 문제.** 추상 회분을 모든 룰북에 적용하면 "필요할 때 아무거나 꺼낼 수 있는" 상태가 되어 밸런스가 붕괴한다. 자원 압박이 재미인 룰북에서는 개별 품목 관리가 **기능이지 부담이 아니다.**

**죽음**

| 유형 | 대표 | 비고 |
|---|---|---|
| **즉사** | OSR, 일부 호러 | **설계 의도. 관용을 넣으면 게임이 망가진다** |
| 빈사 → 안정화 판정 | D&D 5e | |
| 협상 | 던전월드 | |
| 부상 누적 (죽음 대신 영구 손상) | 일부 룰북 | |
| **캐릭터 교체 전제** | 크툴루 계열 | 조사자가 죽거나 미치는 것이 정상 흐름 |

**화폐**도 동일 패턴 — 단일 통화부터 다중 통화 환산까지 룰북 데이터에 정의.

**플랫폼 층으로 남는 것**

| 항목 | 비고 |
|---|---|
| 세션 마감 시점에 뭔가를 할 수 있는 **자리** | 그 자리에서 무엇을 할지는 룰북이 정함 |
| 죽은 캐릭터의 기록 보존 → 캠페인 기념품 | 죽음 규칙과 무관하게 기록은 남는다 |
| 레벨업 화면이 7가지 동작을 재사용 | 성장 유형이 무엇이든 "고르기·배분하기"로 표현 |
| 숫자를 서술로 번역 표시 | 번역 내용은 룰북에서 온다 |

## 7. 플레이 운영

### 7.1. 세션을 1급 개념에서 내린다

```
캠페인 = 영속 상태 (진짜 게임)   ← git repo
세션   = 단순 접속 구간 (뷰포트)  ← 터미널 창
```

v1의 "세션 종료 시 컴파일", "세션당 토큰 예산" 등 세션 중심 서술을 전부 재작성한다.

### 7.2. 안전 정지 지점

장면 경계·전투 종료·목표 달성 직후에 **"지금 끊기 좋습니다"**를 표시한다. 전투 중간 이탈 시에는 경고 + 상태 스냅샷을 강제한다.

| 끊은 지점 | 재개 난이도 |
|---|---|
| 전투 중간, 누구 턴이었는지 불명, 주문 2개 걸려 있음 | 최악 |
| 장면 종료 직후 | 쉬움 |

시작 시 "오늘 대략 얼마나 하실 건가요?"를 **힌트로** 받아 GM이 페이싱한다. 강제하지 않는다.

### 7.3. 재개 (리캡)

**3주 만에 접속했을 때 "우리 어디까지 했지"가 온라인 TRPG 최대 이탈 원인이다.**

- **파티 리캡** — "지난 이야기" 3~5문장
- **개인 리캡** — "당신은 경비병에게 빚을 졌고, 은화 12닢이 남았고, 지하 수로로 가려던 참이었습니다"
- **관계 장부** — 만난 NPC와 그들이 나를 어떻게 생각하는지

**압축 시스템의 목적을 확장한다.** v1은 토큰 절약 용도로만 설계했으나, 같은 데이터로 유저용 리캡을 만든다.

**압축 품질 검증 기준:** v1(스키마 준수 + 엔티티 누락 없음) → **"3주 뒤에 읽고 게임을 이어할 수 있는가"**

### 7.4. 조율 시스템 — 대폭 축소

플레이어끼리의 대화와 순서 조율은 외부 메신저에서 끝난다.

| v1 기능 | 결정 |
|---|---|
| 스포트라이트 토큰 (선착순 락) | **삭제** |
| 상반 행동 이니셔티브 강제 정렬 | **삭제** — 비전투에는 이니셔티브가 존재하지도 않음 |
| 3초 리액션 팝업 | **완화** — 타이머 없는 대기. 짧은 타이머는 스트리머 프리셋에만 |
| AFK 타임아웃 강제 스킵 | **대폭 축소** — "자리 비움" 표시 + 수동 넘기기 |
| 파티 채팅 / 보이스 / 친구 시스템 | **안 만듦** — 대신 **초대 링크** |

**대체: 락이 아니라 신호등.** 누구 차례인지 보이고, 손들기가 있고, 순서를 넘길 수 있으면 된다.

### 7.5. 사람이 오고 가는 문제

**세 경우를 다르게 처리한다** (v1은 "AFK 타임아웃" 하나로 뭉쳐놨다).

| 경우 | 처리 |
|---|---|
| 잠깐 자리 비움 | 아무것도 안 함. "자리 비움" 표시 + 타인이 순서 넘기기 |
| 오늘 중도 이탈 | **서사적 배경화.** "타렌은 일행과 함께 있지만 오늘은 말이 없다." 존재 유지, 행동·판정 없음 |
| 영구 이탈 | 캐릭터는 남긴다. 일정 기간 무응답 시 "모집 중"으로. **시스템이 자동 축출하지 않고 방장이 판단** |

> ⚠️ **AI가 남의 캐릭터를 조종하지 않는다.** 돌아온 유저가 "내 캐릭터가 그런 짓을 했다고?"가 되면 ③ 플레이어 주체성 위반이다.

**신규 합류는 이미 가진 것으로 해결된다** — 파티 리캡 + 위협 시계 상태 + 캐릭터 한 줄 소개. **같은 데이터로 "돌아온 사람"과 "새로 온 사람"을 동시에 처리한다.**

**정원이 안 차도 진행한다.**

```
(X) 4명이 다 와야 시작  →  한 명 못 오면 무산  →  두 번 무산되면 캠페인 사망
(O) 온 사람으로 진행    →  2명만 와도 굴러감
```

**위협 시계가 사람 수와 무관하게 도는 덕분에 가능하다.** 단, 인원이 적으면 위협의 압박을 낮춘다.

**첫 만남:** 각자 캐릭터를 한 문장으로 소개한다. 캐릭터 만들기 마지막에 생성되는 한 줄 소개가 그대로 쓰인다. **낯선 사람끼리 애착의 시작점은 서로의 캐릭터다.**

### 7.6. 안전 장치

**TRPG는 콘텐츠 등급을 사전에 붙일 수 없는 매체다** — 이야기가 그 자리에서 만들어지므로 아무도 오늘 무슨 내용이 나올지 모른다. 그래서 정통 TRPG는 사전 등급 대신 **실시간 브레이크**를 쓴다.

> **인간 GM은 플레이어의 표정이 굳는 것을 보고 말없이 화제를 돌린다. AI는 표정을 볼 수 없다.**
>
> 안전 장치는 규정 준수 기능이 아니라 **AI가 갖지 못한 GM의 눈을 대체하는 장치**다.

**1층 — 방 생성 시 선을 정한다**

```
■ 톤:  진지 / 코믹 / 호러
■ 선 (아예 안 나옴):   고문 · 성적 위협 · 자해 · 아동 위해 · 동물 학대 · 극단적 신체 훼손
■ 장막 (나오지만 묘사 안 함):  같은 목록에서 별도 선택
```

**「장막」이 핵심 개념이다.** "당신은 문을 닫는다. 안에서 무슨 일이 있었는지는 다음 날 아침에야 알게 된다." **이야기의 무게를 유지하면서 묘사만 뺀다.**

**2층 — 정지 카드.** 세 원칙이 절대적이다.

| 원칙 | 이유 |
|---|---|
| **익명** | 이름이 보이면 아무도 안 누른다 |
| **설명 요구 없음** | "왜요?"를 물으면 못 누른다 |
| **즉시 작동** | 다음 문장이 나오기 전에 멈춘다 |

강도 2단계: `[이 장면을 돌려주세요]` / `[이 주제를 빼주세요]`

**3층 — AI가 넘지 않게 하는 3겹**

1. 방의 선·장막 목록을 GM 프롬프트에 상시 포함
2. **GM 출력을 내보내기 전 검사** (v1의 "백엔드가 무결성을 검증한 뒤 송신" 구조에 그대로 붙는다)
3. 장막 처리: 삭제하지 않고 "문이 닫힌다" 식 전환

**4층 — 사람이 문제일 때 (M2).** 신고(다른 사람에게 안 보임) / 방장 강퇴 / 차단.

**핵심 설계 판단 — 안전 장치가 몰입을 깨면 안 된다**

```
(X) ⚠️ 안전 장치가 사용되었습니다. 장면을 조정합니다.
(O) (아무 알림 없이 이야기가 자연스럽게 다른 데로 흐른다)
```

좋은 GM이 하는 것이 정확히 이것이다. **AI에게 "안전 장치 작동 사실을 언급하지 말 것"을 명시적으로 지시한다.**

**이탈 행동의 제재는 두 층**

| 층 | 상황 | 처리 |
|---|---|---|
| 서사적 대가 | 딴 길로 샘 | **막지 않는다.** 세계가 반작용한다. 시계는 계속 돌고, 돌아왔을 때 상황이 나빠져 있다 |
| 사회적 제재 | 타 플레이어 괴롭힘, 안전 선 침범 | **하드 블록** |

## 8. 저작 도구

### 8.1. 저작 흐름

```
1. 유저가 평소처럼 룰북을 쓴다 (또는 가진 파일을 올린다)
2. AI가 읽고 구조화 초안을 만든다
3. 유저가 확인한다                    ← 성패가 갈리는 지점
4. 확인된 부분만 자동 처리. 나머지는 원문 + 재량 판정
```

**확인할 때 구조화 데이터를 보여주지 않는다 — 시험 판정 결과를 보여준다**

```
(X) { "move": "defy_danger", "stat": "dex", "on_miss": {"damage": "1d6"} }

(O) "민첩으로 위험을 무릅쓴다" 판정을 해봤습니다.
      2d6 = [3,4] = 7,  민첩 +1  →  8  (실패)
      결과: 대미지 1d6 = 4
    이게 의도대로입니까?  [맞습니다] [아닙니다 — 방어구를 차감해야 합니다]
```

**유저는 자기 룰북을 알기 때문에, 결과가 이상하면 문법을 몰라도 안다.**

### 8.2. 점진적 구조화 — 저작은 한 번에 끝나는 일이 아니다

| 기존 플랫폼 | 우리 |
|---|---|
| 다 입력하고 → 플레이 | **플레이하면서 → 입력이 쌓임** |
| 입력 안 하면 아무것도 못 함 | 원문만 있어도 플레이됨 (자동화율 20%) |
| 저작이 노동 | 저작이 플레이의 부산물 |

**"굳히는" 메커니즘은 홈브루 승격(4.7절)이 이미 담당한다.** 별도 기능이 아니다.

### 8.3. 안전한 기본값

> **확실한 것만 구조화하고, 애매한 것은 원문 + 재량 판정으로 남긴다.**

AI 변환은 행동 분류보다 훨씬 어렵고, **틀리면 조용히 밸런스가 어긋난 채로 굴러간다.** AI가 "확실 / 애매"를 구분해 표시하고 애매한 것은 구조화하지 않으면 **틀린 규칙이 자동 실행되는 사고**가 나지 않는다.

### 8.4. 범위

| 유저 유형 | 비중 | 필요한 것 |
|---|---|---|
| 있는 룰북을 **고른다** | 대다수 | 목록에서 선택 |
| 가진 룰북을 **올린다** | 소수 | 파일 업로드 + AI 변환 (M1) |
| 처음부터 **만든다** | 극소수 | 전체 저작 도구 |

> 저작 도구의 목표는 "모두가 쓰게"가 아니라 **"쓰려는 사람이 안 막히게"**다.

## 9. 수익 모델

### 9.1. 원가 구조

| | 1인 1시간당 |
|---|---|
| 프론티어 모델 | ≈ $0.30 |
| 중형 이원화 | ≈ $0.20 |
| 저가 모델 | $0.03~0.10 |

**솔로가 파티보다 1인당 7~8배 비싸다.** LLM 호출은 턴 수에 비례하고 사람 수에 비례하지 않는다 — 파티는 4명이 원가를 나눠 쓴다. **관전자는 원가 0.**

**캐싱이 지배 변수다.** 없으면 3.7배. 프롬프트 조립 순서를 안정성 순서(영구 고정 → 세션 고정 → 턴마다 변함)로 짜는 것은 최적화가 아니라 **M0의 설계 제약**이다.

상세: `GPTRPG-cost-analysis.md`

### 9.2. 과금 구조

**무제한 정액제는 성립하지 않는다.** 등급제 + 소프트 상한, 파티/솔로 분리.

**무료 티어 — 시간 카운터를 만들지 않는다**

> "남은 플레이 시간 12시간"을 띄우는 순간 **시계를 보며 노는 게임**이 된다. TRPG 몰입과 상극.
>
> 대신 **"첫 에피소드 무료"** — 위협 시계 1~2칸.

**위협 시계 구조가 그대로 과금 단위가 된다.** 시계 1개 = 캠페인 1개 = 상품 1개. 시계가 남아 있는 상태로 끝나는 것이 **구매 동기**가 된다(드라마 1화 무료 구조).

| 무료 단위 | 플레이 시간 | 파티 1팀 (프론티어) | 파티 1팀 (저가) |
|---|---|---|---|
| 첫 **에피소드** (1~2칸) | 2~5시간 | $2.5~6 | $0.5~1.2 |
| 첫 캠페인 (4칸 전체) | 8~12시간 | $10~15 | $2~3 |

소프트 상한은 뒤에 숨겨 어뷰징만 차단한다.

### 9.3. 코스메틱

| 항목 | M0~M3 | 비고 |
|---|---|---|
| 주사위 스킨 | ✅ | 판정은 항상 있음 |
| **서사 로그 테마** (폰트·색·프레임) | ✅ | **노출 시간 최장. 주사위보다 김** |

## 10. 라이선스

### 10.1. v1의 오해 정정

> v1: "SRD 5.1(CC-BY-4.0) 문서 기반 (고유 명칭 및 공식 세계관 명사는 리브랜딩 **우회**)"

**"우회"는 잘못된 표현이다.** CC-BY는 조건(저작자 표시)을 지키면 자유롭게 쓰라는 **허가**이며, 표시를 빠뜨리는 것이 위반이다. 공식 세계관 고유명사는 애초에 SRD에 없으므로 우회가 아니라 범위 밖이다. 두 개는 별개 문제다.

### 10.2. 보호되는 것과 안 되는 것

| 보호 안 됨 (사용 가능) | 보호됨 |
|---|---|
| **게임 메커니즘 자체** | 룰북의 **문장** |
| 판정 구조, 수학 | **고유명사** |
| | 표의 창작적 배열, 삽화, 레이아웃 |

**첫 줄이 사업의 기반이다.** 그리고 이 때문에 **리트로클론은 대체로 합법이다**(패스파인더가 D&D 3.5를 그렇게 계승했다).

### 10.3. 유저 업로드 — 공개 범위 3단

| 범위 | 정책 |
|---|---|
| 비공개 (본인만) | 관대 |
| 초대한 친구만 | 관대. 기록 보존 |
| **공개 마켓** | **엄격** — 라이선스 선언 + SRD 원문 유사도 검사 + 등록 검수 + 신고·삭제 절차 |

### 10.4. AI 생성물 — 저작권이 아니라 약관으로

AI 생성물의 저작권 성립 여부 자체가 법적으로 불확실하다. **약관상의 이용권으로 설계한다** — 유저에게 자기 플레이 기록의 이용·다운로드·판매 권리, 우리에게 서비스 운영 범위의 이용권.

## 12. 마일스톤 0 결론 — 가설과 멈출 조건

v1의 검증 기준 13개는 전부 "엔진이 작동하나"였고 **"이게 될 일인가"에 답하는 항목이 없었다.**

### 12.1. 검증할 가설

| # | 가설 | 멈출 조건 | 등급 |
|---|---|---|---|
| **H1** | **AI가 GM 노릇을 하면 재미있다** | **참가자 대부분이 "두 번째 세션을 하고 싶지 않다"** | **진짜 킬** |
| H2 | 위협 시계가 AI의 봐주기를 막는다 | 시계는 돌지만 이야기가 억지스럽다 | 재설계 |
| H3 | 룰북을 데이터로 표현할 수 있다 | 두 번째 룰북이 안 들어간다 | 전략 변경 |
| H4 | 자유 텍스트 입력이 쓸 만하다 | 직접 찾아야 하는 비율 30% 이상 | 전략 변경 |
| **H5** | **원가가 사업 가능 범위 안이다** | **1인 1시간당 $1 초과 + 저가 모델로도 안 내려감** | **진짜 킬** |
| H6 | TRPG 비경험자가 룰북 없이 시작할 수 있다 | 비경험자 대부분이 캐릭터 만들기에서 포기 | 재설계 |

**진짜 킬이 두 개뿐이다.** M0 실험은 H1과 H5에 우선 집중한다.

### 12.2. 실험 설계

```
준비    위협 시계 1개 (손으로 4칸) / 룰북 1개 (판정 종류 10개 남짓) / 캐릭터 4개
참가자  TRPG 경험자 2명 + 비경험자 2명    ← 비경험자가 핵심
        우리는 GM을 하지 않고 관찰만 한다  ← 개입하면 H1을 못 잰다
진행    1세션 3~4시간  →  (1주 간격)  →  2세션 3~4시간
```

**1주 간격이 실험의 핵심이다.** "두 번째 세션에 왔는가"가 H1의 답이다.

| 측정 | 답하는 가설 |
|---|---|
| **2세션에 몇 명이 왔나** | **H1 — 가장 중요** |
| 실제 토큰 소모, 실제 턴 수 | **H5** |
| 실패 횟수 대비 시계 진행 횟수 | H2 |
| 비경험자가 캐릭터를 만들었나 | H6 |
| 실제 입력 문장 약 160개 | **H4의 정답 데이터** |
| "당신 캐릭터 어떤 사람이에요?" 대답 | 애착 형성 |

### 12.3. 최소 도구 범위

| 필요 | 안 필요 |
|---|---|
| 텍스트 입력창 | 캐릭터 만들기 화면 (손으로 준비) |
| 행동 분류 + 확인 (최소 형태) | 매칭·로비 |
| 주사위 (코드) | 코스메틱 |
| GM 서사 생성 | 룰북 저작 도구 |
| 위협 시계 상태 + 실패 카운터 | 리캡 자동 생성 (손으로 써도 검증됨) |
| 캐릭터 시트 (읽기만) | 안전 장치 UI (구두 대체) |
| 이벤트 기록 저장 | 결제·계정 |
| 여러 명이 같은 세션을 보는 것 | |

**제품이 아니라 실험 도구다.**

### 12.4. 이 실험이 답하지 않는 것

| 답 못 하는 것 | 언제 |
|---|---|
| **낯선 사람과의 플레이** | 매칭 도입 후 (M2) |
| **장기 캠페인** — 20세션 뒤 NPC 개성 유지, 복선 회수 | 실제 서비스 |
| 여러 룰북에서의 재미 | M1 이후 |
| 동시 접속 규모 | 실서비스 |

> **AI GM의 진짜 실패는 3시간이 아니라 30시간 뒤에 나타난다.** 이 실험은 "시작이 재미있나"만 답한다.
