## 0. 용어 사전

> TRPG 용어를 그대로 쓰면 뜻이 드러나지 않는다. 이 문서는 **왼쪽 이름**을 쓴다.

| 이 문서의 용어 | 원래 TRPG 용어 | 뜻 |
|---|---|---|
| **위협 시계** | 전선 (Front) | 플레이어가 막지 않으면 순서대로 일어날 나쁜 일들의 목록. 시나리오의 뼈대 |
| **시계 칸** | 불길한 징조 (Grim Portent) | 위협 시계의 항목 하나. "우물물이 검게 변한다" 같은 사건 하나 |
| **파국** | 임박한 파멸 (Impending Doom) | 시계가 끝까지 갔을 때 벌어지는 일 |
| **판정** | 롤 / 체크 | 주사위를 굴려 성공·실패를 정하는 것 |
| **무브** | 무브 (Move) | 판정이 발동하는 상황의 종류. 던전월드는 10개 남짓의 닫힌 목록 |
| **GM 대응** | GM 무브 (GM Move) | 플레이어가 실패했을 때 GM이 할 수 있는 일의 목록. "위협을 드러낸다", "시계를 진행시킨다" 등 |
| **재량 판정** | 룰링 (Ruling) | 룰북에 없는 상황을 GM이 그 자리에서 판단하는 것. 정통 TRPG의 절반이 이것 |
| **플레이북** | 플레이북 (Playbook) | 던전월드의 캐릭터 종류. D&D의 클래스에 해당하나 훨씬 단순하고, 사실상 완성된 캐릭터 |
| **판정 커널** | — (자체 용어) | 주사위 판정 수학을 담은 코드. 룰북 계열마다 하나 (2d6식, d20식, d100식…) |
| **효과 DSL** | — (자체 용어) | 주문·특성의 효과를 조합 가능한 원자 연산으로 표현하는 데이터 형식 |
| **자동화율** | — (자체 용어) | 룰북의 판정 중 시스템이 자동 처리하는 비율. 남은 몫은 재량 판정으로 처리 |
| **엔티티 장부** | — (원 기획안 용어) | NPC·아이템·단서의 영구 저장소 |

## 0.5. 설계 원칙

### 세 개의 층 — 모든 기능 제안은 어느 층인지 밝힌다

| 층 | 무엇 | 예 |
|---|---|---|
| **① 플랫폼 기능** | 룰북과 무관하게 우리가 제공 | 안전 장치, 끊고 이어하기, 이벤트 기록, 매칭 |
| **② 표현 어휘** | 룰북이 말하는 것을 담는 그릇 | 7가지 동작, 판정 커널, 효과 표현, 유형 목록 |
| **③ 룰북 규칙** | 룰북 설계자가 정한 것 | 성장·죽음·장비·회복의 구체적 규칙 |

**③을 ①에 올리면 다른 룰북이 망가진다.** 기능을 제안할 때 층을 명시하는 것이 규약이다.

### 원칙 1 — LLM은 파서일 뿐, 저지가 아니다

(원 기획안 유지. D14·D16으로 보강 — 주사위는 순수 코드, LLM은 닫힌 집합 분류와 서술만)

### 원칙 2 (수정) — 판정 커널은 코드, 룰북은 데이터

커널은 소수 정예로 유지하며 우리만 추가한다. 룰북은 커널 하나를 선택하고 나머지를 선언적으로 정의한다. (D5)

### 원칙 3 — 룰북 설계자의 의도를 덮어쓰지 않는다

> 룰북은 설계자의 밸런싱과 세계 설계의 결과물이다. 우리가 표현하지 못하는 규칙은 **"자동화율이 낮다"로 정직하게 표시하고 재량 판정으로 넘긴다.** 편의를 위해 우리 규칙을 대입하지 않는다.
>
> 특히 **성장 속도 · 죽음의 관용 · 자원 관리의 엄격함**은 룰북의 난이도 곡선 그 자체다. 여기에 손대면 게임이 다른 게임이 된다.

구체적 사례:
- D&D 5e의 경험치는 **적의 난이도 등급과 조우 예산에 묶여 있다.** "실패하면 경험치"를 얹으면 성장 속도가 설계값을 벗어나고 조우 밸런스 전체가 무너진다
- **OSR 계열 던전 탐험에서는 횃불 개수와 식량이 게임 그 자체다.** 장비를 추상화하면 게임이 사라진다
- **크툴루 계열은 조사자가 죽거나 미치는 것이 설계 의도다.** 죽음에 관용을 넣으면 장르가 무너진다

**첫 타깃이 던전월드라는 이유로 던전월드의 규칙을 플랫폼에 박지 않는다.** 우리는 범용 시스템을 만든다.

### 원칙 4 — 재방문 동기는 이야기에서 나온다

> **위협 시계가 돌고 있고, 아직 멈추지 않았다.**
> 이야기가 어떻게 끝나는지 보고 싶어서 돌아온다. 그것이 이 제품이 팔아야 하는 감정이다.

성장·보상 시스템을 재방문 유인으로 설계하지 않는다. 진행형 보상을 유인책으로 쓰면 이야기가 성장의 배경으로 밀려나고, 다른 종류의 게임이 된다. 성장은 룰북이 주는 부수적인 것이며, **성장이 없는 룰북도 정상 지원해야 한다.**

## 1. 제품 정의

### 타깃 유저

> TRPG를 잘 모르고, 룰북을 읽을 시간도 없지만,
> 회사·학교가 끝나고 **친구들 또는 처음 보는 모험가들과 실시간으로 몰입할 세계**를 원하는 사람.

플레이 시간은 고정 세션이 아니라 **하고 싶은 만큼**이다. 롤 2~4판처럼 1시간일 수도, 3시간 이상일 수도 있다.

**핵심 함의 3가지**

1. 플레이어끼리의 대화는 **외부 메신저**(디스코드·카카오톡·텔레그램)에서 일어난다. 플랫폼은 소셜 레이어가 아니다.
2. **언제든 끊고 이어할 수 있어야 한다.** Claude Code처럼 — 한 단계를 끝내야만 종료할 수 있는 게 아니다.
3. **처음 보는 사람과의 플레이**를 전제한다. 매칭·안전 도구·드롭인/아웃이 필수가 된다.

### 마케팅 전략 (제품 정의 아님)

스트리머 노출을 통한 진입장벽 완화. **어디까지나 채널이며 제품 요구사항을 규정하지 않는다.**
스트리머 관련 요구(짧은 타이머, 관전자 뷰)는 `PacingPolicy`의 프리셋 하나로 축소해 흡수한다.

## 2. 확정된 결정

### D1. 플레이 모델 = 실시간 동기 파티

- 비동기(PbP)·솔로는 **후속 마일스톤**에서 같은 엔진 위에 추가한다.
- **근거:** "저녁에 친구들과 함께 몰입"은 실시간 외에 답이 없다.
- **아키텍처 근거:** 실시간 → 비동기 전환은 쉽고(비동기는 실시간의 퇴화 케이스), 비동기 → 실시간 전환은 재작성에 가깝다. 방향이 대칭이 아니므로 실시간을 먼저 짓는다.

### D2. "세션"을 1급 개념에서 강등

```
캠페인 = 영속 상태 (진짜 게임)   ← git repo
세션   = 단순 접속 구간 (뷰포트)  ← 터미널 창
```

- 원 기획안의 "세션 종료 시 컴파일", "세션당 토큰 예산" 등 세션 중심 서술을 전부 재작성한다.
- **안전 정지 지점(Safe Stop Point)** 개념을 도입한다. 장면 경계·전투 종료·목표 달성 직후에 "지금 끊기 좋습니다"를 표시하고, 전투 중간 이탈 시에는 경고 + 상태 스냅샷을 강제한다.
- 시작 시 "오늘 대략 얼마나 하실 건가요?"를 **힌트로** 받아 GM이 페이싱한다. 강제하지 않는다.

### D3. 코어 아키텍처 = 이벤트 소싱 + Session Actor + PacingPolicy

```
┌──────────────────────────────────────────────────────┐
│  Transport Adapters   (게임 로직 0줄. 교체 가능)        │
│   WebSocket │ REST │ Push알림 │ 관전자 뷰               │
└──────────────────────┬───────────────────────────────┘
                       │  Command 투입 ↓ / Event 구독 ↑
┌──────────────────────▼───────────────────────────────┐
│  Session Actor        (세션당 1개, 유일한 직렬화 지점)   │
│   Command 수신 → 검증 → Event 발행                     │
│   PacingPolicy 주입 (타이머·순서·리액션 윈도우)          │
└──────────────────────┬───────────────────────────────┘
┌──────────────────────▼───────────────────────────────┐
│  Rules Core           (순수 함수. I/O 없음. 시간 개념 없음)│
│   판정 커널 · 효과 DSL · 주사위 엔진                    │
└──────────────────────┬───────────────────────────────┘
┌──────────────────────▼───────────────────────────────┐
│  Event Log (append-only) + 파생 상태 스냅샷             │
└──────────────────────────────────────────────────────┘
```

**불변 규칙 3가지**

1. **Rules Core는 시간을 모른다.** 타이머·접속 상태 개념이 들어가면 안 된다.
2. **Session Actor가 유일한 쓰기 주체다.** 세션당 단일 직렬화 지점으로 동시성 문제를 구조적으로 제거한다.
3. **모드는 코드 경로가 아니라 `PacingPolicy` 설정값이다.** 새 모드 추가 = 표에 열 하나 추가. `if` 분기 추가가 아니다.

| | 스트리머 | 일반 파티 | 솔로 | 비동기 PbP |
|---|---|---|---|---|
| 턴 타이머 | 45~60초 | 180초 | 없음 | 없음 |
| 순서 강제 | ON | ON | 해당없음 | OFF |
| 리액션 윈도우 | 5초 | 15초 | 인라인 | 알림·무기한 |
| 접속 전제 | 전원 | 전원 | 1인 | 없음 |
| 미접속자 | 자동 스킵 | 자동 스킵 | 없음 | 대기 |

> ⚠️ **이벤트 소싱은 M0에서 확정해야 하는 유일한 되돌릴 수 없는 결정이다.**
> CRUD 제자리 변경으로 먼저 짜면 재접속 델타 동기화·리플레이·비동기 참여·관전자 합류·다시보기가 **전부** 나중에 불가능해진다. 반대로 이벤트 소싱으로 시작하면 이 다섯이 같은 메커니즘 하나로 해결된다.

### D4. 첫 타깃 룰북 = 던전월드 계열 (PbtA)

**D&D 5e는 M4로 이동.** 원 기획안 3.1절의 "가장 복잡한 것으로 엔진 완결성 검증" 논리를 폐기한다.

| 요구 | D&D 5e | 던전월드 |
|---|---|---|
| 룰북 안 읽어도 됨 | ✗ 클래스 13개 + 주문 수백 | ✓ 플레이북 선택 |
| 캐릭터 생성 시간 | ✗ 30~60분 | ✓ 10분 |
| 짧은 플레이에 완결감 | ✗ 전투 1회로 종료 | ✓ 판정 몇 번으로 장면 진행 |
| LLM이 잘 다룸 | ✗ 좌표·수치·리소스 = LLM 최약점 | ✓ 서술 중심 = LLM 강점 |
| ④ 불확실성과 정합 | △ GM fudging 문화 존재 | ✓ **GM이 주사위를 굴리지 않음** |

> **핵심 비대칭:** PbtA는 사람에게도 쉽고 LLM에게도 쉽다. 5e는 둘 다 어렵다.
> 초심자가 가장 헤매는 부분(액션 이코노미·그리드·리소스 추적)이 정확히 LLM이 가장 못하는 부분이다.

**인지도 반론에 대해:** 기획안이 이미 리브랜딩(「크로니클 d20」, 「월드 앤 어드벤처」)을 계획하므로 유저는 어차피 처음 보는 이름을 만난다. 인지도 논거는 약하다.

### D5. 핵심 설계 원칙 2 수정 — 전용 어댑터 폐기

> ~~**원칙 2 (원본).** 범용 메카닉 빌더로 룰북을 추상화하지 않고, 각 룰북 고유의 수학·액션 이코노미·판정 체계를 **전용 어댑터**로 구현한다.~~
>
> **원칙 2 (수정).** **판정 커널은 코드, 룰북은 데이터로 분리한다.**
> 커널은 소수 정예로 유지하며 우리만 추가한다. 룰북은 커널 하나를 선택하고 나머지를 선언적으로 정의한다.

**사유:** UGC 룰북 공유가 제품에 포함되므로, 유저가 룰북을 올릴 때마다 우리가 코드를 짤 수 없다. 원칙 2는 5e 단일 룰북 전제에서만 성립했다.

### D6. 판정 커널 로드맵

| | 커널 | 판정 방식 | 대표 룰북 | 시기 |
|---|---|---|---|---|
| ✅ | **PbtA 티어** | 2d6 + 스탯 → 10+ / 7-9 / 6- | 던전월드, Apocalypse World | **M0** |
| ✅ | **d100 롤언더** | d100 ≤ 능력치, 성공 등급 | 크툴루 계열, BRP, 델타 그린 | **M0** |
| ⬜ | **d20 롤오버** | d20 + 수정치 ≥ DC | D&D 계열, 패스파인더 — **UGC 수요 1순위** | M1 |
| ⬜ | **다이스풀 성공셈** | Nd6/Nd10 중 성공 개수 | WoD, 섀도우런, 블레이드 | M2 |
| ⬜ | **Year Zero** | d6 풀 + 푸시 | 에일리언, 포비든 랜즈, 뮤턴트 | M2 |
| ⬜ | **FATE / 퍼지** | 4dF + 애스펙트 | FATE | M3 |

**M0에 2개를 넣는 이유:** 판정 방향(롤오버 vs 롤언더)과 성공 등급 체계가 서로 달라서, 둘이 같은 효과 DSL 위에서 돌면 추상화가 옳다는 강한 증거가 된다. 커널이 하나면 잘못된 추상화를 만들어도 알 수 없다.

**6개 커널이 시장의 80~90%를 덮는다.** 새비지 월드·사이퍼 등 개별 케이스는 필요 시 추가.

### D7. 효과 DSL 도입 + 자동화율 지표

**3층 구조**

```
룰북 정의   (데이터)  스탯·스킬·플레이북·장비 목록          ← 유저 작성
효과 DSL    (데이터)  무브/주문/특성의 효과를 원자 연산 조합  ← 유저 작성 (핵심)
판정 커널   (코드)    d20롤오버 · PbtA · d100 · 다이스풀…    ← 우리만 추가
```

**원자 연산 예시** (목표 30~50개)

```
DAMAGE(주사위식, 속성, 대상)
APPLY_CONDITION(상태, 지속, 해제조건)
REQUIRE_SAVE(능력치, 난이도, 성공시, 실패시)
MODIFY_ROLL(대상판정, 수정치 | 어드밴티지)
MOVE(대상, 거리, 방향)
SPEND / RESTORE (리소스)
TRIGGER(이벤트, 효과)          ← 리액션·기회공격
CHOOSE(선택지[])               ← 플레이어 선택 지점
CONCENTRATE(효과, 해제조건)
```

**선례:** MTG는 30년간 25,000장 이상을 효과 DSL로 구현했다. TRPG 주문은 MTG 카드보다 단순하다. Foundry VTT의 5e 자동화도 같은 방식이다.

**롱테일 처리:** DSL로 표현 못 하는 효과(소원, 시뮬라크럼, 플래시백 등)는 `requires_ruling`으로 표시되어 **Ruling 계층**이 받는다. 하드 실패가 아니라 우아한 성능 저하.

**자동화율 (Automation Rate)**

> **모든 룰북은 플레이 가능하다. 다만 자동화율이 다르다.**
> `자동화율 = DSL로 자동 처리된 판정 수 / 전체 판정 수`

| 룰북 | 예상 자동화율 |
|---|---|
| 던전월드 (PbtA) | 95%+ |
| 크툴루 (d100) | 90% |
| D&D 5e 클론 | 70~85% |
| 섀도우런 클론 | 50% |

룰북 등록 시 자동 산출해 유저에게 표시한다.

```
「크로니클 d20」  자동화율 82%   ★ 완전 지원
「그림자 도시」   자동화율 54%   ⚠ 부분 지원 — 일부 판정은 GM 재량으로 처리됩니다
```

**목표:** 룰북 100개 중 90개가 자동화율 80% 이상.
**부수 효과:** 자동화율이 낮은 룰북을 보고 어떤 원자 연산을 추가해야 할지 데이터로 알 수 있다. DSL이 데이터 기반으로 성장한다.

### D8. 시나리오는 룰북에 종속되지 않는 독립 계층

원 기획안은 시나리오가 룰북에 종속되어야 한다고 전제했으나 **이는 오해였다.**

| | 룰북 (Rules) | 시나리오 (Adventure) |
|---|---|---|
| 내용 | 캐릭터 생성·판정 체계·전투 규칙 | 특정 모험 하나. 장소·NPC·사건 |
| 재사용 | 수백 개 시나리오가 하나의 룰북 위에서 굴러감 | 룰북 종속 아님 |

분리하지 않으면 "5e 룰로 크툴루 시나리오 돌리기" 같은 조합이 막히고 UGC 재사용성이 죽는다.

### D9. 시나리오 포맷 = 플러그인 인터페이스, 4종

| | 포맷 | 구조 | 용도 | 시기 |
|---|---|---|---|---|
| ✅ | **전선/시계 (Fronts)** | 위협 + 순서 있는 징조 | 서사 중심, 배후 흑막 | **M0** |
| ⬜ | **노드 그래프** | 장소·상황 노드 + 연결 | 던전, 전통 모듈 | M1 |
| ⬜ | **클루 웹** | 단서 → 단서, 필수 정보 보장 | 조사물, 미스터리 | M1 (d100과 함께) |
| ⬜ | **테이블/절차 생성** | 랜덤 표 + 절차 | OSR, 헥스크롤 | M2 |

**조합 가능해야 한다.** 실제 모듈은 대부분 "노드 그래프(던전) + 배후 전선(흑막)"이고, 크툴루 시나리오는 "클루 웹 + 전선(의식 완성까지 남은 시간)"이다.

**Fronts 구조**

```
전선 (Front)  ← 하나의 큰 위협 덩어리
 └ 위협 (Danger)
    ├ 충동 (Impulse)              "이것이 원하는 것"
    ├ 등장인물 (Cast)              관련 NPC
    └ 불길한 징조 (Grim Portents)  ← 순서가 있는 시계
         1. 광부들이 사라지기 시작한다
         2. 마을 우물이 검게 변한다
         3. 사제가 밤에 사라진다
         4. 첫 번째 봉인이 부서진다
    └ 임박한 파멸 (Impending Doom) 아무도 막지 않으면 벌어질 일
```

**Fronts가 동시에 푸는 문제**

| 문제 | 해결 방식 |
|---|---|
| 예스맨 LLM | 판정 실패 시 징조가 **기계적으로** 진행. AI가 봐주고 싶어도 시계는 데이터라 움직임 |
| 정지한 세계 | 위협에 충동이 있어 플레이어가 안 건드려도 스스로 전진 |
| 복선 회수 실패 | 징조 목록이 곧 복선. 기억이 아니라 DB 행이라 안 잊음 |
| 끊고 이어하기 | "몇 번 징조까지 진행됐나"가 명확한 상태값 → 재개 리캡 자동 생성 |
| 자유도 vs 방향성 | 플레이어가 딴 길로 새도 GM이 억지로 안 끌어옴. 위협이 알아서 전진 |
| 토큰 비용 | 전선 하나가 수백 토큰. 모듈 전체를 프롬프트에 넣을 필요 없음 |
| 저작 부담 | 분기 트리 불필요. 위협 + 시계만 정의 → **UGC 경로가 자연스럽게 열림** |

### D10. 외부 메신저 전제 → 조율 시스템 대폭 축소

플레이어 간 대화는 외부 메신저에서 일어난다. 순서 조율도 거기서 끝난다. 플랫폼이 강제할 이유가 없다.

| 원 기획안 기능 | 결정 |
|---|---|
| 스포트라이트 토큰 (선착순 락) | **삭제** |
| 상반 행동 이니셔티브 강제 정렬 | **삭제** — 비전투에는 이니셔티브가 존재하지도 않음 |
| 3초 리액션 팝업 | **완화** — 타이머 없는 리액션 대기. 짧은 타이머는 스트리머 프리셋에만 |
| AFK 타임아웃 강제 스킵 데몬 | **대폭 축소** — "자리 비움" 표시 + 수동 넘기기 |
| 파티 채팅 / 보이스 / 친구 시스템 | **안 만듦** — 대신 **초대 링크** 하나만 잘 되면 됨 |

**대체:** 락이 아니라 **신호등**. 누구 차례인지 보이고, 손들기가 있고, 순서를 넘길 수 있으면 된다. 강제하지 않는다.

### D11. 재개(Recap)를 1급 기능으로 승격

3주 만에 접속했을 때 "우리 어디까지 했지 / 내 캐릭터 뭐였지 / 저 NPC 누구였지"가 **온라인 TRPG 최대 이탈 원인**이다. 인간 GM에게도 "지난 줄거리" 만들기는 부담이라 대충 하고 넘어가고, 그래서 사람들이 안 돌아온다.

원 기획안 4장의 압축 시스템(구조화 서사 레저 + 엔티티 장부)은 지금 **토큰 절약 용도로만** 설계되어 있다. 같은 데이터로 유저용 리캡을 만든다. 목적을 하나 더 붙이는 것뿐이다.

- **파티 리캡** — "지난 이야기" 미드 오프닝처럼, 3~5문장
- **개인 리캡** — "당신은 경비병에게 빚을 졌고, 은화 12닢이 남았고, 지하 수로로 가려던 참이었습니다"
- **관계 장부** — 만난 NPC와 그들이 나를 어떻게 생각하는지

**압축 품질 검증 기준 교체:** 기존(스키마 준수 + 엔티티 누락 없음) → **"3주 뒤에 읽고 게임을 이어할 수 있는가"**

### D12. 목표 재정의 — 완벽 방어에서 투명성으로

| 기존 목표 | 새 목표 |
|---|---|
| 룰북을 100% 정확히 재현한다 | **틀렸을 때 유저가 알아챌 수 있고, 고칠 수 있다** |
| AI 할루시네이션을 완벽하게 방어한다 | **AI가 계산한 것과 판단한 것이 구분되어 보인다** |

**사유:** 100% 재현은 구조적으로 불가능하다. 룰북은 자연어로 쓰인 열린 시스템이고 "적절하다고 판단되면" 같은 문구가 곳곳에 있다. 어떤 VTT도 20년간 이걸 못 풀었다. 그리고 **인간 GM도 100% 재현하지 않는다.**

문제의 성격은 정확도가 아니라 **신뢰**다. 인간 GM이 틀리면 "실수"지만 AI가 틀리면 "이 시스템 못 믿겠다"가 된다. 신뢰는 정확도가 아니라 투명성에서 온다.

**필요한 3가지**

1. **판정 근거 표시 (Show Your Work)** — 모든 판정에 근거를 접어둔 채로 붙인다.
   ```
   🎲 위험을 무릅쓰다 — 강한 성공 (10+)
     ▸ 판정 내역 보기
         2d6 [4, 5] = 9  + 민첩 +2  = 11 → 10+ 강한 성공
         적용: 「위험을 무릅쓰다」 무브 · 근거: 룰북 p.63 · 자동 처리
   ```
   발견 가능한 오류는 신뢰를 크게 안 깎는다. 못 보는 오류가 깎는다.

2. **자동/재량 구분 표시** — `🎲 자동 처리` vs `⚖️ GM 재량 판정`.
   구분되면 재량 판정에 대해 유저가 다른 기대를 갖는다. 실제 테이블에서 GM이 "그건 DC 15로 하자"고 말하는 것과 같은 상태이며, **그건 TRPG의 정상 작동이다.**

3. **정정 가능성 (Override)** — 방장이 판정을 뒤집을 수 있고, 뒤집은 걸 **홈브루로 저장**할 수 있다.
   모든 테이블이 하우스 룰을 갖는 것이 TRPG 문화의 핵심이다. 자주 나오는 재량 판정을 굳혀 자동화로 승격시킬 수 있으므로, 자동화율이 낮은 룰북에 대한 실질적 해결책이기도 하다.

### D13. 제품 정체성 우선순위 — 무엇이 양보 불가인가

| | 요소 | 판정 | 처리 |
|---|---|---|---|
| ① | 룰 정합성 | **대체 가능** | D12의 투명성 + 정정 가능성으로 대체 |
| ② | **결과의 무게** (실패가 아프고 캐릭터가 죽을 수 있음) | **양보 불가** | Fronts의 기계적 징조 진행이 구조적으로 보장 |
| ③ | **플레이어 주체성** (뭐든 시도 가능, 시스템이 막지 않음) | **양보 불가** | Ruling 계층이 열거형 밖 행동을 받음 |
| ④ | **불확실성** (주사위가 진짜 무작위, 아무도 못 건드림) | **양보 불가** | 아래 D14 |
| ⑤ | **공동 창작** (세계가 GM만의 것이 아님) | **양보 불가** | 아래 D15 |
| ⑥ | 전술적 깊이 (수치·위치 계산으로 이기는 재미) | **연기** | M4 (D&D 5e 어댑터 + 전술 그리드) |

앞으로의 모든 설계 결정은 이 표를 기준으로 채점한다.

### D14. 주사위는 순수 코드 — LLM 관여 지점 없음

> **LLM은 난수를 만들지 못한다.** "1~20 중 하나"를 시키면 7과 17이 비정상적으로 많이 나온다. 학습 데이터 편향이 그대로 반영된다.

```
어떤 판정이 발동하는가?   → 파서 + Ruling 계층    (LLM 관여)
무슨 주사위를 굴리는가?   → 판정 커널 + 효과 DSL   (순수 코드)
실제 굴림                → 암호학적 난수 생성기     (순수 코드)
결과 해석                → 판정 커널              (순수 코드)
결과 묘사                → GM 에이전트            (LLM, 수치는 못 바꿈)
```

**Provably Fair 재평가:** ④가 양보 불가이므로 fudging은 금지다. 그러면 Provably Fair는 기술 과시가 아니라 **제품 약속**("우리는 주사위에 손대지 않습니다")을 증명 가능하게 만드는 장치가 된다. 초기 비판(W5)을 철회한다.

**던전월드와의 정합성:** DW에서는 GM이 애초에 주사위를 굴리지 않으므로 fudging이 불가능하고, 대신 **GM 무브 선택**으로 페이싱을 조절한다. ④를 지키면서 드라마를 만드는 방법이 룰 안에 이미 있다. 5e를 골랐으면 이 둘이 충돌했을 것이다.

### D15. 이탈 행동의 "제재"는 두 층

| 층 | 상황 | 처리 |
|---|---|---|
| **서사적 대가** | 딴 길로 샘, 엉뚱한 짓 | **막지 않는다.** 세계가 반작용한다. 전선의 시계는 계속 돌고, 돌아왔을 때 상황이 나빠져 있다 |
| **사회적 제재** | 타 플레이어 괴롭힘, 안전 선 침범 | **하드 블록.** 안전 도구 + 방장 권한 |

TRPG의 정통 해법은 막는 게 아니라 대가를 치르게 하는 것이다.

### D16. Ruling 계층 = 닫힌 집합 분류 + 플레이어 확인

**C1(치명적 결함)이 D4 덕분에 "파서 정확도 문제"로 격하되었다.**

5e였다면 `DC 몇?`, `데미지 몇d몇?`, `어떤 세이빙?`을 **숫자 창작**해야 했다. PbtA에는 DC가 없다. 판정은 항상 `2d6 + 능력치 → 10+ / 7-9 / 6-` 고정이고, 기본 무브 10개 중 **「위험을 무릅쓰다」가 만능 폴백**이다.

**처리 파이프라인**

```
자유 텍스트
   ↓  ① 무브 분류      [닫힌 집합]  기본 무브 10 + 플레이북 무브
   ↓  ② 능력치 선택     [닫힌 집합]  힘·민첩·건강·지능·지혜·매력
   ↓  ③ 주사위          [순수 코드]  LLM 관여 없음 (D14)
   ↓  ④ GM 무브 선택    [닫힌 집합]  7-9 / 6- 일 때만
   ↓  ⑤ 서술           [자유 생성]  LLM 강점 영역
```

**LLM은 ①②④에서 분류만, ⑤에서 서술만 한다.** 판정·연산에는 닿지 않는다.
원칙 1("LLM은 파서일 뿐 저지가 아니다")이 사실상 유지되면서 ③ 플레이어 주체성도 확보된다.

**GM 무브도 닫힌 목록이다.** DW는 이를 명시적 목록으로 제공한다 — 위협을 드러낸다 / 자원을 소모시킨다 / 불리한 위치로 몰아넣는다 / 피해를 입힌다 / 다가올 위협을 알린다 / 대가를 요구하되 이득을 준다 / 가진 것을 빼앗는다 / 세계의 특성을 이용한다 / **전선의 징조를 진행시킨다**(D9와 직결) 등. 창작은 "고른 무브를 이 상황에 맞게 서술하는 것"으로 좁혀진다.

**판정 발동 방식 = (다) 혼합형 확정**

LLM이 제안하면 플레이어가 확인한다.

> "이건 「위험을 무릅쓰다」 판정이 필요해 보입니다  [민첩으로 굴리기]  [아니오, 그냥 하는 겁니다]"

- **(가) LLM 단독 판단**(정통 fiction-first)은 일관성이 흔들린다 — "아까는 안 굴렸는데 왜 지금은?"
- **(나) 플레이어 선언**은 초심자에게 룰 지식을 요구한다
- **(다)**는 초심자가 무브 이름을 몰라도 되고, 플레이하면서 무엇이 왜 판정인지 배우게 되며, 잘못된 분류를 그 자리에서 막을 수 있어 D12 투명성 원칙과 맞는다. 대가는 클릭 한 번.

**부수 효과 — W9(confidence 임계값) 해소.** 모든 분류가 어차피 플레이어 확인을 거치므로 0.9 임계값과 폴백 UI가 불필요해진다. 신뢰도는 **UI 강도**로만 쓴다.

| 신뢰도 | UI |
|---|---|
| 높음 | 무브가 선택된 상태로 제시. 엔터 한 번 |
| 낮음 | 후보 2~3개 나란히 제시. 명시적 선택 요구 |
| 무브 없음 | "판정 없이 진행합니다" + 되돌리기 |

신뢰도가 과신으로 틀려도 플레이어가 보고 고친다. **임계값 튜닝이라는 끝없는 작업이 사라진다.**

**Ruling 계층으로 들어오는 3종**

| 들어오는 것 | 출처 |
|---|---|
| 룰북에 없는 창의적 행동 | C1 (원래 목적) |
| 효과 DSL로 표현 못 한 롱테일 (`requires_ruling`) | D7 |
| 판정이 필요 없는 그냥 되는 일 | M6 (판정 없는 롤플레이) |

세 번째가 중요하다. **플레이의 절반 이상은 판정이 없다.** "무브 없음 → 그냥 서술" 경로가 명시적으로 존재해야 한다.

**재사용:** 자주 나오는 Ruling은 방장이 홈브루로 굳혀 자동화로 승격시킬 수 있다(D12 Override와 동일 메커니즘). **자동화율이 플레이하면서 올라간다.**

### D17. 아키텍처 축소 — 서브에이전트 10개 → 4개

| 원 설계 | 결정 | 사유 |
|---|---|---|
| `master_gm` | **유지** | 핵심 |
| `combat_parser` | **병합** | DW에는 전투가 별도 시스템이 아님 |
| `exploration_parser` | **병합** | → `action_classifier`로 통합 |
| `onboarding_agent` | **유지** | DW 플레이북이라 훨씬 단순해짐 |
| `context_summarizer` | **유지** | 배경 배치 |
| `rules_interpreter` (RAG) | **보류** | DW 룰북은 작아 통째로 프롬프트에 들어감. UGC 대형 룰북 등장 시 M1 부활 |
| `entity_ledger_keeper` | **코드로 강등** | 에이전트가 아니라 DB + 코드 |
| `dice_narrator` | **병합** | 별도 호출은 지연만 늘림 → `master_gm` 내부로 |
| `reaction_classifier` | **삭제** | 리액션 큐 자체가 삭제됨 (D10) |
| `initiative_resolver` | **삭제** | **DW에는 이니셔티브가 없음** (D4) |

**남는 4개**

| 에이전트 | 티어 | 역할 |
|---|---|---|
| `action_classifier` | Light | 자유 텍스트 → 무브 + 능력치 분류 + 신뢰도 (D16 ①②) |
| `master_gm` | **Heavy (M0)** | GM 무브 선택 + 서사 생성 (D16 ④⑤) |
| `onboarding_agent` | Medium | 플레이북 인터뷰 |
| `context_summarizer` | Light | 배경 압축 + 리캡 생성 (D11) |

**메시지 버스도 축소.** gRPC + Redis Streams 이중 구성은 M0에 과하다. Session Actor 하나가 유일한 직렬화 지점이므로 **인프로세스 함수 호출로 충분**하다. 분산이 필요해지면 Actor를 프로세스 밖으로 빼면 되고, 구조는 바뀌지 않는다.

**턴당 LLM 호출**

```
원 설계:  파서(1) + 리액션분류(0~1) + master_gm(1) + dice_narrator(1)  = 3~4회
새 설계:  action_classifier(1) + master_gm(1)                        = 2회
판정 없는 행동:  classifier "무브 없음" → master_gm(1)                = 1회
→ 실제 평균 약 1.5회 (플레이의 절반 이상이 판정 없는 행동, M6)
```

**W8(레이턴시 모순) 해소.** (다)의 플레이어 확인이 중간에 끼면서 체감 지연이 분산된다.

```
입력 → classifier(~0.3초) → [플레이어 확인: 사람 시간] → 주사위(0초) → master_gm 스트리밍(첫 글자 1~2초)
```

목표를 "E2E 3초"에서 **"확인 후 첫 글자까지 2초"**로 교체한다.

**W7(뷰별 정보 분리) 대폭 축소.** DW에는 전장의 안개가 없다(좌표계가 없으므로). 시야 계산 문제는 M4로 이동. M0에 남는 건 **개인 정보**(몰래 하는 행동, 캐릭터 비밀, 개인 단서)뿐이며, `master_gm` 출력에 가시성 필드만 두면 된다.

```json
{ "visibility": "public" }
{ "visibility": "private", "to": ["player_3"] }
```

이벤트 소싱(D3)과 궁합이 좋다. 이벤트마다 가시성이 붙고 플레이어별로 다른 필터를 통과시킨다. M4에서 시야 계산이 들어와도 **같은 메커니즘을 재사용**한다.

### D18. `master_gm` 모델 티어 — M0은 Heavy, 이후 이원화

**M0 = Heavy 고정.** 이후 (C) 상황별 이원화로 내린다 — 일상 서술은 Medium, 결정적 순간(전선 징조 진행, 캐릭터 죽음, 강한 성공/실패)은 Heavy.

**순서를 이렇게 잡는 이유:** M0의 목적은 "재미있나"다. Heavy로도 재미없으면 제품이 성립하지 않으므로 거기서 판단이 끝난다. Heavy로 재미있으면 그때 내리면서 **"어디까지 내려도 재미가 유지되는가"**를 측정한다. 순서를 반대로 하면 모델이 작아서 재미없는 건지 설계가 틀려서 재미없는 건지 구분할 수 없다.

> **M0에서 재는 것은 원가가 아니라 품질 상한선이다. 원가는 M0 이후에 깎는 대상이다.**
> 단, M0은 **원가가 생존 가능한 범위인지는 답해야 한다** (타당성 검토가 M0의 목적이므로).

**이원화 시 과제:** 문체·NPC 말투 일관성 유지.

### D19. 모델 전략 — 에이전트별 분리, 교체 가능하게

**모델을 하나로 통일해 판단하지 않는다.** 두 에이전트의 요구가 다르다.

| | `action_classifier` | `master_gm` |
|---|---|---|
| 난이도 | 낮음 (닫힌 집합 분류 + JSON) | 높음 (한국어 창작 서사, 페르소나 유지) |
| 검증 | **객관적 가능** (골든셋 정답률) | 주관적, Task #9 필요 |
| 원가 비중 | 5% | **95%** |
| 하향 시점 | **M0에서 바로 A/B 가능** | Task #9 완성 후에만 |

- **프로바이더 추상화 계층을 M0에 넣는다.** 에이전트별 모델·프로바이더가 설정값이어야 한다. 지금은 공짜, 나중은 재작성
- **자체 호스팅은 M0의 결정 사항이 아니다.** TRPG는 이용률 패턴이 최악(저녁 8시~자정 집중)이라 실효 원가가 이론값의 3~4배가 된다. 기저 부하 확보 후 하이브리드(기저 자체 / 피크 API) 검토
- **한국어 서사 품질이 특수 변수다.** 영어 벤치마크는 참고가 안 되므로 별도 측정 필요

**원가 요약** (1인 1시간당): 프론티어 $0.30 / 이원화 $0.20 / 저가 모델 $0.03~0.10 / 자체 호스팅 $0.07(이용률 30% 기준)

**캐싱이 지배 변수다.** 캐싱 없으면 3.7배. 프롬프트 조립 순서를 안정성 순서(영구 고정 → 세션 고정 → 턴마다 변함)로 짜는 것은 최적화가 아니라 **M0의 설계 제약**이다.

상세: `GPTRPG-cost-analysis.md`

### D20. 수익 모델

**무제한 정액제는 성립하지 않는다.** 솔로가 파티보다 1인당 7~8배 비싸기 때문(LLM 호출은 턴 수에 비례하고 사람 수에 비례하지 않음 — 파티는 4명이 원가를 나눠 씀). 관전자는 원가 0.

**확정: (다) 등급제 + 소프트 상한 & (라) 파티/솔로 분리**

**무료 티어 — 시간 카운터를 만들지 않는다.**

> "남은 플레이 시간 12시간"을 띄우는 순간 **시계를 보며 노는 게임**이 된다. TRPG 몰입과 상극.
>
> 대신 **"첫 캠페인 무료"** — 전선(Front) 1개를 끝까지.

**D9의 Fronts 구조가 그대로 과금 단위가 된다.** 전선 1개 = 콘텐츠 1개 = 상품 1개. 시계가 안 보이고, 원가 예측이 되고, 완결감이 다음 구매로 이어진다. 소프트 상한은 뒤에 숨겨 어뷰징만 차단한다.

**코스메틱**

| 항목 | M0~M3 | 비고 |
|---|---|---|
| 주사위 스킨 | ✅ | 판정은 항상 있음 |
| **서사 로그 테마** (폰트·색·프레임) | ✅ | **노출 시간 최장. 주사위보다 김** |
| 캐릭터 초상화·아바타 | ✅ | 상시 노출 |
| 캐릭터 시트 테마 | ✅ | 플레이 내내 열림 |
| **캠페인 기념품** (4.2절 모먼트 연대기) | ✅ | 감정 가치 최고. 물리 인쇄로 객단가 확장 |
| 말·토큰 스킨 | ❌ → M4 | **DW에는 그리드가 없어 놓을 보드가 없음** |

**UGC 마켓(장기)이 코스메틱보다 클 수 있다.** 다만 Task #12의 "유저 룰북 수익화 금지"와 충돌 — 저작권 리스크가 이유였으므로 **자작 오리지널 한정 허용**으로 재검토 필요.

### D21. 위협 시계 — 데이터 구조와 진행 규칙

시나리오의 뼈대. 대본이나 분기 트리가 아니라 **"나쁜 일 목록 + 순서"**만 저장한다. 칸 사이의 사건과 플레이어 대응은 AI가 즉흥 생성한다.

**데이터 구조**

```
위협 시계
├─ 이름 / 한 줄 요약
├─ 분량 (칸 수)               ← 상품 단위이자 무료 제공분 원가의 기준
├─ 톤 태그 (진지/코믹/호러)     ← 매칭·로비에 사용 (Task #6)
├─ 위협의 정체
├─ 그것이 원하는 것            ← AI에게 주는 행동 지침 (한 문장)
├─ 등장인물 [ ]               ← 엔티티 장부와 연결
├─ 시계 칸 [순서 있음]
│    ├─ 순번 / 무슨 일이 일어나나 (한 문장)
│    ├─ 상태: 대기 | 진행됨 | 무효화됨
│    ├─ 진행 조건 (조건 트리거)
│    └─ 진행 후 세상에 남는 흔적  ← 이후 판정 조건에 반영
├─ 파국 (끝까지 갔을 때)
└─ 시작 칸 (몇 번부터 시작)
```

**진행 규칙 — 세 가지를 함께 쓴다**

| # | 방식 | 역할 |
|---|---|---|
| ① | **실패 누적 카운터.** 판정 실패 시 +1, N회(기본 3, 시계별 조절) 도달 시 강제 1칸 진행 후 초기화 | **봐주기 방지 안전장치.** AI 의지와 무관하게 프로그램이 센다 |
| ② | **조건 트리거.** 시간 경과·장소·선행 칸 진행 여부 등 | 세상의 관성. 플레이어가 딴 데 있어도 움직인다 |
| ③ | **AI 선택.** 실패·부분성공 시 GM 대응 목록에서 "시계 진행"을 고를 수 있음 | 연출 타이밍 자유도 |

③만 있으면 봐주기가 생기고, ①만 있으면 기계적이 된다. 셋이 함께여야 한다.

**①이 관측 지표를 공짜로 만든다.** 실패 횟수와 칸 진행 횟수가 모두 이벤트 로그에 남으므로, "실패는 많은데 시계가 안 돈다"(= AI가 봐주고 있다)를 사후에 자동 집계할 수 있다. Task #9의 관측 필드 요구가 여기서 충족된다.

**플레이어 승리:** 칸이 무효화되거나 시계 전체가 종료된다. 이것이 캠페인 승리 조건.

**분량과 무료 정책 — D20 정정**

| 무료 단위 | 플레이 시간 | 파티 1팀 (프론티어) | 파티 1팀 (저가) | 1,000팀 |
|---|---|---|---|---|
| 첫 **에피소드** (1~2칸) | 2~5시간 | $2.5~6 | $0.5~1.2 | **$2,500~6,000** |
| 첫 **캠페인** (4칸 전체) | 8~12시간 | $10~15 | $2~3 | $10,000~15,000 |

> **D20의 "첫 캠페인 무료"를 "첫 에피소드 무료"로 정정한다.**
> 원 계산은 세션 하나 기준이었는데 캠페인 전체를 무료로 주는 안이었다. 4~5배 차이.
>
> 에피소드 하나도 작은 완결이 있어 이야기가 끊긴 느낌이 없고, **시계가 남아 있는 상태로 끝나는 것이 오히려 구매 동기가 된다**(드라마 1화 무료 구조).

**확정 규격:** 시계 하나 = **4~6칸 / 8~15시간**. 무료 = **1~2칸**.

**저작 주체 — (다)안 확정**

| 주체 | 개수 | 용도 |
|---|---|---|
| **우리** | 3~5개 | 론칭용. 톤 분산(진지/코믹/호러). **초보자 첫 경험은 반드시 이 중에서** |
| **유저** | 무한 | 동일 양식. 공개 시 검수 후 마켓 등록 |
| **AI** | 무한 | 동일 양식 생성. **초보자 첫 경험에는 사용하지 않음** |

**셋이 완전히 같은 양식을 쓴다.** 시스템은 출처를 구분하지 않고 동일하게 실행하며, 저작 도구도 하나면 된다. 우리가 손으로 만드는 3~5개가 사실상 **양식의 검증** 역할을 한다 — 만들어보면 빠진 필드가 드러난다. AI 생성기와 유저 저작 도구는 그 뒤에 붙인다.

### D22. 캐릭터 만들기 — 7가지 동작 + 애착 설계

**M0의 범위 기준** (이 표로 돌아와 판단한다)

| M0에서 **하는** 것 | M0에서 **안 하는** 것 |
|---|---|
| 데이터가 어떻게 생겼는지 | 화면 배치 |
| 절차가 몇 단계이고 무슨 순서인지 | 버튼 위치·색·애니메이션 |
| 어떤 규칙으로 검증하는지 | 컴포넌트 구조, 프론트엔드 |
| 룰북이 바뀌어도 재사용되는 부분 | 반응형·모바일 대응 |

**어떤 룰북이든 캐릭터 만들기는 7가지 동작의 조합으로 표현된다**

| # | 동작 | 예 |
|---|---|---|
| ① | 목록에서 하나 고르기 | 플레이북, 클래스, 직업 |
| ② | 목록에서 여러 개 고르기 | 기술 3개, 시작 주문 2개 |
| ③ | 숫자를 나눠 담기 | 포인트 27점 배분 |
| ④ | 정해진 숫자를 자리에 배치 | 15·14·13·12·10·8 배치 |
| ⑤ | 주사위 굴려 채우기 | 4d6k3, 3d6 |
| ⑥ | 자유롭게 쓰기 | 이름, 외모, 백스토리 |
| ⑦ | 자동 계산 | 체력, 방어도, 숙련 보너스 |

**룰북 데이터가 "만들기 단계 목록"을 갖고, 시스템은 그것을 순서대로 실행한다.** D5(커널=코드, 룰북=데이터)와 D7(효과 DSL)의 연장이며 새 방식이 아니다. 화면 부품도 7개면 모든 룰북에 재사용된다.

**애착 설계 — 프리젠 우선 안을 폐기한다**

> ~~초보자에게 완성품 집어들기(30초)를 기본 경로로 제공~~
>
> **폐기 사유:** ② 결과의 무게(양보 불가)와 충돌한다. 30초에 집어든 캐릭터가 죽으면 아프지 않다. **애착은 투자에서 나오고, 투자가 일어나는 유일한 지점이 캐릭터 만들기다.** 그것을 건너뛰게 하면 우리가 지키기로 한 것을 스스로 무너뜨린다.

문제는 길이가 아니라 **선택의 종류**였다.

| 재미있는 것 | 지루한 것 |
|---|---|
| 의미가 즉시 이해되는 선택 | 뜻을 모르는 항목 고르기 |
| 고르면 달라지는 게 보이는 선택 | 결과가 안 보이는 숫자 입력 |
| 내가 누구인지 정하는 선택 | 시스템이 해도 되는 계산 |

"클래스 13개 중 하나"는 개수가 아니라 **이해할 수 없는 선택**이 문제였다.

**장치 6개**

1. **숫자를 서술로 번역해 실시간 표시.** `민첩 +2` 옆에 "당신은 그림자처럼 움직인다. 좁은 틈을 지나고, 소리 없이 다가간다." 숫자를 옮기면 문장이 바뀐다. **룰북 지식을 요구하는 대신 결과를 보여준다** — 이것이 "룰북 안 읽어도 된다"의 실제 구현
2. **선택지를 이야기 질문으로 감싼다.** "플레이북 선택" → "당신은 위험을 어떻게 마주합니까? / 정면으로 · 그림자에서 · 이해하려고 · 남을 지키며". 고른 뒤에 직업명을 알려주면 그때는 의미를 갖는다. 원 기획안의 "롤플레이로 녹여낸다"를 살리되, **AI 자유 대화가 아니라 선택지 형태로** (더 빠르고 통제됨)
3. **순서를 바꾼다.** 재미있는 것(누구인가 → 무엇을 잘하나 → 무엇을 들었나 → 이름·외모) 먼저, 기계적인 것(숫자 배치 → 자동 계산) 뒤로. **기계적 단계는 추천값이 미리 채워진 상태로 제시** — 취향 있는 사람은 만지고 초보자는 넘긴다
4. **되돌리기 상시 제공** (원 기획안 유지)
5. **자유 서술 → AI 추천.** 백스토리를 읽고 나머지 선택에 추천을 붙인다. **자동 확정 금지, 추천만** (원 기획안 유지)
6. **완성 순간 보상.** 캐릭터 카드 연출 — 이름·초상화·한 줄 소개("로빈 — 뒷골목에서 자란, 그림자를 믿는 자"). 애착의 시작점이자 코스메틱 판매 지점(D20)과 연결

**경로**

| | 소요 | 애착 |
|---|---|---|
| ~~완성품 집어들기~~ | ~~30초~~ | **없음 — 폐기** |
| 거의 다 된 캐릭터 + 마지막 3~4개 선택 | 2분 | 있음 |
| 전 과정 직접 | 5분 | 강함 |

**30초 경로를 없애는 것이 핵심.** 마지막 몇 개를 직접 골랐으면 그건 자기 캐릭터다.

**목표:** 던전월드 기준 5분 (전 과정)
**성공 기준:** 완성 직후 유저가 **"내 캐릭터는 누구다"를 한 문장으로 말할 수 있는가.** 플레이테스트에서 "당신 캐릭터 어떤 사람이에요?"라고 물어 확인 가능

### D23. 안전 장치 — AI가 갖지 못한 "GM의 눈"

**문제 정의**

TRPG는 어두운 주제를 다루고 그것이 재미의 일부다(② 결과의 무게). 그런데 견딜 수 있는 선은 사람마다 다르고, **TRPG는 콘텐츠 등급을 사전에 붙일 수 없는 매체다** — 이야기가 그 자리에서 만들어지므로 아무도 오늘 무슨 내용이 나올지 모른다. 그래서 정통 TRPG는 사전 등급 대신 **실시간 브레이크**를 쓴다.

> **인간 GM은 플레이어의 표정이 굳는 것을 보고 말없이 화제를 돌린다. AI는 표정을 볼 수 없다.**
>
> 안전 장치는 규정 준수 기능이 아니라 **AI가 갖지 못한 GM의 눈을 대체하는 장치**다.

타깃 정의에 "처음 보는 모험가들"이 포함되므로 선택이 아니라 필수다. 친구끼리는 서로의 선을 알지만 낯선 사람끼리는 모른다.

**정통 TRPG의 표준 도구 (새로 발명하지 않는다)**

| 원래 이름 | 이 문서의 용어 | 무엇인가 |
|---|---|---|
| Session 0 | **0번 모임** | 시작 전에 다루지 않을 것을 정하는 대화 |
| Lines & Veils | **선과 장막** | **선** = 아예 등장하지 않음 / **장막** = 일어나지만 묘사하지 않음 |
| X-Card | **정지 카드** | 누구든 아무 때나 말없이 장면 중단을 요청하는 장치 |

**「장막」이 핵심 개념이다.** "안 다룬다"와 "자세히 묘사한다" 사이의 중간 — "당신은 문을 닫는다. 안에서 무슨 일이 있었는지는 다음 날 아침에야 알게 된다." **이야기의 무게를 유지하면서 묘사만 뺀다.** 안전 때문에 이야기를 물렁하게 만들지 않아도 된다.

**4개 층**

**1층 — 방 생성 시 선을 정한다**

```
■ 톤:  진지 / 코믹 / 호러
■ 선 (아예 안 나옴):   고문 · 성적 위협 · 자해 · 아동 위해 · 동물 학대 · 극단적 신체 훼손
■ 장막 (나오지만 묘사 안 함):  같은 목록에서 별도 선택
```

참가자는 입장 시 이 목록을 방 정보로 본다(체크박스 동의 아님). **낯선 사람 매칭에서는 이것이 곧 필터가 된다** — 같은 선을 가진 사람끼리 매칭하면 갈등이 애초에 줄어든다(Task #6과 연결).

**2층 — 정지 카드**

버튼 하나. 세 원칙이 절대적이다.

| 원칙 | 이유 |
|---|---|
| **익명** | 누가 눌렀는지 안 보인다. 이름이 보이면 아무도 안 누른다 |
| **설명 요구 없음** | "왜요?"를 물으면 못 누른다 |
| **즉시 작동** | 다음 문장이 나오기 전에 멈춘다 |

강도 2단계: `[이 장면을 돌려주세요]` (현재 장면만) / `[이 주제를 빼주세요]` (이후 선에 추가)

**3층 — AI가 넘지 않게 하는 3겹**

1. 방의 선·장막 목록을 GM 프롬프트에 상시 포함
2. **GM 출력을 내보내기 전 검사.** 원 기획안의 "백엔드가 무결성을 검증한 뒤 송신" 구조에 그대로 붙는다 — 새 구조가 아니다
3. 장막 처리: 삭제하지 않고 "문이 닫힌다" 식 전환

**4층 — 사람이 문제일 때**

신고(다른 사람에게 안 보임 — D17의 개인 채널 구조 재사용) / 방장 강퇴 / 차단(재매칭 제외). D15의 "사회적 제재" 층이 이것이다.

**핵심 설계 판단 — 안전 장치가 몰입을 깨면 안 된다**

```
(X)  ⚠️ 안전 장치가 사용되었습니다. 장면을 조정합니다.
     → 게임이 멈추고, 누군가 눌렀다는 게 드러나고, 다음부터 아무도 안 누른다

(O)  (아무 알림 없이 이야기가 자연스럽게 다른 데로 흐른다)
```

좋은 GM이 하는 것이 정확히 이것이다 — 정지 카드가 올라오면 아무 말 없이 화제를 바꾸고 지적하지 않는다. **AI에게 "안전 장치 작동 사실을 언급하지 말 것"을 명시적으로 지시해야 한다.** 프롬프트 설계 항목.

**⚠️ 미결 — 법률 확인 필요 (제 판단 범위 밖)**

- 방 등급 (전체 / 15세 / 청소년 이용 불가)
- 낯선 사람 매칭 시 성인 인증 필요 여부 (친구 초대 링크와 다를 수 있음)
- **AI 실시간 생성 콘텐츠의 등급 분류 책임** — 사전 심의가 구조적으로 불가능하므로 실시간 필터 + 사후 신고 체계로 대응한다는 법적 근거가 필요

→ 국내 게임물 등급 분류 제도가 AI 실시간 생성물을 어떻게 다루는지 확인 필요. 스폰서 기업 법무 라인에 문의할 항목.

### D24. 사람이 오고 가는 문제 — 친구 초대 링크 우선, 낯선 사람 매칭은 미룬다

**확정: M1은 친구 초대 링크만. 공개방 매칭은 M2 이후.**

매칭에는 신고·차단·성인 인증·톤 필터가 전부 딸려 오는 큰 덩어리다. 초대 링크만으로 먼저 출시하면 M1 범위가 크게 줄어든다.

**M1에 남는 것 / M2로 미루는 것**

| 항목 | M1 | 사유 |
|---|---|---|
| 초대 링크 (디스코드·카톡에 붙여넣을 URL) | ✅ | 이것만 잘 되면 친구 플레이는 충족. 로그인·친구추가·초대승인 안 만듦 |
| **정지 카드** (D23 2층) | ✅ | **친구끼리도 선은 다르고, AI는 여전히 브레이크가 없다** |
| **선·장막 방 설정** (D23 1층) | ✅ | 같은 이유 |
| **AI 출력 검사** (D23 3층) | ✅ | 같은 이유 |
| 중도 이탈 처리 | ✅ | **구조이므로 미룰 수 없다** (아래) |
| 정원 미달 진행 | ✅ | 친구끼리도 한 명은 못 온다 |
| 첫 만남 캐릭터 소개 | ✅ | 친구라도 서로의 캐릭터는 모른다 |
| 진행 중 합류 | ✅ | "돌아오기"와 같은 메커니즘이라 공짜 |
| 신고·차단 (D23 4층) | ⬜ M2 | 친구끼리는 불필요 |
| 공개방 목록·톤 필터 | ⬜ M2 | 친구끼리는 외부에서 합의 |
| 성인 인증 | ⬜ M2 | 매칭이 없으면 쟁점이 작아짐. **다만 서비스 자체의 등급 분류는 여전히 확인 필요** |

**사람이 빠질 때 — 세 경우를 다르게 처리한다** (원 기획안은 "AFK 타임아웃" 하나로 뭉쳐놨다)

| 경우 | 처리 |
|---|---|
| **잠깐 자리 비움** (화장실·전화) | 아무것도 안 함. "자리 비움" 표시 + 타인이 순서 넘기기 |
| **오늘 중도 이탈** (다음엔 옴) | **서사적 배경화.** "타렌은 일행과 함께 있지만 오늘은 말이 없다." 존재 유지, 행동·판정 없음 |
| **영구 이탈** | 캐릭터는 남긴다(언제든 복귀). 일정 기간 무응답 시 자리를 "모집 중"으로. **시스템이 자동 축출하지 않고 방장이 판단** |

> ⚠️ **AI가 남의 캐릭터를 조종하지 않는다.**
> 많은 온라인 TRPG 도구가 "GM이 대신 굴려주기"를 하지만 우리는 금지한다. 돌아온 유저가 "내 캐릭터가 그런 짓을 했다고?"가 되면 **③ 플레이어 주체성(양보 불가) 위반**이다. 실제 테이블에서도 결석자 캐릭터는 "뒤에서 따라온다"로 처리한다.

**진행 중 캠페인에 신규 합류 — 이미 가진 것으로 해결된다**

| 필요한 것 | 이미 있는 것 |
|---|---|
| 지금까지 무슨 일이 있었나 | 파티 리캡 (D11, 재개용) |
| 위협이 어디까지 왔나 | 위협 시계 상태 (D21) |
| 이 사람들이 누군가 | 엔티티 장부 + 각 캐릭터 한 줄 소개 (D22) |

**같은 데이터로 "돌아온 사람"과 "새로 온 사람"을 동시에 처리한다.** 위협 시계 구조 덕분에 신규 합류자도 "우리가 어디로 가고 있는지"를 한눈에 안다 — 대본형 시나리오였으면 불가능했다.

**핵심 결정: 정원이 안 차도 진행한다**

```
(X) 4명이 다 와야 시작  →  한 명 못 오면 무산  →  두 번 무산되면 캠페인 사망
(O) 온 사람으로 진행    →  2명만 와도 굴러감
```

**전원 출석을 요구하지 않는다.** 경험 많은 온라인 GM들이 하는 방식과 같다.

**이것이 가능한 이유가 위협 시계 구조다.** 시계는 **사람 수와 무관하게** 정해진 규칙대로 돈다. 대본형이었다면 "이 장면은 4명이 필요합니다"가 생겼을 것이다. 단, 인원이 적으면 위협의 압박을 낮춘다(2명이 4명용 위협을 상대하면 전멸).

**첫 만남 — 캐릭터 소개 한 줄**

D22의 성공 기준("내 캐릭터는 누구다를 한 문장으로")이 여기서 실제로 쓰인다. 캐릭터 만들기 마지막에 생성되는 한 줄 소개가 그대로 자기소개가 된다.

> **낯선 사람끼리 애착의 시작점은 서로의 캐릭터다.** 사람은 몰라도 캐릭터는 안다. 남의 캐릭터에 관심이 생기면 다음 세션에 온다.

### D25. 캐릭터 라이프사이클 — 유형 목록으로 (초안 폐기 후 재작성)

> ⚠️ **초안 폐기 사유.** 첫 설계에서 던전월드의 규칙(실패→경험치 / 세션 끝 질문 3개 / 장비 회분 추상화 / 죽음 협상 / 5분 생성 목표)을 **플랫폼 기능**으로 올렸다. 이는 **원칙 2의 정신과 원칙 3 위반**이다. 아래로 대체한다.

캐릭터 만들기를 7가지 동작으로 쪼갠 것과 **같은 방식**을 적용한다. 유형은 우리가 코드로 구현하고, **어느 유형인지는 룰북이 데이터로 선언한다.**

**성장 (Advancement)**

| 유형 | 어떻게 | 대표 |
|---|---|---|
| 경험치 누적 | 점수를 모아 레벨업. **획득 조건은 룰북이 별도 정의** | D&D(적 격파·목표 달성), 던전월드(판정 실패·세션 질문) |
| 사용 기반 개선 | 성공한 기술에 표시 → 나중에 성장 판정 | 크툴루 계열, BRP 계열 |
| 점수 지급 | 세션 후 점수를 받아 원하는 곳에 사용 | 월드 오브 다크니스, FATE |
| **성장 없음** | 성장이 없는 것이 설계 의도 | 원샷 시나리오, 일부 호러 |

**"경험치를 얻는 조건"은 별도 데이터다.** 우리가 정하지 않는다.

**회복 (Recovery)**

| 유형 | 대표 |
|---|---|
| 휴식 기반 (짧은/긴 휴식) | D&D 5e |
| 시간 경과 기반 (일당 얼마) | 크툴루 계열 |
| 치료 판정 기반 | 다수 |
| 안전지대 기반 | 던전월드 |
| **거의 회복 안 됨** | 호러 계열 — 설계 의도 |

**장비 (Inventory)**

| 유형 | 대표 | 비고 |
|---|---|---|
| **개별 품목 + 무게·슬롯 제한** | D&D, OSR | **1순위 구현.** 자원 관리가 게임의 핵심인 경우가 많다 |
| 추상 회분 | 던전월드 | 초안에서 이것을 기본으로 잡은 것은 순서가 거꾸로였다 |
| 하중 등급만 | 일부 룰북 | |
| 관리 없음 (서사적으로만) | 일부 서사 룰북 | |

> **도라에몽 주머니 문제.** 추상 회분을 모든 룰북에 적용하면 "필요할 때 아무거나 꺼낼 수 있는" 상태가 되어 밸런스가 붕괴한다. 자원 압박이 재미인 룰북에서는 개별 품목 관리가 **기능이지 부담이 아니다.**

**죽음 (Death)**

| 유형 | 대표 | 비고 |
|---|---|---|
| **즉사** | OSR, 일부 호러 | **설계 의도. 관용을 넣으면 게임이 망가진다** |
| 빈사 → 안정화 판정 | D&D 5e | |
| 협상 | 던전월드 | |
| 부상 누적 (죽음 대신 영구 손상) | 일부 룰북 | |
| **캐릭터 교체 전제** | 크툴루 계열 | 조사자가 죽거나 미치는 것이 정상 흐름 |

**화폐**도 같은 패턴 — 단일 통화(던전월드 코인)부터 다중 통화(D&D 금·은·동 환산)까지 룰북 데이터에 정의.

**플랫폼 층으로 남는 것 (룰북 무관)**

| 항목 | 층 |
|---|---|
| 세션 마감 시점에 뭔가를 할 수 있는 **자리** | ① 플랫폼 — 그 자리에서 무엇을 할지는 룰북이 정함(던전월드는 질문 3개, 없는 룰북은 아무것도 안 함) |
| 죽은 캐릭터의 기록 보존 → 캠페인 기념품(D20) | ① 플랫폼 — 죽음 규칙과 무관하게 기록은 남는다 |
| 레벨업 화면이 7가지 동작을 재사용 | ② 어휘 — 성장 유형이 무엇이든 "고르기·배분하기"로 표현됨 |
| 숫자를 서술로 번역 표시 | ② 어휘 — 번역 내용은 룰북에서 온다 |

**초안에서 살릴 만한 관찰 (룰북별 특성으로 기록, 플랫폼 기능 아님)**

- 던전월드가 "실패→경험치"로 좌절을 완화하는 구조는 **던전월드의 우수한 설계**다. 초보자 친화적 룰북을 고를 때의 판단 근거로는 유효하나, 다른 룰북에 이식하지 않는다
- 죽은 캐릭터가 파티의 전설이 되는 현상은 TRPG 문화의 보편적 특징이므로, **기록 보존**은 플랫폼 층으로 둘 수 있다

### D26. 룰북의 실제 형태 — 원문을 버리지 않는다

**문제.** 구조화 데이터(JSON 등)를 유저가 직접 작성하게 하면 저작 진입장벽이 치명적으로 높아진다. 사람은 자연어 백과사전 형태로 룰북을 써왔고, 그게 편하다. 문법을 배우게 하면 아무도 쓰지 않는다.

**놓쳤던 것.** 초기 설명은 "자연어 → 변환 → 구조화 데이터(원문은 버림)" 그림이었다. **원문은 버리는 게 아니라 시스템의 일부다.** 이미 정한 것들이 원문을 요구하고 있었다.

| 이미 정한 것 | 원문이 필요한 이유 |
|---|---|
| 재량 판정 계층 (D16) | AI가 판단할 때 원문을 읽어야 함 |
| 판정 근거 표시 (D12) | 가리킬 원문이 있어야 함 |
| **자동화율** (D7) | **자동화 안 된 부분은 원문으로 굴러간다** |

세 번째가 핵심이다. 자동화율이 100%가 아니어도 플레이 가능하다는 것은 곧 **구조화되지 않은 부분이 원문으로 처리된다**는 뜻이다.

**룰북 = 세 부분**

```
① 원문 (자연어)      사람이 쓰고 읽는 것. 백과사전 형태 그대로.
                     게임 중에도 살아 있음 — 재량 판정이 읽는다
② 구조화 데이터       판정 방식 / 만들기 단계 / 라이프사이클 유형 / 효과 …
③ 연결               ①의 어느 문단이 ②의 어느 항목인가 → 판정 근거 표시에 사용
```

**유저가 쓰는 것은 ①뿐이다.** ②는 도구가 만들고 유저가 확인하며, ③은 자동으로 붙는다.

**저작 흐름**

```
1. 유저가 평소처럼 룰북을 쓴다 (또는 가진 파일을 올린다)
2. AI가 읽고 구조화 초안을 만든다
3. 유저가 확인한다                    ← 성패가 갈리는 지점
4. 확인된 부분만 자동 처리. 나머지는 원문 + 재량 판정
```

**확인할 때 구조화 데이터를 보여주지 않는다 — 시험 판정 결과를 보여준다**

```
(X)  { "move": "defy_danger", "stat": "dex", "on_miss": {"damage": "1d6"} }
     → 유저가 맞는지 알 수 없다

(O)  "민첩으로 위험을 무릅쓴다" 판정을 해봤습니다.
       2d6 = [3, 4] = 7,  민첩 +1  →  8  (실패)
       결과: 대미지 1d6 = 4
     이게 의도대로입니까?
     [맞습니다]  [아닙니다 — 방어구를 차감해야 합니다]
```

D22의 「숫자를 서술로 번역해 보여준다」와 같은 원칙을 저작 도구에 적용한 것이다. **유저는 자기 룰북을 알기 때문에, 결과가 이상하면 문법을 몰라도 안다.**

**핵심 — 저작은 한 번에 끝나는 일이 아니다 (점진적 구조화)**

| 기존 플랫폼 | 우리 |
|---|---|
| 다 입력하고 → 플레이 | **플레이하면서 → 입력이 쌓임** |
| 입력 안 하면 아무것도 못 함 | 원문만 있어도 플레이됨 (자동화율 20%) |
| 저작이 노동 | 저작이 플레이의 부산물 |

```
원문만 넣고 바로 시작        자동화율 20%  (대부분 재량 판정, 근거 표시됨)
        ↓  자주 나오는 판정을 굳힌다
                            자동화율 50%
        ↓  계속 쓰면서 자란다
                            자동화율 80%
```

**"굳히는" 메커니즘은 이미 만들어져 있다.** D12·D16의 홈브루 승격(자주 나오는 재량 판정을 방장이 굳혀 자동화로 올린다)이 곧 점진적 룰북 저작이다. 별도 기능이 아니다.

**안전한 기본값**

> **확실한 것만 구조화하고, 애매한 것은 원문 + 재량 판정으로 남긴다.**

AI 변환은 행동 분류(D16)보다 훨씬 어렵다 — 문서 전체와 규칙 간 상호작용을 이해해야 한다. 그리고 **틀리면 조용히 밸런스가 어긋난 채로 굴러간다.** AI가 "확실 / 애매"를 구분해 표시하고 애매한 것은 구조화하지 않으면, **틀린 규칙이 자동 실행되는 사고**가 나지 않는다. 자동화율이 낮게 시작하는 것이 잘못 구조화하는 것보다 안전하다.

**저작 도구의 범위를 정직하게 잡는다**

| 유저 유형 | 비중 | 필요한 것 |
|---|---|---|
| 있는 룰북을 **고른다** | 대다수 | 목록에서 선택. 저작 도구 안 씀 |
| 가진 룰북을 **올린다** | 소수 | 파일 업로드 + AI 변환 |
| 처음부터 **만든다** | 극소수 | 전체 저작 도구 |

> 저작 도구의 목표는 "모두가 쓰게"가 아니라 **"쓰려는 사람이 안 막히게"**다. 이를 헷갈리면 저작 도구에 과투자한다.

**룰북 파일 업로드 → M1 포함 확정.** 저작권은 기존 정책 유지(비공개는 관대, 공개 마켓은 엄격 — 자기가 가진 룰북을 자기 게임에 쓰는 것과 배포하는 것은 다른 문제).

### D27. 룰북 파일 목차 + 판정 엔진 형태 (2개 방식으로 검증)

**룰북 파일 목차** (② 표현 어휘)

```
룰북
├─ 메타          이름·설명·버전·저작자·라이선스 / 판정 방식 지정 / 자동화율(계산됨)
├─ 원문          자연어 그대로, 절 단위로 나뉨
├─ 캐릭터 정의    능력치 목록 / 파생값 계산식 / 캐릭터 종류 / 만들기 단계(7가지 동작 나열)
├─ 판정 정의      판정 종류 목록(닫힌 집합) / 결과 등급 집합 / 수정치 규칙
├─ 효과 목록      주문·특성·아이템 (원자 연산 조합)
├─ 라이프사이클    성장 / 회복 / 장비 / 죽음 / 화폐 유형 (D25)
├─ 적·위협 정의
└─ 원문↔구조 연결표
```

**두 판정 방식 비교 검증** — 하나만 보면 원칙 3 위반이 재발한다

| | 2d6 등급식 (던전월드 계열) | d100 롤언더식 (크툴루 계열) |
|---|---|---|
| 굴림 | 2d6 + 능력치 | d100 |
| **방향** | **높을수록 좋음** | **낮을수록 좋음** |
| 목표값 | **없음** (경계 10·7 고정) | **있음** (기술값이 목표) |
| 결과 등급 | **3개** | **최대 6개** (대성공/극단/어려운/보통/실패/대실패) |
| 난이도 표현 | 없음 | 목표값의 배수 (1 / ½ / ⅕) |
| 수정치 방식 | 숫자 가감 | **주사위 추가** (보너스 다이스) |

**발견 1 — 결과 등급을 코드에 고정하면 안 된다**

```
(X) 등급 = { 성공, 실패, 대성공, 대실패 }  ← 코드에 박음. 3개인 룰북도 6개인 룰북도 안 맞음
(O) 룰북이 자기 등급 집합을 선언한다. 등급마다 "조건" + "그때의 효과"
```

던전월드만 보고 짰다면 3개로 고정했을 것이다 — **원칙 3 위반이 판정 엔진에서도 발생할 수 있었다.**

등급이 **이름 목록이 아닌 경우**도 있다. 다이스풀 방식은 등급이 "성공 3개"처럼 **수치**다. 등급 표현이 목록과 수치 구간을 모두 받아야 한다.

**발견 2 — 수정치도 유형 목록이 필요하다**

"수정치는 숫자"라는 암묵 가정은 틀렸다.

| 유형 | 예 |
|---|---|
| 숫자 가감 | +1, -2 |
| **주사위 추가·제거** | 보너스 다이스(크툴루), 유리·불리(D&D) |
| 목표값 변경 | 난이도 상승 |
| **재굴림** | **푸시 롤(크툴루) — 그 룰북의 정체성.** 숫자 수정치만 지원하면 표현 불가 |

**발견 3 — 두 방식이 같은 인터페이스에 들어간다 (검증 통과)**

```
판정 요청 { 판정 종류 / 기준값 / 난이도(선택) / 수정치 목록(유형별) }
        ↓  판정 방식 코드 (순수 함수, 룰북 데이터를 읽어 계산)
판정 결과 { 굴림 원본(검증·표시용) / 최종값 / 등급 / 그 등급의 효과 }
```

두 방식이 같은 그릇에 담기는 것을 확인했으므로, 나머지 방식(d20식·다이스풀식 등)도 같은 형태로 추가 가능하다는 근거가 생겼다.

**효과 원자 연산** (30~50개 규모 목표)

```
피해를 준다 / 상태를 부여한다 / 저항 판정을 요구한다 / 판정을 수정한다 /
이동시킨다 / 자원을 쓴다·회복한다 / 발동 조건을 심는다(반격·기회공격) /
선택을 요구한다 / 집중을 요구한다  …
```

선례: 카드 게임(매직 더 개더링 등)이 25,000장 넘는 카드를 이 방식으로 구현해왔다. **표현 안 되는 것은 "재량 판정 필요"로 표시하고 사람이 판단한다** — 억지로 끼워맞추지 않는다(원칙 3).

**M0 범위 선**

| M0에서 확정 | M1 착수 시 |
|---|---|
| 목차 (어떤 항목이 있는가) | 필드 단위 상세 규격 |
| 두 판정 방식이 같은 그릇에 들어간다는 검증 | 실제 구현 |
| 등급·수정치가 룰북 선언 사항이라는 결정 | 원자 연산 최종 목록 확정 |
| 원자 연산이 30~50개 규모라는 판단 | 스키마 문서 |

필드 하나하나를 지금 정하는 것은 M0가 아니다 (D22의 「M0에서 하는 것 / 안 하는 것」 기준).

### D28. 자유 텍스트 해석 검증 계획

**층:** 검증 방법은 ① 플랫폼. **정답 데이터는 룰북마다 따로** 필요하다(판정 종류 목록이 룰북마다 다름).

**목표가 이미 바뀌어 있다.** 원 기획안은 "500개 샘플에서 신뢰도 0.9 이상이 95%, 오분류 1% 이하"였으나, D16에서 **신뢰도 임계값 자체를 폐기**했다(모든 해석이 플레이어 확인을 거침). 그러면 실패의 결과가 달라진다.

| | 원 설계 | 현 설계 |
|---|---|---|
| 잘못 해석하면 | **잘못 실행됨** | 플레이어가 고침 |
| 위험도 | 치명적 | **마찰만 발생** |
| 재야 할 것 | 정확도 | **마찰의 크기** |

**새 측정 기준 — 마찰**

| 상황 | 플레이어가 하는 일 | 판정 |
|---|---|---|
| 첫 제안이 맞음 | 엔터 한 번 | 이상적 |
| 첫 제안 틀렸으나 후보에 있음 | 클릭 한 번 | 허용 |
| 후보 어디에도 없음 | 직접 찾아야 함 | **문제** |

**목표: 앞의 두 가지 합쳐 95% 이상.** 숫자는 실측으로 조정한다(판정 종류가 닫힌 목록이라 분류 난이도는 낮은 편).

**측정할 실패 유형** — 단순 정답률보다 실패 방식이 중요하다(유형마다 대응이 다름)

| 순위 | 실패 유형 | 예 |
|---|---|---|
| **1** | **판정 필요 여부 오판 (양방향)** | 필요 없는데 요구 → "문 여는 데 판정을?" / 필요한데 안 함 → 긴장 소멸 |
| 2 | 목표 누락 | "공격한다" → 누구를? |
| 3 | 판정 종류 오분류 | 설득인데 위협으로 |
| 4 | 여러 행동 분해 실패 | "다가가서 벤다" → 이동+공격 |
| 5 | 메타 잡담을 행동으로 오인 | **중요도 낮음** — 아래 참조 |

> **5번의 중요도 하향 근거.** D10에서 플레이어끼리의 잡담은 외부 메신저에서 일어나고 입력창은 행동 선언용으로 정했다. 메타 대화("이 던전 무섭네")는 입력창에 오지 않는다 — 오면 입력창 오사용이며 부수적 문제다.
>
> 단, **캐릭터의 판정 없는 행동**("주변을 둘러본다", "인사한다")은 입력창의 정상 사용이며 중요하다. 이는 1번의 반대 방향이므로 1번에 통합했다. 플레이의 절반 이상이 판정 없는 행동이므로(M6), 여기서 자꾸 주사위를 요구하면 게임이 피곤해진다.

**한국어 특수 사항** — 영어 기준 사례를 그대로 쓸 수 없다

| 특성 | 예 | 대응 |
|---|---|---|
| **목표를 생략함** | "공격한다" (대상 누락) | 씬 정보(누가 있나)를 반드시 함께 전달. **원 기획안이 이 부분은 잘 잡았다** |
| 어순이 자유로움 | "고블린 벤다" / "벤다 고블린을" | 어순 비의존 |
| 반말·존댓말·줄임말 | "일단 때려봄", "ㄱㄱ" | 실제 로그로 검증 |
| 오타 | | |

**정답 데이터 확보 — M0 실험의 부산물**

```
M0 킬 크리테리아 실험 (위협 시계 1개 손으로 만들어 3~4시간 굴려보기)
        ↓
   실제 입력 세션당 약 80개  →  사용자 실험 2세션 = 약 160개
        ↓
   사람이 정답 라벨 부여  →  첫 정답 데이터
        ↓
   사내 플레이로 약 140개 보충  →  300개
```

**단위를 명시한다.** 80은 세션당, 160은 사용자 실험 2세션 합계다(D30 측정 표의 숫자가 이것이다). H4가 요구하는 300개 중 나머지 약 140개는 **우리가 직접 굴린 세션에서 수집한다.** 사내 플레이는 재미 가설(H1)을 측정하지 못한다 — "우리는 GM을 하지 않고 관찰만 한다"는 규칙은 H1 때문이며, 파서 마찰 측정에는 그 제약이 적용되지 않는다. 우리가 굴린 세션의 입력 문장도 정답 데이터로는 동일하게 유효하다.

**80개는 적지만 우리가 상상해서 쓴 500개보다 낫다.** 실제 유저 문장은 예상과 다르다. 별도 작업이 아니라 실험의 부산물이다.

**부수 용도 — 저가 모델 객관 비교 (D19)**

정답 데이터가 생기면 같은 300개를 여러 모델에 돌려 위 실패 유형별로 비교할 수 있다. **여기가 원가 절감의 유일한 안전 지대다** — 서사 품질과 달리 숫자로 판단 가능하다.

### D29. 라이선스·저작권 정책

**층:** 전부 ① 플랫폼 정책.
**전제:** 아래는 정책 설계와 확인 필요 항목 정리이며 **법적 결론이 아니다.** 법무 이관 목록을 말미에 정리했다.

**원 기획안의 오해 정정**

> 원문: "D&D 5e SRD 5.1(CC-BY-4.0) 문서 기반 (고유 명칭 및 공식 세계관 명사는 리브랜딩 **우회**)"

두 가지가 섞여 있고 "우회"라는 표현이 잘못됐다.

| | 실제 |
|---|---|
| SRD 내용 사용 | **우회가 아니라 허가다.** CC-BY는 조건(저작자 표시)을 지키면 자유롭게 쓰라는 라이선스. 표시를 빠뜨리는 것이 위반 |
| 공식 세계관 고유명사 | **애초에 SRD에 없다.** 우회가 아니라 범위 밖. 리브랜딩은 별개 작업 |

"우회"라는 단어가 나온다는 것 자체가 라이선스를 규제로 오해했다는 신호다. 실제로는 **우리가 지켜야 할 의무가 있는 허가**다.

던전월드도 동일 — CC BY 3.0이므로 저작자 표시 필수. 원 기획안의 "완벽 인용"은 모호하며, 구체적으로는 **서비스 내 명시된 위치에 고지문 게재**다.

**보호되는 것과 안 되는 것**

| 보호 안 됨 (사용 가능) | 보호됨 |
|---|---|
| **게임 메커니즘 자체** ("d20을 굴려 목표값을 넘으면 성공") | 룰북의 **문장** |
| 판정 구조, 수학 | **고유명사** (몬스터·주문·지명·인명) |
| | 표의 창작적 배열, 삽화, 레이아웃 |

**첫 줄이 사업의 기반이다.** 메커니즘이 보호되지 않으므로 판정 방식을 코드로 구현하는 것 자체는 문제없다.

**리트로클론은 대체로 합법.** 메커니즘을 가져오되 문장과 고유명사를 새로 쓴 것. 패스파인더가 D&D 3.5를 그렇게 계승했고 선례가 다수다. **초기 분석에서 이를 침해로 오해하고 리스크를 과대평가했다 — 정정한다.**

**세 종류의 콘텐츠**

| 종류 | 정책 |
|---|---|
| 우리가 제공하는 룰북 | 오픈 라이선스만. 고지문 게재 |
| 유저가 올린 룰북 | 아래 3단 구조 |
| 유저가 만든 시나리오(위협 시계) | 대체로 자작이므로 리스크 낮음 |

**유저 업로드 — 공개 범위에 따라 3단**

| 범위 | 정책 |
|---|---|
| **비공개** (본인만) | 관대 |
| **초대한 친구만** | 관대. 기록 보존 |
| **공개 마켓** | **엄격** — 라이선스 선언 + 유사도 검사 + 등록 검수 |

배포와 사적 이용은 법적 취급이 다르다. 이 선을 시스템으로 그으면 리스크가 세 번째 칸에 모인다.

공개 등록 시: ① 라이선스 선언 강제(자작 / 오픈 라이선스+출처 / 기타 — 선언 없으면 공개 불가) ② SRD 원문 유사도 자동 검사, 임계값 초과 시 보류 ③ 신고 창구 + 처리 절차(없으면 플랫폼 책임 제한 주장이 어렵다).

**D26의 원문 보관 구조가 여기서 유리하다** — 유사도 검사를 걸 대상이 명확하다.

**AI 생성물의 권리 — 저작권이 아니라 약관으로 설계한다**

수익 모델의 전제다: 캠페인 기념품(D20)과 유저 시나리오 마켓의 내용물은 AI가 쓴 서사다. 그런데 **AI 생성물의 저작권 성립 여부 자체가 법적으로 불확실하다**(한국·미국 모두 인간의 창작성을 요구).

> **약관상의 이용권으로 설계한다.**
> 유저에게: 자기 플레이 기록의 이용·다운로드·판매 권리
> 우리에게: 서비스 운영에 필요한 범위의 이용권

저작권 성립 여부와 무관하게 작동하는 구조. 다만 문구는 법무가 작성.

**유저 룰북 수익화 — D20의 "금지"를 수정한다**

> ~~유저 룰북 수익화 금지~~ → **자작 오리지널에 한해 허용**
>
> 판단 기준은 **어느 판정 방식을 쓰는지가 아니라**(메커니즘은 보호 대상 아님) **문장과 고유명사가 자작인지**다.

절차: 자작 선언 → 유사도 검사 통과 → 수익화 신청 시 별도 검수.

**⚠️ 법무 이관 목록 (제 판단 범위 밖)**

| # | 항목 | 시급도 |
|---|---|---|
| 1 | **AI 실시간 생성 콘텐츠의 게임물 등급 분류** — 사전 심의가 구조적으로 불가능한 서비스 | **높음. 출시 전 필수** |
| 2 | **AI 생성물의 권리 귀속을 약관으로 어떻게 설계할 것인가** | **높음. 수익 모델의 전제** |
| 3 | 플랫폼 책임 제한 요건 충족 방법 (신고·삭제 절차의 법적 요건) | 높음. 유저 업로드 개시 전 |
| 4 | CC-BY 고지문의 구체적 문구와 게재 위치 | 중간. 출시 전 |
| 5 | 낯선 사람 매칭 시 성인 인증 의무 | 낮음 (D24로 M2 이후) |
| 6 | **해외 서비스 시 각국 요건** | 중간 |

**6번을 빠뜨리지 말 것.** 초기 타깃 정의에 "국내 그리고 국외"가 포함되어 있다. 국외 진출 시점에 관할이 늘어난다.

### D30. 마일스톤 0 결론 — 가설과 멈출 조건

**원 기획안에 없던 것.** 검증 기준 13개는 전부 "엔진이 작동하나"였고 **"이게 될 일인가"에 답하는 항목이 하나도 없었다.** V2 해결.

**검증할 가설 6개**

| # | 가설 | 확인 방법 | 멈출 조건 | 등급 |
|---|---|---|---|---|
| **H1** | **AI가 GM 노릇을 하면 재미있다** | 위협 시계 1개로 실제 플레이 | **참가자 대부분이 "두 번째 세션을 하고 싶지 않다"** | **진짜 킬** |
| H2 | 위협 시계가 AI의 봐주기를 막는다 | 실패 횟수 대비 시계 진행 횟수 집계 | 시계는 돌지만 **이야기가 억지스럽다** | 재설계 |
| H3 | 룰북을 데이터로 표현할 수 있다 | 판정 방식이 다른 룰북 2개를 같은 그릇에 | **두 번째 룰북이 안 들어간다** | 전략 변경 |
| H4 | 자유 텍스트 입력이 쓸 만하다 | 정답 데이터 300개로 마찰 측정 | **직접 찾아야 하는 비율 30% 이상** | 전략 변경 |
| **H5** | **원가가 사업 가능 범위 안이다** | 실측 (한국어 토큰, 실제 턴 수) | **1인 1시간당 $1 초과 + 저가 모델로도 안 내려감** | **진짜 킬** |
| H6 | TRPG 비경험자가 룰북 없이 시작할 수 있다 | 비경험자에게 캐릭터 만들기 + 30분 | 비경험자 대부분이 **캐릭터 만들기에서 포기** | 재설계 |

**멈출 조건 3등급**

| 등급 | 해당 | 뜻 |
|---|---|---|
| **진짜 킬** | H1, H5 | 프로젝트를 멈춘다 |
| 전략 변경 | H3, H4 | 제품은 살리되 사업 규모·정체성이 바뀐다 (H3 실패 시 유저 콘텐츠 마켓 소멸, H4 실패 시 "말하듯 플레이" 셀링포인트 소멸) |
| 재설계 | H2, H6 | 해당 부분만 다시 만든다 |

> **진짜 킬이 두 개뿐이라는 것이 중요하다.** M0 실험은 **H1과 H5에 우선 집중**한다.
> H5의 $1 기준 근거: 월 20시간 유저의 원가가 $20이 되면 어떤 가격 정책도 성립하지 않는다.

**실험 하나로 대부분을 잰다**

```
준비    위협 시계 1개 (손으로 4칸) / 룰북 1개 (판정 종류 10개 남짓) / 캐릭터 4개
        (절반은 미리 준비, 절반은 참가자가 직접 — H6 검증용)

참가자  TRPG 경험자 2명 + 비경험자 2명    ← 비경험자가 핵심. 타깃이 초심자
        우리는 GM을 하지 않고 관찰만 한다  ← 개입하면 H1을 못 잰다

진행    1세션 3~4시간  →  (1주 간격)  →  2세션 3~4시간
```

**1주 간격이 실험의 핵심이다.** "두 번째 세션에 왔는가"가 H1의 답이고, 시간을 두지 않으면 알 수 없다.

| 측정 | 답하는 가설 |
|---|---|
| **2세션에 몇 명이 왔나** | **H1 — 가장 중요** |
| 세션 완주 / 중간 흐지부지 | H1 |
| 실제 토큰 소모, 실제 턴 수 | **H5** |
| 실패 횟수 대비 시계 진행 횟수 | H2 |
| 비경험자가 캐릭터를 만들었나 | H6 |
| 실제 입력 문장 약 160개 (2세션 합계 · 세션당 80) | **H4의 정답 데이터** (D28. 300개까지는 사내 플레이로 보충) |
| "당신 캐릭터 어떤 사람이에요?" 대답 | 애착 형성 (D22 성공 기준) |
| 2세션 시작 시 이어할 수 있었나 | 재개 구조 (D11) |

H3만 별도 — 플레이 없이 데이터 작성만으로 확인된다.

**최소 도구 범위** (M0가 설계에서 살짝 넘어가는 지점 — 범위를 최소로 자른다)

| 필요 | 안 필요 |
|---|---|
| 텍스트 입력창 | 캐릭터 만들기 화면 (손으로 준비) |
| 행동 분류 + 확인 (최소 형태) | 매칭·로비 (링크 하나) |
| 주사위 (코드) | 코스메틱 |
| GM 서사 생성 | 룰북 저작 도구 (데이터를 손으로) |
| 위협 시계 상태 + 실패 카운터 | 리캡 자동 생성 (**손으로 써서 보여줘도 검증됨**) |
| 캐릭터 시트 (읽기만) | 안전 장치 UI (실험에서는 구두 대체) |
| 이벤트 기록 저장 | 결제·계정 |
| 여러 명이 같은 세션을 보는 것 | |

**제품이 아니라 실험 도구다.** 화면이 투박해도 H1을 재는 데 방해만 안 되면 된다.

**이 실험이 답하지 않는 것**

| 답 못 하는 것 | 언제 알 수 있나 |
|---|---|
| **낯선 사람과의 플레이** (참가자가 아는 사이면 검증 안 됨) | 매칭 도입 후 (M2) |
| **장기 캠페인** — 20세션 뒤 NPC 개성 유지, 복선 회수 | 실제 서비스 |
| 여러 룰북에서의 재미 | M1 이후 |
| 동시 접속 규모 | 실서비스 |
| 저가 모델의 서사 품질 | H1 통과 후 |

> **AI GM의 진짜 실패는 3시간이 아니라 30시간 뒤에 나타난다.** 이 실험은 "시작이 재미있나"만 답한다. 그래도 시작이 재미없으면 끝은 볼 필요가 없으므로 순서로는 이게 먼저다.

### D31. 기억 주입 규칙 — 장면에 있는 것만 넣는다

**층:** ① 플랫폼 기능. 룰북과 무관하게 우리가 정한다.

**해소하는 지적:** W6 (엔티티 장부 무한 성장 + "상시 주입" 설계 모순)

**문제.** 세션이 진행되면 만난 인물·물건·단서가 계속 쌓인다. 원 기획안은 이것을 매 턴 AI에게 전부 보여준다고 설계했다. 장기 캠페인에서 프롬프트가 터지고, 목록이 매 턴 바뀌므로 프롬프트 캐싱도 깨진다. 원가 계산의 전제(1인 1시간당 목표)가 무너진다.

**확정: 매 턴 넣는 것은 네 가지다.**

| 매 턴 넣는 것 |
|---|
| 현재 장면에 등장한 대상 |
| 내 캐릭터 상태 |
| 위협 시계 상태 |
| 최근 대화 몇 턴 (초기값 10턴, 실측으로 조정) |

나머지 저장소는 **이름 + 한 줄 색인만** 보인다. AI가 특정 항목의 상세를 필요로 하면 그 항목을 요청하고, 코드가 꺼내서 다음 턴에 넣는다.

**금지.** AI가 저장소 전체를 훑는 경로는 만들지 않는다. 원 기획안의 ~~"상시 주입"~~은 폐기한다. 사유: 세션 길이에 비례해 주입량이 늘어나는 구조는 원가와 캐싱 양쪽을 동시에 깨뜨린다.

**안전장치.** 턴당 토큰 예산 상한을 둔다. 넘치면 오래된 대화부터 요약으로 접는다. 단 다음 세 가지는 접지 않는다 — 접히면 안 되는 것을 명시해 두지 않으면 구현할 때 가장 먼저 접힌다.

| 접지 않는 것 | 왜 |
|---|---|
| 저장소 색인 | 접히면 AI가 무엇을 요청할 수 있는지 모른다 |
| 위협 시계 상태 | 원칙 4 — "시계가 아직 멈추지 않았다"가 재방문 동기다 |
| 관계 장부 (D11) | 원칙 4 — 재방문 동기의 재료는 시계만이 아니라 NPC와의 관계와 심어둔 복선이다 |

**캐싱과의 관계.** 룰북과 캐릭터 시트는 프롬프트 앞쪽에 고정되어 캐시가 붙고, 장면 정보만 뒤쪽에서 바뀐다. 주입량이 세션 길이와 거의 무관해지므로 원가가 예측 가능해진다.

**폐기한 대안.** 예산 상한만 두고 오래된 것부터 접는 방식 — 구현이 가장 단순하지만 "오래됐지만 중요한 것"(1세션에 심은 복선)이 접힌다. 장기 캠페인에서 가장 아픈 지점이다. 예산 상한은 이 결정에서 안전장치로만 쓴다.

**미룸.** 매 턴 관련 항목을 검색해서 꺼내오는 방식은 M0에 넣지 않는다. 검색 품질이라는 실패 지점을 추가하면 H1(AI GM이 재미있나)을 측정할 수 없게 된다. 장기 캠페인이 실제로 문제가 되는 시점(실서비스)에 재검토한다.

### D32. 적과 NPC의 숫자는 룰북이 선언한다

**층:** ② 표현 어휘. 그릇은 우리가, 내용은 룰북이.

**해소하는 지적:** M2 (몬스터 스탯블록 + 전투 AI 부재, 검증 케이스에 "적의 턴"이 없음)

**절반은 이미 해소되어 있었다.** 첫 타깃을 PbtA 계열로 정한 뒤(D4), 적의 행동은 닫힌 GM 대응 목록에서 나온다(D16). 별도의 전투 AI는 필요하지 않다.

**확정: 플랫폼이 정하는 것은 그릇뿐이다.**

| 플랫폼이 정하는 것 | 룰북 데이터가 선언하는 것 |
|---|---|
| 식별자 | 상태값 묶음에 어떤 항목이 있는지 |
| 표시 이름 | 각 값의 뜻 |
| 상태값 묶음 (키-값 그릇) | 특정 값이 바닥나면 무슨 일이 일어나는지 |
| 소속 룰북 | |
| 가시성 (D17) | |

상태 변경은 효과 표현(D7)을 통해서만 일어난다.

**저장.** 캐릭터와 같은 그릇을 재사용하고 유형으로만 구분한다. 성장·애착·인벤토리(D22, D25)는 캐릭터 유형에만 적용된다.

**금지.** 플랫폼 코드에 체력·피해·태그처럼 룰북 고유의 개념을 넣지 않는다. 이는 폐기한 ~~룰북별 전용 어댑터~~(D5)와 같은 실수의 다른 얼굴이며, 원칙 2 수정판(판정 커널은 코드, 룰북은 데이터)과 원칙 3의 마지막 줄("첫 타깃이 던전월드라는 이유로 던전월드의 규칙을 플랫폼에 박지 않는다")의 직접적 연장이다.

**대가.** 코드가 "체력"이라는 개념을 모르므로, 값이 바닥났을 때의 자동 처리를 룰북이 직접 선언해야 한다. 자동화율(D7)이 그만큼 룰북 작성 품질에 의존한다. 이 대가는 원칙 3이 요구하는 것이다 — 죽음의 관용은 룰북의 난이도 곡선 그 자체이므로 우리가 대신 정할 수 없다.

**범위.** 좌표계와 전술 그리드는 M4 유지(D13 ⑥).

**검증 추가.** H3(룰북을 데이터로 표현할 수 있다) 검증에 적 표현도 포함한다 — 두 번째 룰북의 적이 같은 그릇에 들어가는지 확인한다.

### D33. 응답 속도 목표와 초과 시 행동

**층:** ① 플랫폼 기능.

**해소하는 지적:** W8 (레이턴시 목표 자기모순 — E2E 3초 vs 무거운 모델 타임아웃 15초)

**폐기.** ~~"전체 3초"~~. 완결 기준이었고 달성 불가능하다. 사유: 무거운 모델의 첫 토큰이 1~2초, 완결이 5~10초다(원가 문서 §7 실측 기준).

**확정: 사람이 기다림을 느끼는 두 지점에 각각 목표를 둔다.**

| 구간 | 목표 |
|---|---|
| 문장 입력 → 행동 확인 표시 | 0.5초 |
| 확인 → GM 서사 첫 글자 | 2초 |
| 완결까지 | 목표 없음 (스트리밍이므로 체감은 첫 글자에서 결정된다) |

**초과 시 행동.**

| 상황 | 화면 |
|---|---|
| 첫 글자가 5초 초과 | 진행 표시를 띄운다 |
| 15초 타임아웃 | 판정 결과(주사위·성공/실패·시계 변화)를 먼저 내보내고, 서사를 뒤이어 붙인다 |

주사위와 판정은 순수 코드(D14)라 서사보다 먼저 끝나 있다. 추가 설계 없이 된다. 목표는 **"AI가 느려도 게임이 멈추지 않는다"**다.

**자체 호스팅.** 피크 대기로 첫 글자가 튀는 것은 이용률 계산에 포함한다(원가 문서 §7).

## 3. 마일스톤 로드맵

| | 내용 |
|---|---|
| **M0** | 타당성 검토 + 아키텍처 결정 + **킬 크리테리아 실험**. 판정 방식 2종(2d6 등급식, d100 롤언더), 위협 시계, 효과 DSL 골격 |
| **M1** | 실시간 파티(친구 초대 링크) · d20 판정 방식 · 노드 그래프 · 클루 웹 · 룰북 파일 업로드 · 안전 장치 1~3층 |
| **M2** | 공개방 매칭 · 톤 필터 · 신고·차단 · 성인 인증 · 솔로 모드 · 비동기 PbP · 다이스풀/Year Zero 판정 방식 · 테이블 생성 |
| **M3** | FATE 판정 방식 · UGC 마켓 본격화 |
| **M4** | D&D 5e 어댑터 + 전술 그리드 (⑥ 전술적 깊이 · 말·토큰 스킨) |

**M0에는 킬 크리테리아 실험이 포함된다.** 이 표의 이전 판은 M0을 "타당성 검토 + 아키텍처 결정"까지만 적어 설계가 끝나면 M0이 끝나는 것처럼 읽혔다. 설계 종결과 M0 종결은 다르다.

**M1은 친구 초대 링크만이다** (D24). 이 표의 이전 판은 M1에 ~~매칭/로비~~를 넣었으나 D24가 공개방 매칭을 M2 이후로 확정했으므로 표를 결정에 맞춘다. 함께 내려간 항목(공개방 목록·톤 필터·신고·차단·성인 인증)은 낯선 사람을 받는 순간 같이 필요해지는 묶음이라 분리할 수 없다. 룰북 파일 업로드(D26)와 안전 장치 1~3층(D23)은 M1 확정 항목인데 이전 판에서 빠져 있었다.

**용어.** 이 문서가 "커널"이라 쓰던 것을 기획 명세서와 맞춰 **"판정 방식"**으로 통일한다(용어 사전 방침 — 뜻이 드러나는 이름을 쓴다).

**M2의 솔로·비동기가 "거의 공짜"인 것이 D3 아키텍처를 택하는 이유다.**
